# migration — новый проект на фреймворке «Аврора»

Как развернуть Аврору в новом проекте и разложить накопленные документы. Ключевой
принцип — **движок ≠ знания**: копируется пустой движок, знания нового проекта
извлекаются из его же документов. Знания одного проекта в новый
проект НЕ переносятся — это чужая предметная область.

## Что переносится, а что нет

| Слой | Переносить в новый проект? |
|---|---|
| Движок: `aurora-vault`, скрипты, `Templates/`, `Prompts/`, `conventions.md` | ✅ да, вербатим (это `aurora_init.py`) |
| Sync-скиллы `confluence-sync-*`, `jira-export-*` | ✅ да, с заменой slug (делает init) |
| `AuroraKnowledgeDB/` карточки знаний | ❌ нет — это знания старого проекта |
| `Sources/`, `Raw/`, `Deliverables/`, `Artifacts/` | ❌ нет — контент старого проекта |
| `Reference/` справочники (аббревиатуры, участники) | ⚠️ только если **тот же домен/заказчик** (`--with-reference`). общие отраслевые аббревиатуры переиспользуются; проектные коды — нет |
| Decision Records | ⚠️ обычно нет; но DR о рабочем процессе (не о предметке) можно скопировать как отправную точку |

## Шаг 1 — развернуть движок

Из корня репозитория-эталона:

```
python3 .opencode/scripts/aurora_init.py ~/projects/НОВЫЙ \
    --name "ABVAT" --slug ABVAT \
    --confluence-url https://confluence.example.com --confluence-space ABVAT \
    --jira-url https://jira.example.com --jira-key ABVAT
```

Получаете чистый проект: движок + пустой скелет слоёв + `aurora.config.yaml` с новыми
адресами. `git init` в новой папке.

## Шаг 2 — разложить накопленные документы (миграция контента)

Накопленная по проекту информация раскладывается по слоям доверия **вручную или через
ingest-команды** — по природе документа, а не по формату:

| Что за документ | Куда | Как |
|---|---|---|
| Госконтракт, ТЗ, НПА, регламенты | `Raw/contract/`, `Raw/laws/` | положить как есть → `ingest-tz` / `ingest-raw` |
| Транскрибации и протоколы встреч | `Raw/meetings/` | → `ingest-meeting` |
| Материалы заказчика (AS-IS схемы, форматы) | `Raw/customer/` | → `ingest-raw` |
| Концепт-документы, первичные обзоры проекта | `Raw/project/` | → build-источники |
| Готовые US/AC, написанные ранее | `Artifacts/us/`, `Artifacts/ac/` | это продукты, не знания |
| Наработки под конкретную задачу (черновики, версии) | `Workspaces/<задача>/` | + строка в README |
| Уже сданные документы (ОПЗ, ПМИ) | `Deliverables/released/` | неизменяемо |

Правило разбора: **сначала кладём первоисточник в `Raw/`, потом извлекаем из него
карточки** — так сохраняется провенанс. Не создавайте карточки знаний напрямую из
головы, если есть документ-источник.

## Шаг 3 — настроить синхронизацию Confluence/Jira

Всё в `aurora.config.yaml` (движок и sync-скиллы читают только его):

1. **Jira** — `atlassian.jira.project_key` и при необходимости `default_jql` (по умолчанию
   «project = KEY ORDER BY updated DESC»).
2. **Confluence** — `atlassian.confluence.space` + список `sync_roots`: `page_id` и `title`
   корневых страниц, которые тянем. page_id виден в URL страницы
   (`viewpage.action?pageId=XXXX`). Тянется страница и всё её поддерево.
3. **Аутентификация** — `auth.mode: mcp_user`: каждый аналитик логинится в Cursor MCP
   (mcp-atlassian) своим аккаунтом. Токены в git не кладём (см. `DR-0002` про секреты).
4. Проверка готовности: `python3 .opencode/scripts/aurora_doctor.py`.

## Шаг 4 — первое наполнение базы

```
/confluence-sync-<SLUG>     # зеркала Confluence → Sources/Confluence
/jira-export-<SLUG>         # зеркала Jira → Sources/JIRA
/aurora-vault build         # извлечь карточки из Sources/ и Raw/project/ (все → draft)
/aurora-vault ingest-tz Raw/contract/...   # если есть ТЗ — требования и трассировка
/aurora-vault status        # дашборд: сколько карточек, доля knowledge (стартует в bootstrap)
```

Дальше — обычный цикл: `agent:build` → `kb:kind` → `agent:distill` → `ops:trace-table` →
`kb:trust` → `garden` (пятница). Доля `knowledge` растёт не приёмкой, а движением задач в
Jira. Пока она ниже 20 %, действует bootstrap-режим (черновики в контексте с пометкой) —
см. `retrieval.md`.

## Шаг 5 — проект уже имел зеркало Confluence (переезд на детерминированный экспорт)

Частый случай: проект синкал Confluence прежним LLM-скиллом, пути и формат отличаются от
того, что делает `confluence_export.py`. Порядок такой (иначе потеряется провенанс —
`source:` у карточек указывает на старые пути):

```
1. python3 .opencode/scripts/kb_remap.py --snapshot     # карта page_id → путь ДО переезда
2. git add -A && git commit -m "WIP до переезда зеркала"  # чистое дерево для отката
3. python3 .opencode/scripts/confluence_export.py       # собрать зеркало заново
4. python3 .opencode/scripts/confluence_export.py --prune  # убрать файлы старого зеркала
5. python3 .opencode/scripts/kb_remap.py                # dry-run: что перенацелится
6. python3 .opencode/scripts/kb_remap.py --apply
7. python3 .opencode/scripts/sync_audit.py              # должно быть 0/0/0/0
8. python3 .opencode/scripts/aurora_stats.py            # «битые источники» — остаток на разбор
```

Забыли снять снимок на шаге 1 — карта достаётся из истории:
`kb_remap.py --from-git <ревизия до переезда>`.

Как работает сопоставление: по **page_id** из старых файлов зеркала (понимает обе шапки —
`page_id:` нового экспортёра и `- **ID:**` прежнего синка), затем по нормализованному
заголовку с учётом гомоглифов. Что не легло ни туда ни туда — попадает в отчёт: это
страницы, удалённые из Confluence или лежащие вне синкаемых корней. Их решает человек:
перенацелить вручную, снять `source:` или деприкейтнуть карточку. Скрипт не угадывает.

Опыт живого переезда (1971 карточка): 829 сопоставилось по id, 209 по заголовку,
135 уже были верны, 149 осталось человеку; «битые источники» упали с 1241 до 206.

Осторожно с macOS: если старое зеркало содержало папку, отличающуюся только регистром,
запись новой перехватывается старой. Симптом — `sync_audit` показывает MISSING/MOVED
сразу после экспорта. Лечится сносом затронутого каталога и повторным экспортом.

## Что править руками после init (движок этого не знает)

- В `Prompts/` персона-тексты содержат плейсхолдер `{{ПРОЕКТ}}` — подставьте имя проекта.
- `build.md` таблица «Primary Sources» перечисляет первичные доки проекта-источника
  (`00._Main_process.md` и т.д.) — заменить на первичные доки нового проекта или
  очистить (build подхватит `Raw/project/*` в любом случае).
- Confluence-страницы фреймворка «Аврора БЗ 0–6» — общие, публикуются один раз на
  пространство; для нового проекта либо переиспользуются, либо копируются в его space.
