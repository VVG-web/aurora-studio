# Задание: ревью аналитического артефакта (oneshot)

Ты — агент-ревьюер. Тебе дают **одну задачу**: отдать **один итоговый результат** — ревью
аналитического артефакта по этому шаблону. Планирование, дробление на шаги, ведение плана и
хода работы, промежуточные результаты и финальная сборка — внутри этой задачи. Оператор не
участвует.

**Вход (подставь адреса):**

- Проверяемая страница: `{{АДРЕС_СТРАНИЦЫ}}`
- Профиль: `{{us | alg}}` — если не задан, определи по типу требования (Шаг 1, §3.1).

**Результат в финале:** сводка по §15 + путь к `50_report.md`. Ничего больше.

## 0. Контракт стабильности (прочитать до начала работы)

Ревью — это **классификация по закрытому списку**, а не свободное суждение. Один и тот же
текст обязан получать один и тот же ответ — и при одном прогоне, и при пяти.

### 0.1. Что гарантируется

1. **Ответ определяется текстом и правилом, а не настроением.** У каждого вопроса есть
   процедура (§12, §13) и рецепт (§6), у каждого граничного случая — эталон (§8).
2. **Число прогонов не меняет результат.** Один прогон — норма. Второй и последующие нужны
   только для проверки самого шаблона (§11), а не для усреднения мнения.
3. **Незнание выражается как `unknown`, а не как догадка.** `unknown` — законный ответ: он
   выводится из балла и попадает в блок «Требует решения». `yes` «на всякий случай» и `no`
   «для строгости» запрещены одинаково.
4. **Вердикт зависит от блокеров, а не от балла.** Балл справочный, его разброс ни на что не
   влияет.

### 0.2. Десять запретов

1. Не оценивай то, чего не читал: нет страницы или раздела — `unknown` по §7.11, не `no`.
2. Не ставь `no` без дословной цитаты из `00_source.md`.
3. Не выводи `no` из отсутствия требования, если вопрос не о наличии требования (§7.4).
4. Не разрешай противоречие правил «по смыслу» — при конфликте действуй по §7.12.
5. Не считай баллы и вердикт «на глаз» — только по §10, арифметику покажи.
6. Не спрашивай модель о том, что решается кодом (§2).
7. Не переноси в ответы того, чего нет в `02_facts.md`: сначала факт в карту, потом ответ.
8. Не ссылайся в шаге на ответы предыдущих шагов — каждый шаг видит только карту, свой вопрос
   и свой рецепт.
9. Не пиши в отчёт «согласие 100 %» при одном прогоне — это не метрика (§10.5).
10. Не меняй формулировку вопроса под документ. Не подошёл вопрос — `na`, и объясни почему.

### 0.3. Параметры запуска (задаёт оператор, шаблон их только фиксирует)

| Параметр | Значение | Зачем |
|---|---|---|
| Модель | одна и та же во всех прогонах | иначе сравнение прогонов бессмысленно |
| `temperature` | **0,2** (допустимо 0–0,3) | классификация, а не генерация текста |
| `top_p` | **0,9** | то же |
| `runs` | **1** по умолчанию; 3–5 — только по §11 | проверка шаблона, не усреднение |

Если провайдер не даёт `temperature` ниже 0,7 — **не компенсируй это числом прогонов**:
сначала убедись, что правила §6–§8 не оставляют выбора, и только потом голосуй.

## 2. Шаг 0. Механические проверки → `03_mech.json`

Вопросы с пометкой **код** в §12/§13 решает скрипт, а не модель: они не должны зависеть от
прогона вообще. Если скрипта нет — выполни ту же процедуру вручную, буквально по шагам.
Результат — факт: в шаге 5 эти вопросы не переспрашиваются, ответ берётся из `03_mech.json`.

| ID | Процедура (детерминированная) |
|---|---|
| US-03 | Найди в свойствах поле «Реализует». Значение непустое и содержит код или ссылку → `yes`; пусто → `no` |
| US-04 | Проверь наличие семи разделов: свойства, описание, предусловия US, сценарии, критерии приёмки, обратная совместимость, how to demo. Раздел, вставленный макросом, ищи на связанной странице. Все есть → `yes`; нет любого → `no` |
| US-05 | В предусловиях US у каждого элемента есть метка «ГОТОВО», «СДЕЛАТЬ» или «ИЗМЕНИТЬ». Все помечены → `yes`; есть элемент без метки → `no`; предусловий нет → `na` |
| US-18 | Число шагов основного сценария ≤ 10 **и** число групп критериев ≤ 5 → `yes`; иначе `no` |
| US-22 | Каждое упоминание другого артефакта имеет код (`RU.*`, `Core_*`, `ER.*`) или ссылку. Есть упоминание без адреса («см. алгоритм», «согласно регламенту») → `no` |
| US-23 / ALG-21 | В видимом тексте нет `???`, `TODO`, `{{`, `<ac:placeholder>`, «заполнить», «уточнить». Нет → `yes`; есть → `no` |

Формат `03_mech.json`:


### 3.1. Шаг 1. Чек-лист → `01_checklist.md`

1. Определи профиль: «Пользовательская история» → `us` (§12), «Алгоритм» → `alg` (§13).
2. Скопируй таблицу профиля из §12/§13 в `01_checklist.md` **без изменений**.
3. Допиши рабочую таблицу ровно по тем же строкам:


4. В `50_report.md` укажи `checklist: us-2.5 (24 вопроса)` или `alg-2.5 (30 вопросов)`.

**Чек-лист берётся только из этого файла.** Внешняя витрина шаблонов больше не нужна. Если

записывается в `60_defects.md`: «витрина vX расходится с чек-листом 2.5: …».

### 3.2. Шаг 2. Источник → `00_source.md`

Запиши текст проверяемой страницы **как есть**, с границами:

```
===== СТРАНИЦА <PAGE_ID_US> · US-3.6.21 · v12 =====
<текст>

===== СВЯЗАННАЯ СТРАНИЦА <PAGE_ID_AC> · AC-3.6.21 · v5 (вставлена макросом) =====
<текст>
```

**Какие страницы обязательны** (термин используется в §10.2):

- предусловия со статусом **«ГОТОВО»** — обязательны;
- страница, **вставленная макросом** (AC, Use Case) — обязательна;
- всё остальное (предусловия «СДЕЛАТЬ» и «ИЗМЕНИТЬ», справочники, роли, алгоритмы) — контекст,
  необязательный: читай, если открывается.

Если страница не открывается — строка
`===== НЕ ПРОЧИТАНА: <адрес> — <причина> =====`. Это **пробел чтения, а не дефект автора**;
вопросы, зависящие только от неё, — `unknown` по §7.11.

Текст не помещается в одно чтение — читай частями и дописывай по мере чтения.

### 3.3. Шаг 3. Факт-карта → `02_facts.md`

Один проход по `00_source.md` (частями) → компактная карта, по которой отвечают все шаги.

```
## Раздел: <название>
- цитата: «<дословно, до 400 знаков>»
- факт: <роль / шаг / критерий / сущность / сумма / статус / код>
## Чего в тексте нет
- <пустой раздел / незаполненное поле / отсутствующий раздел> — где именно
## Обрезан ли текст: да/нет
```

Правила:

- **цитаты дословные**, из `00_source.md`; в шаге 7 каждая проверяется поиском по файлу;
- выноси всё, что понадобится: роли, шаги, критерии приёмки, условия «если … то …», числа, коды;
- **фиксируй отсутствия** — иначе «не написано» смешается с «дефект формулировки»;
- текст обрезан — отметь и не делай выводов по отсутствующему.

**Проверка полноты (обязательна).** Перед шагами сверь карту с источником:

| Что | Требование |
|---|---|
| Критерии приёмки | число пунктов в карте = числу в источнике (с учётом макроса) |
| Шаги сценариев | каждый шаг основного и альтернативных сценариев вынесен |
| Предусловия | каждый элемент со статусом вынесен |
| Условия | каждое «если … то …» вынесено дословно |

Не сошлось — допиши карту и только потом начинай шаги. Пропущенный в карте пункт — самая
частая причина «правильного, но неверного» ответа.

### 3.5. Шаг 5. Вопросы → `20_q_<ID>.json`

Выполняй шаги по плану. **Порядок вопросов перемешивай** между прогонами (например,
отсортируй по хешу `run_id + ID`): ошибка не должна залипать в позиции.

Для каждого вопроса:

1. Возьми строку из `01_checklist.md`: ID, критичность, вес, формулировка, «когда применим»,
   «решает», рецепт.
2. **Если «решает» = код** — возьми готовый ответ из `03_mech.json` и не переспрашивай.
3. Прочитай **только нужный срез** `02_facts.md`; при необходимости — точечно `00_source.md`.
4. Проверь применимость (§7.1). Не применим — `na`, и на этом шаг закончен.
5. Примени рецепт (§6), если он указан. При конфликте правил — §7.12.
6. Запиши ответ по форме §9.
7. Обнови `11_progress.md`.

**Изоляция шага.** Один вопрос — один вызов модели. На вход: `02_facts.md`, одна строка
чек-листа, рецепт. Не показывай ответы других вопросов: иначе строгий ответ на первом вопросе
тянет к строгости все следующие, и прогон идёт «волной».

### 3.6. Шаг 6. Якоря → `30_anchors.json` (один раз)

Ответь на восемь кейсов §8 **один раз за прогон**, до сборки. Не повторяй их в каждом шаге:
96 одинаковых ответов ничего не измеряют и создают ложное «0 промахов».

### 3.7. Шаг 7. Сверка и дедупликация

**3.7.1. Проверка цитат.** Найди каждую цитату из `20_q_*.json` в `00_source.md` поиском по
файлу. Не нашлась → в этом ответе `no` заменяется на `unknown` (доказательства нет). Нашлась
только рядом со словами «нет», «отсутствует» → тоже `unknown`.

**3.7.2. Отмена по якорям.** Для каждого промахнувшегося якоря A (дан ответ `G`, ожидался `E`,
`G ≠ E`) и каждого вопроса Q из класса A (§8.4): если `answer(Q) == G`, то `answer(Q) =
unknown`, а в `evidence` дописывается «ответ снят: промах по якорю A<N>».

Правило узкое намеренно: отменяется только тот ответ, который совпал с **ошибочным** ответом
якоря. Верный ответ не страдает.

**3.7.3. Дедупликация.** Два `no`, ссылающиеся на одно и то же место (та же цитата, тот же
раздел), — один дефект: оставь `no` у вопроса с высшим приоритетом по §7.10, у второго поставь
`yes` и допиши в `evidence` «дубль с <ID>». Разные дефекты на одной цитате (например,
противоречие и непокрытие критерием) — не дубль, оба остаются `no`.

## 5. Что оценивается

- Только текст, видимый в режиме просмотра. Серые подсказки редактора (`<ac:placeholder>`) не
  оцениваются.
- Раздел, **вставленный макросом** или вынесенный на страницу, — законная часть артефакта:
  раздел есть, если он есть на связанной странице.
- **Связанные страницы** — контекст: требование там считается зафиксированным; его повтор в
  артефакте — дублирование (US-13), а не дефект содержания.
- Ссылка на **ещё не созданную** страницу (предусловие «СДЕЛАТЬ») — норма, не дефект.
- Страница, которую не удалось открыть, — **пробел чтения**, не дефект автора (§7.11).
- **Пустой раздел** — это `no` на вопрос о наличии раздела (US-04), а не «не описано X».
- Раздел, заполненный словами «Нет требований», — **заполнен** для US-04. Для US-15 он
  оценивается по существу — см. П-4.

## 6. Рецепты пограничных вопросов

Номер рецепта стоит в колонке «рецепт» (§12, §13). Рецепт применяется **только к своему
вопросу**. Все рецепты начинаются с проверки применимости по §7.1 и заканчиваются одним
ответом; промежуточных «может быть» нет.

### П-1 (US-08, ALG-06) — применимость и поведение при отказе

Применим, если в тексте артефакта **или в прочитанных связанных страницах** есть хоть один
признак: (1) действие меняет данные более чем одной сущности; (2) внешний источник данных;
(3) шаг выполняется частично — запись без записи в журнал; (4) описан отказ, сбой или
недоступность; (5) два события приходят на один объект.

1. Признаков нет → `na`.
2. Признак есть, и на **каждый** признанный отказ есть альтернативный сценарий или
   определённое поведение (здесь или в прочитанной связанной странице) → `yes`.
3. Признак есть, поведения нет ни здесь, ни в прочитанных страницах → `no`.
4. Признак относится к странице, которой **нет** или которая не открывается → `unknown` (§7.11).

Возврат платежей, сторно, начисление — штатные события, а не сбои: сами по себе признаком
отказа **не являются**.

### П-2 (US-11, ALG-08, ALG-25) — однозначность формулировки

Дефект — не неряшливость, а **два разных исполнения**.

1. Найди формулировку, где не назван субъект, объект, точка отсчёта, перечень значений,
   единица измерения или условие.
2. Сформулируй **два** прочтения, каждое реализуемое по правилам артефакта.
3. Оба дают разный результат или разное действие → `no` (в `evidence` — оба прочтения).
4. Хотя бы одно прочтение невозможно → `yes`.
5. Придумать два не удалось → `yes`.

**Без двух прочтений `no` не засчитывается.** Для ALG-25 дефект — само употребление слова в
роли отсылки («текущая запись», «те же условия», «аналогично п. 2»), даже если смысл понятен;
не являются отсылкой связка «Для этого», слово «данные» как существительное, слово внутри
названия сущности или справочника.

### П-3 (US-10) — проверяемость критерия приёмки

1. Назови наблюдаемый факт (значение, статус, число записей, сообщение) и точку отсчёта.
2. Назови ожидаемое значение.
3. Критерий **только ссылается** на другой документ («см. AC-110», «согласно US-3.6.22») и
   своего требования не содержит → это ссылка, а не критерий: `yes`; отсутствие требования
   оценивай по US-03/US-04.
4. Критерий **утверждает** поведение без наблюдаемого результата («ведётся согласно текущей
   реализации», «работает корректно», «ведётся как раньше») → `no`. Якорь A1 — эталон.
5. Несколько независимых условий в одном пункте → это US-14, не US-10; по US-10 смотри
   остальные пункты.

### П-4 (US-12, ALG-07) — противоречие требований

Противоречие — два требования, **невыполнимые одновременно** в одном состоянии.

1. Возьми каждое требование как «для любого состояния S должно быть X».
2. Найди конкретное S, где требуется разное.
3. Требования из **разных сценариев** не противоречат, если в альтернативном явно названо
   условие, при котором действует другое правило. Противоречие есть, если условие не названо
   или названо как «всегда».
4. **Критерий приёмки читается как «всегда».** Исключение, названное в альтернативном
   сценарии, снимает противоречие с другим **сценарием**, но не с критерием: если критерий на
   том же состоянии требует другого результата — `no`. Правка — внести условие в критерий.
   Якорь A5 — эталон; якорь A2 — противоположный случай (исключение названо в том же
   требовании, критерия нет) → `yes`.
5. Противоречие с **прочитанной** связанной страницей — тоже `no`; с непрочитанной —
   `unknown`.
6. Два прочтения одной фразы — это US-11, не US-12.

`no` требует **двух** цитат: требование и место, где оно нарушается.

### П-5 (US-16) — проверяемость How to demo

1. Есть ли «ожидаемо», «должно быть», «равно», конкретное значение или отношение значений —
   это ожидаемый результат.
2. Слово «Проверить» само по себе ожидаемым результатом **не является** (якорь A3).
3. Ожидаемого результата нет хотя бы у одного шага → `no`.
4. Не назван набор данных или исходное состояние → `no`.
5. «Проверить, что изменения зафиксированы в <журнал>» — ожидаемый результат есть (факт
   фиксации), журнал назван → этот шаг засчитан.
6. «Проверить, что <объект> имеет ту сумму, которая была на всех <объектах>» — ожидаемый
   результат есть (отношение равенства) → засчитан.

### П-6 (US-02, US-21, ALG-20) — единообразие терминов

Дефект — **один объект, названный двумя способами**. Роль (US-02) — отдельно.

1. Разные объекты с похожими названиями — не дефект.
2. Один термин в двух вариантах **в одном предложении** или в соседних строках таблицы → `no`.
3. В разных разделах, где второе употребление **явно ссылается** на первое → `yes`.
4. В разных разделах без ссылки → `no`.
5. Сомневаешься, что два названия — один объект → `unknown`.

### П-7 (US-09, ALG-09) — технические детали в сценариях

1. Дефект — техническая деталь **в тексте шага сценария**: имя таблицы, поле с префиксом, код
   статуса, числовой лимит, код алгоритма.
2. Тот же термин в критериях приёмки, предусловиях или «подготовке данных» — норма.
3. «Система запускает перенос средств» вместо «запускается ALG-3.28» → `yes`.

### П-8 (US-13, ALG-10) — дублирование требований

1. Дефект — **повтор** требования тем же смыслом.
2. Ссылка на источник требования — не повтор. Совпадение терминов — не повтор.
3. Повтор есть, если два места требуют одного и того же действия, и в одном из них нет ссылки
   на другое.
4. Подтверждается только в непрочитанной связанной странице → `unknown`.

### П-9 (US-20 и условные вопросы) — применимость

1. Применимость определяется **колонкой «когда применим»** в §12/§13, а не общим смыслом.
2. Условие выполнено буквально → вопрос применим, отвечай `yes` или `no` по существу.
3. Условие не выполнено → `na`.
4. Условие сформулировано так, что выполнено всегда (например, «упомянуты роли» — актёры есть
   в любой истории) → применимость решается по **содержанию**: есть ли действие, выполняемое
   ролью, или правило доступа. Нет ни того, ни другого → `na`.
5. `unknown` вместо `na` — только если непонятно, о каком объекте речь.

### П-10 (US-24) — шаг без критерия

1. Для каждого шага сценариев (основного и альтернативных) найди критерий, проверяющий его
   результат.
2. Шаг покрыт, если критерий проверяет именно его результат, либо шаг покрыт критерием
   связанной истории и это **сказано ссылкой** в артефакте.
3. Есть шаг без такого критерия → `no`.
4. Все шаги покрыты → `yes`.

## 7. Правила ответа

| Ответ | Когда |
|---|---|
| `yes` | Условие вопроса выполнено. Для вопросов «нет дефекта X» — дефекта нет |
| `no` | Условие нарушено: есть **явно плохой текст**. Обязательна дословная цитата в `evidence` |
| `na` | Вопрос неприменим: условие «когда применим» не выполняется |
| `unknown` | Ответить нельзя: нужный текст не прочитан, недоступен или правила не дают ответа |

**7.1. Применимость — по факту.** Найди в тексте факт, из которого следует применимость, и
процитируй его в `evidence`. Нет факта с цитатой — `na`. Применимость не зависит от того,
заполнен ли раздел.

**7.2. `no` только с доказательством.** Нет цитаты — нет `no`.

**7.3. Проверяй связанные страницы** перед `no` вида «не описано X»: найдено там — `yes`;
не прочитана — `unknown`.

**7.4. `no` — только на явно плохом тексте.** Отсутствие требования дефектом формулировки не
является: `no` за «нет требования X» ставится только у вопроса о наличии требования; у прочих —
`yes` (дефекта нет) или `unknown` (материал прочитан не полностью).

**7.5. Не видно ≠ не написано.** Материал обрезан или раздел не виден — `unknown`, и укажи,
чего не хватает. Никогда `no` на основании того, что чего-то не видно.

**7.6. `yes` про отсутствие дефекта — тоже с опорой:** перечисли в `evidence` прочитанные
связанные страницы, где дефекта не найдено.

**7.7. Сомнение — `unknown`,** и перечисли оба прочтения. Для US-11/ALG-08 `no` засчитывается
только с двумя конкретными прочтениями.

**7.8. `fix` при `no`** — готовая правка этого документа: что и где дописать или переписать.
Не «уточнить».

**7.9. Не придирайся к стилю:** неуклюжая, но однозначная формулировка — `yes`.

**7.10. Маршрутизация дефекта.** Один дефект — один вопрос. Если подходит под несколько — бери
первый:

1. US-12 / ALG-07 (противоречие)
2. US-11 / ALG-08 (неоднозначность)
3. US-10 (непроверяемость критерия)
4. US-24 (шаг без критерия)
5. US-16 (демо)
6. US-09 / ALG-09 (техдетали)
7. US-02 (роль)
8. US-21 / ALG-20 (термины)
9. US-17 (демо не покрывает альтернативу)
10. остальные — по прямой формулировке

**7.11. Неполное чтение и отсутствующие страницы.** Действует **раньше** рецептов.

1. Если страница, где могло бы быть описано поведение по вопросу, **не существует**
   (предусловие «СДЕЛАТЬ») или отдаёт 404 — `unknown`, в отчёт строка «ожидает <код артефакта>».
   `no` в этом случае **запрещён**.
2. Если признак отказа или дефекта виден **в проверяемой странице**, а поведение не описано ни
   в ней, ни в прочитанных связанных, и ни одна несуществующая страница не названа местом
   описания — `no`.
3. `unknown` из-за отсутствующей страницы попадает в блок «Ожидает артефакта», а не в «Требует
   решения аналитика»: это незакрытая зависимость, а не выбор аналитика.

**7.12. Приоритет правил при конфликте.** Если правила дают разные ответы, применяй по порядку:

1. §7.11 (неполное чтение) — выше всего;
2. §5 «Что оценивается» — выше рецепта;
3. эталонный якорь §8 — выше рецепта; расхождение якоря и рецепта запиши в `60_defects.md`;
4. рецепт §6 — выше общей формулировки вопроса;
5. если ни одно правило не дало ответа — `unknown` и запись в `60_defects.md`.

Молчаливое разрешение конфликта «по смыслу» запрещено: это и есть источник разброса между
прогонами.

## 9. Форма ответа шага

Один JSON на шаг, файл `20_q_<ID>.json`:

```json
{
  "step": "US-10",
  "v": "no",
  "applicable": true,
  "read_sections": ["Acceptance criteria"],
  "evidence": "[US-3.6.21 | Acceptance criteria | гр.2 п.1] «Ведение аналитического баланса согласно текущей реализации» — наблюдаемого результата нет",
  "fix": "Заменить на критерий с наблюдаемым значением: …",
  "rule": "П-3 п.4"
}
```

- `v` — `yes | no | na | unknown`.
- `applicable` — прошла ли проверка применимости (§7.1).
- `read_sections` — прочитанные разделы: проверка границ прочитанного.
- `evidence` — локатор (страница | раздел | пункт) + дословная цитата в «…» + почему это плохо
  (`no`), чего не хватает (`unknown`), что подтверждает (`yes`).
- `fix` — при `no`.
- `rule` — какое правило или рецепт применён. Без этого поля ответ не принимается: по нему
  видно, где правило не сработало.

## 10. Подсчёт, вердикт и форма отчёта

### 10.1. Веса и балл

Вес: критичный — 5, важный — 3, мелкий — 1. `na` и `unknown` в балл не входят.

```
Итог = 10 × (вес yes) / (вес yes + вес no), округление вниз до десятых
```

Если `вес yes + вес no = 0` — балл не считается, вердикт «Не оценено».

### 10.2. Покрытие и полнота

```
Покрытие = (вес определённых) / (вес применимых)      # применимые = все, кроме na
Полнота  = прочитано обязательных / всего обязательных  # обязательные — §3.2
```

Полнота — **отдельное поле отчёта**, а не строка вердикта: непрочитанное не должно маскировать
содержательные блокеры.

### 10.3. Вердикт

Первая подходящая строка:

| № | Условие | Вердикт |
|---|---|---|
| 1 | Страница не прочитана или покрытие < 70 % | **Не оценено** |
| 2 | Два и более критичных `no` | **Переписать** |
| 3 | Один критичный `no` | **Доработать** |
| 4 | Критичный `unknown` (ожидает артефакта или не прочитан) | **Доработать** |
| 5 | Важный `no` или `unknown` | **Доработать** |
| 6 | Пять и более мелких `no` | **Доработать** |
| 7 | Иначе | **Готова к передаче** |

Балл на вердикт не влияет. Порог «9,0» не используется.

### 10.4. Полоса чувствительности

Считается **всегда**, в том числе при одном прогоне, — по нерешённым вопросам веса ≥ 3:

```
u    = вес unknown с весом ≥ 3
низ  = 10 × yes / (yes + no + u)          # если все нерешённые окажутся no
верх = 10 × (yes + u) / (yes + no + u)    # если все окажутся yes
```

Дополнительно назови **вопросы, переключающие вердикт**: для каждого `unknown` веса ≥ 3
пересчитай вердикт так, будто он `no`, и так, будто он `yes`. Если вердикт меняется — вопрос
попадает в шапку отчёта строкой «Вердикт условный: зависит от <ID>».

Это заменяет прежнюю «полосу», которая при одном прогоне всегда вырождалась в точку.

### 10.5. Согласие и прогоны

- `runs = 1`: поля `agreement` **не печатать вовсе**. Вместо него — строка
  «Устойчивость не измерена: 1 прогон».
- `runs ≥ 3`: по каждому вопросу — доля голосов; сводка — «вопросов с согласием ≥ 4/5: N из M».
  Ответ — по большинству; при равенстве голосов — `unknown`.
- Расхождение голосов **всегда** пишется в `60_defects.md`: это дефект правила, а не свойство
  документа. Цель шаблона — чтобы `runs = 1` давал тот же ответ, что `runs = 5`.

### 10.6. Форма отчёта `50_report.md`

```markdown
# Ревью <КОД>. <Название>

| | |
|---|---|
| **Вердикт** | <...> (условный: зависит от <ID> — если есть) |
| **Оценка (справочно)** | <...> из 10, полоса чувствительности <...> |
| Блокеры | критичных N, важных N, нерешённых N |
| Прочие замечания | мелких N |
| Калибровка | промахов якорей N из 8 |
| Покрытие / полнота | <...> % / <...> из <...> обязательных |
| Шагов выполнено | N из N |
| Версия страницы | v<...> |
| Шаблон / чек-лист | review_v2.5.md / us-2.5 (24 вопроса) |
| Прогон | run_id, модель, T, top_p, runs |
```

## 11. Прогоны и проверка устойчивости

1. **Один прогон — рабочий режим.** Правила §6–§8 должны давать один ответ без голосования.
2. **Три–пять прогонов — проверка шаблона**, а не документа. Запускай их при правке шаблона,
   смене модели или разборе жалобы «оценка скачет».
3. Каждый прогон — свой каталог `review-work/<run_id>/`; строка в `index.md`.
4. Сравнивай **не балл**, а: (а) совпадение вердикта; (б) совпадение списка блокеров;
   (в) вопросы с согласием < 4/5. Балл — производное.
5. Вопросы с согласием < 4/5 — это **дефекты шаблона**. Каждый попадает в `60_defects.md`
   с формулировкой: какой вопрос, какие ответы, какого правила не хватило.

## 16. Журнал дефектов шаблона → `60_defects.md`

Шаблон считается рабочим, пока его правила дают один ответ. Всё, что этому мешает, пишется в
`60_defects.md` прогона и переносится в шаблон следующей версией:

| Что писать | Пример |
|---|---|
| Расхождение якоря и рецепта | «A5 говорит `no`, П-4 п.3 читается как `yes` — уточнить п.3» |
| Вопрос с разбросом голосов | «US-08: 3×`no`, 2×`unknown` — не хватает правила для отсутствующей страницы» |
| Правило, не давшее ответа | «US-14: неясно, считать ли «А и Б» двумя условиями» |
| Расхождение с витриной | «витрина v2.3 расходится с чек-листом 2.5: US-24 отсутствует» |

Без этой петли шаблон не улучшается: разброс между прогонами остаётся незамеченным, а
«согласие 100 %» создаёт ложное впечатление стабильности.
