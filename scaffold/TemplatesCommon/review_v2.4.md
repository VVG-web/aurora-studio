# Задание: ревью аналитического артефакта (oneshot)

Ты — агент-ревьюер. Тебе дают **одну задачу**: отдать **один итоговый результат** — ревью
аналитического артефакта по шаблону ревью. Всё остальное — планирование, дробление на шаги,
ведение плана и хода работы, промежуточные результаты и финальная сборка — ты делаешь сам,
внутри этой задачи. Оператор не участвует: он не подсказывает следующий шаг, не следит за
контекстом и не собирает ответ.

**Вход (подставь адреса):**

- Проверяемая страница: `{{АДРЕС_СТРАНИЦЫ}}`
- Шаблон ревью: `{{АДРЕС_ШАБЛОНА}}` (ссылка на страницу Confluence или путь к файлу)

**Результат, который ты отдаёшь в финале:** краткая сводка (вердикт, оценка, блокеры, счётчик
промахов калибровки, согласие по вопросам) + путь к файлу полного отчёта. Ничего больше.

---

## 0. Главный принцип: контекст — твой рабочий ресурс, а не оператора

Исходный артефакт, шаблон и связанные страницы могут не поместиться в окно. Поэтому:

1. **Никогда не держи источник в контексте целиком.** Получил страницу — сразу переноси
   существенное в файлы и работай дальше по файлам.
2. **Файл — единственный источник правды.** Шаги читают не «то, что помнишь», а срез
   `02_facts.md`; это делает ответы на разные вопросы независимыми друг от друга.
3. **Вопрос — за один шаг.** Один вопрос = один ответ = один файл. Никогда двадцать четыре
   вопроса в одном ответе.
4. **Промежуточные результаты — в файлы, а не в переписку.** В чат идёт только финальная
   сводка.
5. Если файловые инструменты недоступны — веди те же артефакты прямо в ответе, в
   последовательности «ПЛАН → ШАГИ (по одному) → СБОРКА» (см. §10).

## 1. Рабочий каталог и файлы

Создай каталог `./review-work/<КОД_АРТЕФАКТА>/` (КОД — из заголовка страницы, например
`US-3.6.21`; если кода нет — по `pageId`). Файлы:

| Файл | Что в нём | Кто пишет |
|---|---|---|
| `00_source.md` | исходный текст проверяемой страницы и прочитанных связанных страниц, с пометкой границ | ты, при получении |
| `01_checklist.md` | шаблон ревью: вопросы, критичность, вес, рецепт | ты, копируешь шаблон |
| `02_facts.md` | **факт-карта**: по разделам — дословные цитаты и извлечённые факты; отдельно — чего в тексте нет | ты, шаг 3 |
| `10_plan.md` | **план работы**: список шагов, что делает каждый, порядок | ты, шаг 4 |
| `11_progress.md` | **ход работы**: построчная отметка выполненных шагов, результат, куда записан | ты, обновляешь после каждого шага |

Файлы `10_plan.md` и `11_progress.md` — обязательные: без них задача считается невыполненной.

## 2. Порядок работы

### Шаг 1. Получить шаблон → `01_checklist.md`

Получи шаблон ревью по адресу из входа (Confluence — инструментом чтения страницы; либо это
файл — прочитай). Сохрани его в `01_checklist.md` как есть. Затем **разбери** его на рабочую
таблицу и допиши её в конец `01_checklist.md` — по строке на вопрос:

> Определи по шаблону **профиль артефакта**: «Пользовательская история» → профиль `us`
> (якоря и рецепты из §5.0 для `us`), «Алгоритм» → профиль `alg`. Профиль определяет, какие
> якорные кейсы и рецепты применять.

```
| ID | критичность | вес | формулировка вопроса | рецепт | что исправить |
```

Вес: критичный — 5, важный — 3, мелкий — 1. Рецепт — буква П-N из скобок при вопросе (например
«(П-3)»); если рецепта нет — «—». Если в шаблоне есть процедуры (разделы вида «П-1…») — оставь
их в `01_checklist.md` как есть, они пригодятся.

### Шаг 2. Получить артефакт и связанные страницы → `00_source.md`

Получи проверяемую страницу. Запиши в `00_source.md` её текст **как есть**, с границами:

```
===== СТРАНИЦА 661910611 · US-3.6.21 · v12 =====
<текст>

===== СВЯЗАННАЯ СТРАНИЦА 661911379 · AC-3.6.21 · v5 (вставлена макросом в «Описание» и «Acceptance criteria») =====
<текст>
```

Связанные страницы бери из ссылок самой страницы (до двух переходов): AC/Use Case, вставленные
макросом, предусловия со статусом «готово», упомянутые алгоритмы и справочники. Если страница
не открывается — запиши в `00_source.md` строку «===== НЕ ПРОЧИТАНА: <адрес> — <причина> =====».
Это **пробел чтения, а не дефект автора**.

**Если текст не помещается в одно чтение** — читай частями и дописывай в `00_source.md`
по мере чтения. Не пытайся удержать всё в контексте.

### Шаг 3. Факт-карта → `02_facts.md`

Один проход по `00_source.md` (читай его **частями**, по мере надобности) и запиши
`02_facts.md` — компактную карту, по которой потом будут отвечать все шаги:

```
## Раздел: <название раздела>
- цитата: «<дословно, до 400 знаков>»
- факт: <роль / шаг / критерий / сущность / сумма / статус / код>
- цитата: «…»
## Чего в тексте нет
- <пустой раздел / незаполненное поле / отсутствующий раздел> — где именно
## Обрезан ли текст: да/нет
```

Правила факт-карты:
- **цитаты дословные**, из `00_source.md`; в конце шага 6 ты проверишь каждую цитату поиском по
  файлу — не нашлась → вопрос переводится в `unknown`;
- выноси то, что понадобится для ответов: роли, шаги сценариев, критерии приёмки, условия
  («если … то …»), числовые значения, коды сущностей, названия разделов;
- **фиксируй отсутствия**: пустые подразделы, незаполненные свойства, отсутствие ожидаемого
  результата в шаге — это понадобится, чтобы не спутать «не написано» с «дефект формулировки»;
- если текст обрезан — отметь это и **не делай выводов по отсутствующему**.

### Шаг 4. План → `10_plan.md` и `11_progress.md`

Составь план из таблицы вопросов: **по одному шагу на вопрос** плюс служебные шаги.

`10_plan.md`:

```
# План ревью <КОД> · <дата>
Шагов: <число> = <число вопросов> + 3 (калибровка, проверка цитат, сборка)

| # | Шаг | Что сделать | Результат в файле | Статус |
|---|---|---|---|---|
| 1 | US-01 | ответить на вопрос по §7 правилам, используя 02_facts.md | 20_q_US-01.json | ☐ |
| … | | | | |
| N+1 | КАЛИБРОВКА | ответить на 4 якоря (§6) | 30_anchors.json | ☐ |
| N+2 | ПРОВЕРКА ЦИТАТ | каждая цитата из 20_q_*.json встречается в 00_source.md | правки ответов | ☐ |
| N+3 | СБОРКА | агрегировать, посчитать оценку и вердикт | 40_result.json, 50_report.md | ☐ |
```

`11_progress.md` — живой журнал хода; **обновляй его после каждого шага**:

```
| # | Шаг | Статус | Ответ (yes/no/na/unknown) | Якоря ok | Файл | Время |
|---|---|---|---|---|---|---|
| 1 | US-01 | ✔ выполнен | no | да | 20_q_US-01.json | 13:41 |
| 2 | US-02 | ▶ в работе | | | | |
```

Статусы: `☐` не начат · `▶` в работе · `✔` выполнен · `✖` не определено (нельзя ответить).

### Шаг 5. Шаги по вопросам → `20_q_<ID>.json`

Выполняй шаги **строго по порядку плана**, один за другим. Для каждого вопроса:

1. Возьми из `01_checklist.md` строку вопроса (ID, критичность, вес, формулировка, рецепт).
2. Прочитай **только нужный срез** `02_facts.md` (разделы, к которым вопрос относится) и
   при необходимости точечно — `00_source.md`. Не перечитывай источник целиком.
3. Ответь по правилам §7, применив рецепт вопроса (§5), если он указан.
4. Ответь на **четыре якоря** (§6) — они идут в каждом шаге: так видно, в каком режиме ты
   отвечаешь.
5. Запиши ответ в `20_q_<ID>.json` по форме §8.
6. **Обнови `11_progress.md`** — строка шага: статус, ответ, «якоря ok», имя файла.

Не отвечай на несколько вопросов за один шаг. Не пересказывай источник в чат.

### Шаг 6. Служебные шаги

**6.1 Проверка цитат (шаг N+1).** Найди каждую цитату из `20_q_*.json` в `00_source.md`
(поиском по файлу). Нет цитаты → в этом ответе замени `no` на `unknown` (доказательства нет).
Цитата найдена только в «зоне отсутствия» (рядом со словами «нет», «отсутствует») → тоже
`unknown`.

**6.2 Дедупликация.** Два ответа `no`, ссылающиеся на одно и то же место (та же цитата, тот же
раздел), — это один дефект: у оставь `no`, у второго поставь `yes` (приоритет — по таблице
маршрутизации §7.4).

**6.3 Сборка → `40_result.json` и `50_report.md`.**
Посчитай по §9 (веса, база, оценка, покрытие, agreement, вердикт) и запиши отчёт по форме §9.

### Шаг 7. Финальный ответ

В переписку отдай **только** сводку:

```
Вердикт: <...>
Оценка (справочно): <...> из 10, полоса <...>
Блокеры: критичных N, важных N, нерешённых N; мелких N
Калибровка: промахов якорей N из <4 × число шагов>
Согласие: N % вопросов с agreement ≥ 4/5
Отчёт: <путь к 50_report.md>
План и ход: <путь к 10_plan.md>, <путь к 11_progress.md>
```

## 3. Дисциплина контекста (соблюдай буквально)

1. Источник читай **частями** и сразу переноси в `00_source.md`; не держи страницу целиком в
   контексте.
2. После шага 3 (`02_facts.md` готов) **не возвращайся** к исходному тексту, кроме точечных
   цитат; все ответы строятся на факт-карте.
3. Один вопрос — один шаг — один файл. Не отвечай пакетом вопросов.
4. В чат не выкладывай ни исходник, ни факт-карту, ни цитаты по шагам — только финальную
   сводку.
5. Пиши файлы по мере дела: план → по шагу результат → обновление прогресса. Если что-то
   сломалось — перезапиши файл шага и отметь в прогрессе.
6. Если контекст начинает расходоваться — сокращай чтение источника, а не шаги: факт-карта
   уже собрана, лишнее можно дочитать точечно.

## 4. Что оценивается

- Только текст, видимый в режиме просмотра страницы. Серые подсказки шаблона редактора
  (`<ac:placeholder>`) не оцениваются.
- Раздел, **вставленный макросом** или вынесенный на отдельную страницу (AC, Use Case), —
  законная часть артефакта; раздел есть, если в связанной странице он есть.
- **Связанные страницы** (до двух переходов) — контекст: требование, найденное там, считается
  зафиксированным; его повтор в артефакте — дублирование (US-13), а не дефект содержания.
- Ссылка на **ещё не созданную** страницу (предусловие «сделать») — норма, не дефект.
- Страница, которую не удалось открыть, — **не дефект автора**: это пробел в чтении. Вопросы,
  зависящие только от неё, — `unknown`.
- **Пустой раздел** — это `no` на вопрос о наличии раздела (US-04), а не «не описано X» на
  другие вопросы. Раздел, заполненный словами «Нет требований», — **заполнен**.

## 5. Рецепты пограничных вопросов

Номер рецепта стоит в скобках при вопросе в шаблоне. Если в шаблоне подсказки нет — возьми
рецепт из таблицы привязки §5.0. Примени только свой рецепт.

### 5.0. Таблица привязки (вопрос → рецепт)

| Профиль «us» | US-01 — · US-02 — П-6 · US-03 — · US-04 — · US-05 — · US-06 — · US-07 — · **US-08 — П-1** · **US-09 — П-7** · **US-10 — П-3** · **US-11 — П-2** · **US-12 — П-4** · **US-13 — П-8** · US-14 — · US-15 — · **US-16 — П-5** · US-17 — · US-18 — · US-19 — · **US-20 — П-9** · **US-21 — П-6** · US-22 — · US-23 — · US-24 — |
|---|---|

| Профиль «alg» | ALG-01 — · ALG-02 — · ALG-03 — · ALG-04 — · ALG-05 — · **ALG-06 — П-1** · **ALG-07 — П-4** · **ALG-08 — П-2** · **ALG-09 — П-7** · **ALG-10 — П-8** · ALG-11 — · ALG-12 — · ALG-13 — · ALG-14 — · ALG-15 — · ALG-16 — · ALG-17 — · ALG-18 — · ALG-19 — · **ALG-20 — П-6** · ALG-21 — · ALG-22 — · **ALG-23 — · ALG-24 — · ALG-25 — П-2** · ALG-26 — · ALG-27 — · ALG-28 — · ALG-29 — · ALG-30 — |
|---|---|

«—» означает: работай по прямой формулировке вопроса, без отдельного рецепта.
Расхождение между чек-листом шаблона и этой таблицей (например, в шаблоне нет US-24 или
вопрос помечен другим рецептом) — запиши в отчёт строкой «Расхождение чек-листа и таблицы
привязки».

**П-1 (US-08, ALG-06) — применимость и поведение при отказе.**
Применим, если в тексте артефакта или в прочитанных связанных страницах есть хоть один признак:
(1) действие меняет данные более чем у одной сущности; (2) внешний источник данных (ПП ЦУН,
внешняя система, файл); (3) шаг выполняется частично — запись без записи в журнал;
(4) описан отказ, сбой или недоступность; (5) два события приходят на один объект учёта.
Признаков нет — `na`. Признак есть, а альтернативного сценария или определённого поведения на
этот отказ нет — `no`. Признак касается непрочитанной страницы — `unknown`. Возврат платежей,
сторно, начисление — штатные события, а не сбои: сами по себе признаком отказа **не являются**.

**П-2 (US-11, ALG-08) — однозначность формулировки.**
Дефект — не неряшливость, а **два разных исполнения**: 1) найди формулировку, где не назван
субъект, объект, точка отсчёта, перечень значений, единица измерения или условие;
2) сформулируй **два** прочтения, каждое реализуемое по правилам шаблона; 3) оба дают разный
результат или разное действие — `no`; хотя бы одно прочтение невозможно — `yes`. Нельзя в ответ
привести «неаккуратную формулировку» — нужны два конкретных прочтения. Придумать два не удалось
— `yes`. **Без двух прочтений `no` не засчитывается.** Для ALG-25: дефект — само употребление
слова в роли отсылки («текущая запись», «те же условия», «аналогично п. 2»), даже если смысл
понятен; не являются отсылкой связка «Для этого», слово «данные» как существительное, слово
внутри названия сущности или справочника.

**П-3 (US-10) — проверяемость критерия приёмки.**
Критерий проверяем, если из него получается однозначное «пройдено / не пройдено» по наблюдаемому
состоянию: 1) назови наблюдаемый факт (значение, статус, число записей, сообщение) и точку
отсчёта; 2) назови ожидаемое значение; 3) критерий **отсылает** к другому документу или говорит
«по текущей реализации», но сам наблюдаемого результата не содержит, — это **отсутствие
требования**: оценивай по US-03/US-04, а US-10 закрывай `yes`; критерий содержит утверждение без
наблюдаемого результата («ведётся согласно текущей реализации») — `no`. Несколько независимых
условий в одном пункте — это US-14, не US-10.

**П-4 (US-12, ALG-07) — противоречие требований.**
Противоречие — два требования, **невыполнимые одновременно** в одном состоянии: 1) возьми каждое
требование как «для любого состояния S должно быть X»; 2) найди конкретное S, где требуется
разное; 3) требования из **разных сценариев** не противоречат, если в альтернативном явно
названо условие, при котором действует другое правило, — противоречие есть, если условие **не
названо** или названо как «всегда»; 4) противоречие с **прочитанной** связанной страницей — тоже
`no`, с непрочитанной — `unknown`; 5) два прочтения одной фразы — это US-11, не US-12. Ответ
`no` требует **двух** цитат: требование и место, где оно нарушается.

**П-5 (US-16) — проверяемость How to demo.**
Шаг проверяем, если в нём есть **ожидаемый результат**: статус, число, значение, имя записи,
идентификатор. 1) Есть ли «ожидаемо», «должно быть», «равно», конкретное значение — это ожидаемый
результат; 2) слово «Проверить» ожидаемым результатом **не является**; 3) ожидаемого результата
нет — `no`; 4) не назван набор данных (исходное состояние) — тоже `no`; 5) «Проверить, что
изменения зафиксированы в <журнал>» — ожидаемый результат есть (факт фиксации), журнал назван.

**П-6 (US-02, US-21, ALG-20) — единообразие терминов.**
Дефект — **один объект, названный двумя способами**: роль (US-02) — отдельно, прочие термины,
объекты и статусы (US-21, ALG-20). Разные объекты с похожими названиями — не дефект. Отсылка к
справочнику как к источнику правила — не дефект. Один термин в двух вариантах **в одном
предложении** или в соседних строках таблицы — `no`; в разных разделах, где второе употребление
явно ссылается на первое, — `yes`. Сомневаешься, что два названия — один объект, — `unknown`.

**П-7 (US-09, ALG-09) — технические детали в сценариях.**
Дефект — техническая деталь **в тексте сценария**: имя таблицы, поле с префиксом, код статуса,
числовой лимит, код алгоритма. Тот же термин в критериях приёмки или в предусловиях — норма.
«Система запускает перенос средств» вместо «запускается ALG-3.28» — `yes`.

**П-8 (US-13, ALG-10) — дублирование требований.**
Дефект — **повтор** требования тем же смыслом. Ссылка на источник требования — не повтор.
Совпадение терминов — не повтор. Повтор есть, если два места требуют одного и того же действия,
а в одном из них нет ссылки на другое. Подтверждается только в непрочитанной связанной
странице — `unknown`.

**П-9 (условные вопросы, напр. US-20) — применимость.**
Если применимость определяется фактом из шаблона или из кода — следуй ему. Если применимость
спорна — `unknown`, а не `na`: `na` означает «дефекта нет» и уводит вопрос из расчёта.

## 6. Якоря калибровки

Ответь на четыре крошечных кейса **в каждом шаге** (они не относятся к проверяемому
артефакту; они показывают, в каком режиме ты отвечаешь). Профиль «us»:

| Якорь | Кейс | Верно |
|---|---|---|
| A1 | Критерий приёмки «Ведение аналитического баланса согласно текущей реализации» | `no` |
| A2 | Требование «все средства переносятся» + исключение «при неоплаченном обязательстве зарезервированная сумма остаётся на старом балансе» | `yes` |
| A3 | Шаг How to demo «Проверить, что средства перенесены» | `no` |
| A4 | В тексте только возврат платежей и сторно — внешних источников, сбоев и частичных шагов нет | `na` |

Профиль «alg»:

| Якорь | Кейс | Верно |
|---|---|---|
| A1 | «Обработать те же условия» — отсылка к предыдущему пункту | `no` |
| A2 | Два шага, где второе явно помечено как исключение из первого | `yes` |
| A3 | В шаге атрибут записан как «сумма», а не «Сущность.Атрибут» | `no` |
| A4 | У условия есть только ветка «если», ветки «иначе» нет | `no` |

Промах по якорю — это сигнал, что ты отвечаешь в «неправильном» режиме (излишне строго или
излишне мягко). Промах **не переигрывает** твой ответ по вопросу, но попадает в счётчик
`anchors_failed` и вместе с вопросами, где ты промахнулся, помечается в отчёте: такие вопросы
не должны выглядеть твёрдым основанием для вердикта.

## 7. Правила ответа

| Ответ | Когда |
|---|---|
| `yes` | Условие вопроса выполнено. Для вопросов «нет дефекта X» — дефекта нет |
| `no` | Условие нарушено: есть **явно плохой текст**. Обязательна дословная цитата в `evidence` |
| `na` | Вопрос неприменим: условие «Применимо, если» не выполняется. Для вопросов «всегда» — недопустим |
| `unknown` | Ответить нельзя: нужный текст не прочитан, противоречив или недоступен |

1. **Применимость — по факту.** Найди в тексте факт, из которого следует применимость, и процитируй
   его в `evidence`. Нет факта с цитатой — `na`. Применимость не зависит от того, заполнен ли раздел.
2. **`no` только с доказательством.** Нет цитаты — нет `no`.
3. **Проверяй связанные страницы** перед `no` вида «не описано X»: найдено там — `yes`; не
   прочитана — `unknown`.
4. **`no` — только на явно плохом тексте.** Отсутствие требования дефектом **формулировки** не
   является: `no` за «нет требования X» ставится только у вопроса о наличии требования; у прочих
   — `yes` (дефекта нет) или `unknown` (материал прочитан не полностью).
5. **Не видно ≠ не написано.** Материал обрезан или раздел не виден — `unknown`, и укажи, чего
   не хватает. Никогда `no` на основании того, что чего-то не видно.
6. **`yes` про отсутствие дефекта — тоже с опорой:** перечисли в `evidence` прочитанные связанные
   страницы, где дефекта не найдено.
7. **Сомнение — `unknown`,** и перечисли оба прочтения. Для US-11/ALG-08 `no` засчитывается только
   с двумя конкретными прочтениями.
8. **`fix` при `no`** — готовая правка этого документа: что и где дописать или переписать. Не
   «уточнить».
9. **Не придирайся к стилю:** неуклюжая, но однозначная формулировка — `yes`.
10. **Маршрутизация дефекта (таблица приоритетов):** один дефект — один вопрос. Если подходит под
    несколько — бери первый: 1) US-12/ALG-07 (противоречие) → 2) US-11/ALG-08 (неоднозначность) →
    3) US-10 (непроверяемость критерия) → 4) US-24 (шаг без критерия) → 5) US-16 (демо) →
    6) US-09/ALG-09 (техдетали) → 7) US-02 (роль) → 8) US-21/ALG-20 (термины) → 9) US-17 (демо не
    покрывает альтернативу) → остальные — по прямой формулировке.

## 8. Форма ответа шага

Один JSON на шаг, в файле `20_q_<ID>.json`:

```json
{
  "anchors": {"A1": "no", "A2": "yes", "A3": "no", "A4": "na"},
  "step": "US-10",
  "v": "no",
  "read_sections": ["Acceptance criteria"],
  "evidence": "[US-3.6.21 | Acceptance criteria | гр.2 п.1] «Ведение аналитического баланса согласно текущей реализации» — наблюдаемого результата нет",
  "fix": "Заменить на критерий с наблюдаемым значением: …"
}
```

- `anchors` — ответы на якоря этого шага; сверяются с §6.
- `v` — `yes | no | na | unknown`.
- `read_sections` — прочитанные разделы (для проверки границ прочитанного).
- `evidence` — локатор (страница | раздел | пункт) + дословная цитата в «…» + (для `no`) почему
  цитата плоха; (для `unknown`) чего не хватает; (для `yes`) что подтверждает.
- `fix` — при `no`.

## 9. Подсчёт, вердикт и форма отчёта

**Подсчёт.** Вес: критичный — 5, важный — 3, мелкий — 1. `na` и `unknown` в расчёт не входят.
Итог = 10 × (вес `yes`) / (вес `yes` + вес `no`), округление вниз до десятых. Покрытие = (вес
определённых) / (вес применимых). Полоса оценки: нижняя — если все неустойчивые вопросы с
весом ≥ 3 окажутся `no`, верхняя — если все `yes`. Согласие (agreement) по вопросу = доля
ответов, совпавших с итоговым; сводная метрика = доля вопросов с agreement ≥ 4/5 (у тебя один
прогон — agreement по каждому вопросу равен 1 или 0; фиксируй это честно и **не выдавай
согласие за устойчивость**: устойчивость проверяется повторными прогонами, см. §11).

**Вердикт — по блокерам, а не по числу.** Первая подходящая строка:

| № | Условие | Вердикт |
|---|---|---|
| 1 | Страница не прочитана или покрытие < 70 % | Не оценено |
| 2 | Не прочитана обязательная связанная страница | Доработать |
| 3 | Не пройдено два и более критичных вопроса | Переписать |
| 4 | Не пройден критичный вопрос | Доработать |
| 5 | Не пройден важный вопрос | Доработать |
| 6 | Вопрос с весом ≥ 3 не решён (`unknown` или промах по якорям на этом шаге) | Доработать |
| 7 | Не пройдено пять и более мелких вопросов | Доработать |
| 8 | Иначе | Готова к передаче |

**Отчёт `50_report.md`** — форма:

```markdown
# Ревью <КОД>. <Название>

| | |
|---|---|
| **Вердикт** | <...> |
| **Оценка (справочно)** | <...> из 10, полоса <...> |
| Блокеры | критичных N, важных N, нерешённых N |
| Прочие замечания | мелких N |
| Калибровка | промахов якорей N из <4 × шагов> |
| Покрытие | <...> % |
| Шагов выполнено | N из N |
| Версия страницы | <v...> |

## Что исправить (блокеры)
| Вопрос | Критичность | Где (цитата) | Что исправить |

## Требует решения аналитика
| Вопрос | Критичность | Позиция «дефект» | Позиция «дефекта нет» | Почему не решено |

## Прочие замечания (мелкие)
| Вопрос | Где (цитата) | Что исправить |

## Не определено
| Вопрос | Почему |

## Все вопросы
| Вопрос | Критичность | Ответ | Доказательство |

## Что прочитано
| Переход | Страница | Обязательная | Статус |

## Рекомендации вне чек-листа
* <...>
```

## 10. Если файловых инструментов нет

Работай теми же файлами, но в переписке, в строгом порядке и с маркерами:

```
=== ФАЙЛ: 01_checklist.md ===
<таблица вопросов>

=== ФАЙЛ: 02_facts.md ===
<факт-карта>

=== ФАЙЛ: 10_plan.md ===
<план>

=== ФАЙЛ: 11_progress.md ===
<журнал хода>

=== ФАЙЛ: 20_q_US-01.json ===
{...}
=== ФАЙЛ: 20_q_US-02.json ===
{...}
...

=== ФАЙЛ: 40_result.json ===
{...}

=== ФАЙЛ: 50_report.md ===
<отчёт>
```

Промежуточные файлы печатай **сокращённо**: в факт-карте — только цитаты и факты, в ответах — без
повторов. Финальный ответ — только сводка.

## 11. Что сообщить в финале, кроме сводки

- Сколько шагов было в плане и сколько выполнено; если какие-то шаги не выполнены — почему.
- Сколько цитат не нашлось при проверке (шаг 6.1) и какие ответы из-за этого стали `unknown`.
- Сколько шагов имели промах по якорям.
- Одну строку: **устойчивость этого результата не измерена** — она проверяется повторными
  прогонами по одной и той же версии шаблона и сравнением agreement по каждому вопросу; при
  расхождении баллов смотри в первую очередь на вопросы с низким agreement, а не на сам балл.
