<!-- ============================================================
     ПРАВИЛА ДЛЯ ИИ: тип decision — Решение (запись)
     ============================================================

ЖАНР. Decision Record — запись о выборе из вариантов: что решили, из чего выбирали, почему именно
так и почему не иначе. Это запись человека: движок её не пишет, не пересказывает и не сливает с
другими. Её нельзя вывести из источников, поэтому она живёт в `Raw/decisions/` и переживает любую
пересборку базы; в базе остаётся дословное зеркало.

1. РАЗДЕЛЕНИЕ ОТВЕТСТВЕННОСТИ:

   | Раздел | Что в нём живёт | Чего в нём быть НЕ должно |
   |---|---|---|
   | Контекст | какая задача потребовала решения; ссылки на US, процессы, карточки | пересказа документов, оценок вариантов |
   | Рассмотренные варианты | ВСЕ варианты, включая отклонённые: плюсы, минусы, **причина отказа** | вариантов, которых не рассматривали |
   | Решение | что решили и кто участвовал | обоснования (оно в вариантах) |
   | Следствия | что меняется; **«Затронутые карточки: [[…]]»** | новых решений |
   | История | строки «дата — событие (кто)» | правок прошлых решений |

2. ЦИКЛ РЕШЕНИЯ (`status`): `proposed` → `accepted` | `rejected` → `superseded`.
   `status` у записи — состояние решения, а не класс доверия: `kb:trust` такие карточки не пересчитывает.
   В контекст ответа строгого режима попадает только `accepted`; `proposed` помечается «НЕ ФАКТ».

3. НЕИЗМЕНЯЕМОСТЬ (append-only). Принятое и отклонённое решение не правят. Единственная правка —
   перевод в `superseded` с заполнением `superseded_by`, когда его заменило новое решение.
   Отклонённые варианты остаются в теле навсегда. Запись не удаляют.

4. СВЯЗИ. Запись обязана ссылаться на карточки знаний, которых касается («Затронутые карточки»);
   карточки знаний на запись вручную не ссылаются — обратную связь даёт граф и карта «Решения».
   Заменяющее решение называет прежнее в `supersedes`.

5. НОМЕР И ИМЯ. `DR-NNNN-<кратко-суть>.md`, NNNN — следующий свободный номер среди `Raw/decisions/` и
   зеркала `Decisions/` (команда `kb:record --new decision` берёт его сама).

6. ЕСЛИ ЭТО НЕ РЕШЕНИЕ. Одно неизвестное, которое нужно выяснить, — question. Поправка к ошибке
   источника — correction. Требование заказчика — requirement.
     ============================================================ -->

## Общие правила для всех карточек базы знаний

1. **Карточка — сущность, а не пересказ документа.** Про один предмет — одна карточка; знание из разных источников накапливается в ней. Перед созданием найдите карточку по имени и синониму и дополните её. Если внутри объясняется другая сущность — вынесите её в свою карточку, на месте оставьте ссылку.
2. **Только то, что есть в источнике.** Ни одного факта из общих знаний. Числа, сроки, коды, названия систем, ролей и статусов — дословно. Нет данных — раздел не пишется: пустых разделов и заглушек «нет данных» в карточке нет.
3. **Первая строка — определение.** Что это и чем отличается от соседнего — одной–двумя фразами. Дальше — существенное: условия, границы, исключения. Вёрстку источника, «см. рисунок», «в данной статье», номера разделов и повторы не переносите.
4. **Стиль.** Деловой русский, настоящее время, подлежащее — сама сущность. Без оценок, разговорных оборотов, вопросов в тексте и обращений к читателю. Термины проекта — как в источнике, без синонимов.
5. **Связи — часть мысли.** Каждое упоминание другой сущности — ссылка `[[Имя-карточки]]`; связь называется глаголом («входит в», «использует», «формирует», «ограничивает», «заменяет»), а не «см. также». Существование цели не проверяйте — пустышку заведёт движок. Ссылок на себя нет; карточка `knowledge` не ссылается на `deprecated`. Поле `related:` ведёт движок — вручную не заполняйте.
6. **Расхождения.** Источники говорят разное об одном факте — не усредняйте и не выбирайте «правдоподобное». Раздел `## Расхождения` пишет код по результату проверки: в тексте остаётся значение источника более доверенного класса, при равных классах — оба значения с указанием источников.
7. **Слово человека побеждает.** Если у карточки есть раздел `## Исправления человеком`, его текст — непреложная правда: утверждение из исправления помечается «(исправление человека)» и не выбрасывается.
8. **Встреча.** Знание из `Raw/meetings/` — только решения, факты, требования, ответы; каждое утверждение помечено «(встреча ДД.ММ.ГГГГ)», карточка несёт пометку `> 🎙 Из встречи …`. Шутки, рассуждения вслух и организационные реплики — не знание.
9. **Хвост карточки служебный.** Порядок и названия: `## Под вопросом` → `## Источник (перенесено дословно)` → `## Исправления человеком` → `## История изменений` → `## Слияние`. Свои служебные разделы не придумываются; хвост ведёт движок.
10. **Шапка.** Поля с пометкой «ставит движок» руками не меняются. Значения — только из перечисленных в шаблоне. Лишних полей нет. Даты — `ГГГГ-ММ-ДД`. Поле `template` называет файл этого шаблона.
11. **Что не живёт в карточке:** артефакты (US, AC, Epic, ревью, отчёты), задачи и планы работ, мнения и догадки, персональные данные людей, секреты и ключи, определение чужой сущности (вместо него — ссылка).
12. **Не подходит ни один шаблон — карточку не создавайте.** Ответьте `type: none` и назовите причину; придумывать тип нельзя.

## Шапка карточки

Шапка мастер-файла `Raw/decisions/DR-NNNN-….md`:

````yaml akdb-frontmatter-raw
---
title: "DR-{{NNNN}}: {{краткая формулировка решения}}"    # Совпадает с именем файла без расширения по правилам нормализации.
aliases: ["DR-{{NNNN}}"]                 # Номер записи.
tags: [decision]
type: decision                           # Не менять.
template: akdb_decision_v1.0.md          # Файл этого шаблона.
status: proposed                         # proposed | accepted | rejected | superseded. Цикл РЕШЕНИЯ, не класс доверия.
date: {{ГГГГ-ММ-ДД}}                     # Дата решения (у proposed — дата предложения).
owner: "{{@автор}}"                      # Человек, который ведёт запись. Имя модели или программы — нельзя.
supersedes: []                           # ["[[DR-0007-…]]"], если это решение заменяет прежнее.
superseded_by:                           # Заполняется ТОЛЬКО у superseded: "[[DR-0012-…]]".
applies_to: []                           # Релизы, для которых решение действует; пусто — для всех.
created: {{ГГГГ-ММ-ДД}}
updated: {{ГГГГ-ММ-ДД}}
---
````

Шапка **зеркала** в `AuroraKnowledgeDB/Decisions/` (строит движок; руками не пишется):

````markdown akdb-example
# DR-0001: Срок подтверждения заявки — три рабочих дня

## Контекст
В ТЗ срок подтверждения заявки — три рабочих дня, в описании процесса — пять. Нужно единое значение для [[Заявка на поставку]].

## Рассмотренные варианты

### 1. Три рабочих дня — выбран
- Плюсы: совпадает с ТЗ (документ заказчика).
- Минусы: поставщики просили больше времени.

### 2. Пять рабочих дней — отклонён
- Плюсы: удобнее поставщикам.
- Минусы: противоречит ТЗ.
- **Причина отказа:** ТЗ — подписанный документ; изменение требует доп. соглашения.

## Решение
Срок подтверждения — три рабочих дня. Решили аналитик и руководитель проекта.

## Следствия
- Описание процесса приводится к ТЗ.
- Затронутые карточки: [[Заявка на поставку]], [[Обработка заявки на поставку]]

## История
- 2026-09-20 — создана (@analyst)
````
