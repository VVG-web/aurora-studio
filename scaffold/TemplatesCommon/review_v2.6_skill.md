# Ревью аналитического артефакта

Обвязка. Не содержит вопросов: вопросы, веса и процедуры — в файле профиля:

| Профиль | Файл |
|---|---|
| Пользовательская история | `review_v2.6_us.md` |
| Алгоритм | `review_v2.6_alg.md` |

Загрузи ровно один файл профиля — тот, что соответствует проверяемому артефакту. Если ревью
захватывает связанные алгоритмы (§2), понадобится и второй.

---

## 0. Контракт

Ревью — классификация по закрытому списку, а не свободное суждение. Один и тот же текст обязан
получать один и тот же ответ.

1. **`no` — только с дословной цитатой.** Нет цитаты — нет `no`.
2. **Не читал — не оцениваю.** Нет страницы, раздела или доступа → `unknown`, не `no`.
3. **Отсутствие требования — не дефект формулировки.** `no` за «не написано X» ставится только
   там, где пункт прямо об этом.
4. **Конфликт правил не разрешаю «по смыслу».** Порядок: §9.5.
5. **Один дефект — один пункт, один артефакт.** Не дублируй находку в двух ревью.
6. **Считаю не на глаз.** Формулы и таблица вердикта — §7. Арифметику показываю.
7. **Не ссылаюсь на предыдущие ответы.** Каждый пункт оценивается по тексту, не по соседям.

---

## 1. Вход

- `page` — адрес или номер проверяемой страницы (обязательно);
- `profile` — `us` или `alg`. Бери из поля **«Тип требования»** в свойствах страницы; только если
  его нет — по сегменту кода (`US-` / `ALG-`);
- `include_us_links` — `context` (по умолчанию) или `skip`; см. §2.

Параметры прогона задаёт оператор: `temperature` 0,2, `top_p` 0,9, `runs` 1. Если модель
не даёт низкую температуру — не компенсируй это числом прогонов, а сообщи об этом в отчёте.

---

## 2. Шаг 1. Что ревьюим: сбор связей

Сначала собери список субъектов ревью, потом читай. Иначе контекст расползётся.

### 2.1. Как читать связи

Связь — макрос Requirement Yogi. В **storage** он выглядит так (проверено на живой странице):

```html
<ac:structured-macro ac:name="requirement">
  <ac:parameter ac:name="type">LINK</ac:parameter>
  <ac:parameter ac:name="key">ER.AB.IsActual</ac:parameter>
  <ac:parameter ac:name="freetext">Link</ac:parameter>
</ac:structured-macro>
```

Читатель видит только код — кликабельный `ER.AB.IsActual`. **В storage нет ни `href`, ни
`#req-`:** якорь `#req-<КОД>` появляется лишь в адресе отрендеренной страницы. Искать надо по
макросу и его параметру `key`.

| Что ищем | Шаблон | Что даёт |
|---|---|---|
| ссылка на требование | `ac:name="requirement"` | блок ссылки |
| код | `ac:parameter ac:name="key">([^<]+)` | код связанного артефакта |
| роль | `ac:parameter ac:name="type">(DEFINITION|LINK)` | `DEFINITION` — определение этого требования (шапка), `LINK` — ссылка на другое |
| ссылка на страницу | `ri:page ri:content-title="([^"]+)"` | страница по названию: ERD, `Core_…` |
| якорь (только в HTML) | `#req-([A-Z0-9._-]+)` | код из адреса отрендеренной страницы |
| готовый перечень | `linked_page_ids` или макрос traceability | список связанных страниц |

1. **`DEFINITION` — не связь**, это шапка самой страницы. Субъектами становятся только `LINK`.
   Иначе страница сама себе станет связанным артефактом.
2. **От кода к странице.** `key` не содержит `pageId`. Путь: список связанных страниц
   (`linked_page_ids`) плюс поиск по коду. Найденную страницу подтверди: в её шапке должен
   стоять макрос `DEFINITION` с тем же кодом. Не подтвердилось — страница не та.
3. **Два чтения.** Storage — для ссылок. Для цитат — только видимый текст: storage и markdown
   подмешивают то, чего читатель не видит (см. §3 «Что видит читатель»). В `evidence` идёт
   текст со страницы, а не из разметки.

4. **Код и страница — разное.** Требование живёт на странице, код — его имя. Одно требование
   на странице — субъект равен странице. Несколько — границы требования: от его заголовка до
   следующего требования.
5. **Дубли — по коду.** Макрос в тексте и та же ссылка в таблице предусловий — один субъект.
   Один код — один субъект, сколько бы раз он ни встретился.
6. **Код без макроса.** Код стоит обычным текстом, без `ac:name="requirement"` — это дефект
   (H-22 в истории, A-12 в алгоритме), но артефакт всё равно найди поиском по коду: нашёл —
   включай по общим правилам и поставь дефект; не нашёл — запиши в «Отсутствующие артефакты»
   как дефект, а не как ожидание.
7. **Тип — по полю «Тип требования» на самой странице** (Алгоритм / Пользовательская история).
   Если поля нет — по сегменту кода: `US` → история, `ALG` → алгоритм, `AC` → критерии.
   Неизвестный сегмент → контекст, не субъект.
8. **Если storage недоступен** и инструмент отдаёт только текст — не останавливайся: найди коды
   регулярно по тексту (п.2) и разреши каждый поиском по коду. Ссылку восстановить не удастся,
   но субъект будет найден; в `00_scope.md` в колонке «Как найдено» пиши `поиск по коду` и
   отметь это в отчёте.

### 2.2. Что делать с найденным

| Что нашли | Что делаем |
|---|---|
| Проверяемый артефакт | **субъект ревью** |
| Алгоритм (`ALG-`) | **субъект ревью** — отдельный результат (§7.4) |
| История (`US-`) | **не ревьюим**; читаем как контекст (`include_us_links=context`), при `skip` — не читаем |
| Критерии (`AC-`) | часть своего артефакта, **не** отдельный субъект |
| `ER.`, `Core_`, справочники, контракты, маппинги, роли | контекст, не ревьюим |
| `pageId` не открывается или 404 | **дефект**, а не «ждём»: §2.3 |
| Страница открылась, но пуста или содержит только шапку | субъект ревью; ответы уйдут в `unknown`, вердикт — «Не оценено» |

### 2.3. Статусы предусловий

Статус говорит о **разработке**, а не о документе. Постановка обязана быть написана к моменту
передачи истории на ревью — при любом статусе.

| Статус | Что значит для разработки | Что проверяет ревью |
|---|---|---|
| **ГОТОВО** | уже есть, менять не нужно; предусловие для старта работы | только наличие метки (H-05) |
| **СДЕЛАТЬ** | артефакт делается с нуля | постановка **написана** и заполнена |
| **ИЗМЕНИТЬ** | артефакт есть, в нём уже внесены правки под эту историю, их надо отразить в коде | правки описаны в самом артефакте |

Отсюда два следствия:

1. **«СДЕЛАТЬ» ≠ «страницы нет».** Существование проверяется только открытием `pageId`.
2. **Отсутствие страницы — дефект истории**, а не основание ждать. Фиксируется **один раз**
   пунктом H-06 (в алгоритме — A-12), с цитатой строки предусловия. Остальные вопросы по
   этому артефакту — `unknown`: проверить нечего, а второй `no` за тот же пробел нарушил бы
   «один дефект — один пункт».

Правила:

1. **Глубина ровно 1.** Ссылки со связанных алгоритмов не раскрываем: иначе контекст растёт
   лавинообразно, а стабильность падает.
2. **Циклы не разворачиваем:** артефакт, уже попавший в список, второй раз не добавляется.
3. **Лимит — 5 субъектов ревью.** Больше — остановись, покажи список со ссылками и спроси
   оператора, что включать. Молча резать нельзя.
4. **Дубли снимаются по коду**, а не по названию или адресу: одна и та же страница может быть
   вставлена макросом, стоять в предусловиях и упоминаться текстом.

Список фиксируется в `00_scope.md` до чтения текста:

```
| # | КОД | Тип | Роль | Страница | Как найдено | Статус |
|---|---|---|---|---|---|---|
| 1 | <КОД> | История | ревью | проверяемая | — | прочитана |
| 2 | DEMO-ALG-3.28 | Алгоритм | ревью | <PAGE_ID_ALG> | макрос `requirement` (LINK) | прочитана |
| 3 | <КОД> | История | контекст | <PAGE_ID_US> | `linked_page_ids` | прочитана |
| 4 | <КОД> | Алгоритм | ревью | — | макрос, `pageId` нет | **страницы нет — дефект** |
```

Колонка «Как найдено» нужна для приёмки (§7.1): каждый макрос `requirement` с типом `LINK`
обязан оказаться либо субъектом, либо строкой «Что прочитано».

## 3. Шаг 2. Факты → `02_facts.md`

Читай каждый субъект и контекст, переноси в файл. Держать источник в контексте не нужно —
дальше работа идёт по карте.

```
## АРТЕФАКТ: <КОД> (<тип>) · стр. <pageId> · v<версия> · <ревью | контекст>
### Раздел: <название>
- цитата: «<дословно, до 400 знаков>»
- факт: <роль / шаг / критерий / сущность / сумма / статус / код>
### Чего в тексте нет
- <пустой раздел / незаполненное поле> — где именно
```

Если на странице несколько требований, у каждого своя секция `## АРТЕФАКТ: <КОД>` и границы по
якорям (§2.1 п.3).

**Границы обязательны.** Каждая цитата лежит в секции своего артефакта: иначе на вопрос по
истории прилетит цитата из алгоритма, и наоборот.

**Что видит читатель.** Storage содержит конструкции, которые на странице не отображаются. Не
вырезал их — проверил текст, которого нет, и поставил ложный дефект.

| Конструкция | Видно читателю | Что делать |
|---|---|---|
| `<ac:placeholder>…</ac:placeholder>` | **нет**, только в редакторе | вырезать целиком |
| `<ac:inline-comment-marker …>текст</…>` | да, сам текст | оставить текст, снять маркер |
| `<ac:parameter>…</ac:parameter>` | нет | не цитировать |
| макрос `requirement` | да, как код из `key` | цитировать код |
| `requirement-property` | да, как подпись свойства | цитировать подпись |
| `toc`, `change-history`, `expand`, `jira` | навигация или карточка | не текст тела |

**Подсказки шаблона — не дефект.** «Указать название страницы…», «(Опционально) Вставить
ссылку…», «При правках обязательно писать комментарий…» стоят в `ac:placeholder`: это
инструкции автору, а не пометки в тексте. Дефект — только **видимая** пометка.

**Скрытый текст не привязан к типу страницы.** `ac:placeholder` встречается и в истории
(описание, предусловия, шаги сценария, критерии приёмки, таблицы), и в алгоритме, и на
AC-странице. Правило одно для всех профилей: невидимое не цитируется и не оценивается — оно
не бывает ни дефектом пометки, ни доказательством, что раздел заполнен. Плоский текст и
markdown-конвертер подсказки показывают: чистить до цитирования, а не после.

**Раздел из одной подсказки — пустой.** Если после вырезания `ac:placeholder` в разделе ничего
не осталось, для читателя раздела нет: это пустой раздел (свой пункт профиля), а не заполненный.

**Проверка видимости.** Не уверен, виден ли фрагмент, — не строй на нём дефект: возьми
отрендеренную страницу или ответь `unknown`.

**Качество извлечения.** Прежде чем оценивать, проверь, что представление сохранило структуру.
Плоское текстовое извлечение теряет нумерацию и таблицы, и на этом ломаются пункты о структуре.

| Что должно сохраниться | Признак потери | Что делать |
|---|---|---|
| нумерация шагов | шаги идут абзацами без `1.`, `1.1` | перечитать в HTML или markdown; без этого не ставить `no` по нумерации |
| вложенность | все уровни списка на одном | то же |
| таблицы | поля слиты в строку, колонки потеряны | перечитать в markdown |
| схемы и картинки | раздел выглядит пустым, хотя в нём ERD | `unknown`, не `no` |
| макросы | мусор в тексте: `LinkLINK`, `DEFINITION`, `dependancy`, `true`, GUID | вычистить перед цитированием |

**Шум макросов не цитируется.** `LinkLINKER.AB` — это `ER.AB` с обрывками макроса ссылки; в
`evidence` идёт чистый текст. Цитата с мусором не найдётся при сверке и будет снята.

**Правило одного источника структуры:** если пункт спрашивает о структуре (нумерация,
вложенность, наличие раздела), ответ берётся из структурированного представления. Ответ по
плоскому тексту — не ответ.

**Проверка полноты — до оценок:**

| Что | Требование |
|---|---|
| Критерии приёмки | число пунктов в карте = числу в источнике (с учётом макроса) |
| Шаги сценариев | каждый шаг основного и альтернативных сценариев вынесен |
| Предусловия | каждый элемент со статусом вынесен |
| Условия | каждое «если … то …» вынесено дословно |

Не сошлось — допиши карту. Пропущенный пункт в карте — самая частая причина «правильного, но
неверного» ответа.

## 4. Шаг 3. Ответы

Для каждого субъекта ревью — свой проход по пунктам его профиля.

1. Возьми пункт из файла профиля: ID, критичность, вес, «Когда», процедуру.
2. Прочитай нужный срез `02_facts.md` (секция своего артефакта).
3. Проверь применимость: условие «Когда» выполнено по факту с цитатой? Нет — `na`, конец.
4. Выполни процедуру. Она заканчивается одним из четырёх ответов.
5. Запиши JSON по §6. Обнови прогресс.

**Изоляция.** Один пункт — один проход. Не показывай себе ответы других пунктов: строгий ответ
на первом тянет к строгости все следующие, и прогон идёт волной. Если есть возможность —
отдельный вызов модели на пункт, на вход только карта и одна процедура.

**Кросс-артефактный ответ** разрешён, только если процедура пункта прямо это допускает
(например, «здесь или в связанной странице»). В таком случае в цитате обязателен код источника:

```
[<КОД> | <РАЗДЕЛ> | <пункт>] «цитата»
```

**Дедупликация между артефактами.** Пробел, относящийся к алгоритму, — дефект алгоритма. В
ревью истории соответствующий пункт закрывается `yes` со ссылкой на связанный артефакт, а не
вторым `no`. Один дефект живёт в одном отчёте.

## 5. Шаг 4. Якоря

В файле профиля — четыре крошечных кейса с эталонным ответом. Ответь на них **один раз** за
прогон, после ответов, до сборки.

Якоря не переписывают ответы. Их назначение — пометить, где прогон мог пойти не в том режиме:

| Промахов | Что делаем |
|---|---|
| 0 | ничего |
| 1 | строка в шапке: «промах по якорю K<N>» |
| 2 и более | блок «Требует ручной проверки»: перечислить пункты классов промахнувшихся якорей |

Классы «якорь → пункты» — в файле профиля.

---

## 6. Форма ответа

Один JSON на пункт, файл `20_<КОД>_<ID>.json`:

```json
{
  "artifact": "<КОД>",
  "step": "H-12",
  "v": "no",
  "applicable": true,
  "read_sections": ["Acceptance criteria"],
  "evidence": "[<КОД> | <РАЗДЕЛ> | <пункт>] «дословная цитата» — почему это плохо",
  "fix": "готовая правка: что и где дописать",
  "rule": "процедура пункта, шаг N"
}
```

- `v` — `yes | no | na | unknown`.
- `rule` — по какому шагу процедуры получен ответ. Без него ответ не принимается: по нему видно,
  где процедура не сработала.
- `evidence` — для `no` цитата обязательна; для `unknown` — чего не хватает; для `yes` — что
  подтверждает; для `na` — какое условие «Когда» не выполнено.

## 7. Шаг 5. Приёмка, расчёт, вердикт

### 7.1. Приёмка (до расчёта, не пропускать)

- [ ] каждый субъект из `00_scope.md` имеет ответы по всем пунктам своего профиля;
- [ ] каждый `LINK`-макрос и каждый код `RU.*` со страницы — либо субъект, либо строка «Что прочитано»;
- [ ] каждый артефакт из предусловий «СДЕЛАТЬ» и «ИЗМЕНИТЬ» открыт и его статус записан;
- [ ] число ответов = числу пунктов (24 или 30) × числу субъектов;
- [ ] у каждого `no` есть цитата, и она найдена поиском в `02_facts.md`;
- [ ] у каждого ответа заполнен `rule`;
- [ ] все `unknown` веса ≥ 3 перечислены;
- [ ] якоря отвечены;
- [ ] в отчёте нет кодов и адресов, которых нет в `00_scope.md`.

Не прошло — исправь, не переходи к расчёту.

### 7.2. Балл и покрытие (по каждому артефакту отдельно)

Вес: критичный 5, важный 3, мелкий 1. `na` и `unknown` в балл не входят.

```
Балл     = 10 × вес(yes) / (вес(yes) + вес(no)), вниз до десятых
Покрытие = вес(определённых) / вес(применимых), применимые = все, кроме na
```

Полоса чувствительности — по нерешённым веса ≥ 3:

```
u    = вес unknown с весом ≥ 3
низ  = 10 × yes / (yes + no + u)
верх = 10 × (yes + u) / (yes + no + u)
```

### 7.3. Вердикт артефакта

Первая подходящая строка:

| № | Условие | Вердикт |
|---|---|---|
| 1 | Страница не прочитана или покрытие < 70 % | **Не оценено** |
| 2 | Два и более критичных `no` | **Переписать** |
| 3 | Один критичный `no` | **Доработать** |
| 4 | Критичный `unknown` | **Доработать** |
| 5 | Важный `no` или `unknown` | **Доработать** |
| 6 | Пять и более мелких `no` | **Доработать** |
| 7 | Иначе | **Готова к передаче** |

Балл на вердикт не влияет.

**Пустой артефакт — не «Не оценено».** Если страница открылась, но постановки в ней нет
(H-04, H-06 или A-12 = `no`), вердикт — «Доработать»: это дефект автора, а не нехватка данных у
ревьюера. «Не оценено» — только когда прочитать не дали: нет доступа, страница не открылась,
текст обрезан или проверяющий не прочитал обязательную страницу.

### 7.4. Сводный вердикт (когда субъектов больше одного)

Отдельные вердикты **не усредняются**: среднее скрывает блокер.

| № | Условие | Сводка |
|---|---|---|
| 1 | Хотя бы один артефакт «Не оценено» | **Не оценено** + перечислить, чего не хватило |
| 2 | Хотя бы один «Переписать» | **Переписать** + перечислить, какие именно |
| 3 | Хотя бы один «Доработать» | **Доработать** |
| 4 | Иначе | **Готова к передаче** |

В шапке отчёта — строка «Передавать нельзя из-за: <КОД> (<вердикт>)».

## 9. Правила ответа

### 9.1. Четыре значения

| Ответ | Когда |
|---|---|
| `yes` | Условие пункта выполнено |
| `no` | Условие нарушено: есть явно плохой текст **и** дословная цитата |
| `na` | Условие «Когда» не выполнено |
| `unknown` | Ответить нельзя: не прочитано, не существует, правила не дают ответа |

### 9.2. Применимость

По факту, с цитатой. Условие «Когда» сформулировано так, что выполняется всегда (например,
«упомянуты роли» — актёры есть в любом документе)? Решай по содержанию: есть ли действие,
выполняемое ролью, или правило доступа. Нет — `na`.

### 9.3. Проверка перед `no`

Прежде чем написать «не описано X», проверь связанные страницы: найдено там — `yes`. Не
прочитана — `unknown`.

### 9.4. Неполное чтение и отсутствующие артефакты

1. **Постановка должна существовать.** На момент передачи все артефакты из предусловий
   «СДЕЛАТЬ» и «ИЗМЕНИТЬ» написаны. Отсутствие страницы — дефект, он фиксируется один раз
   пунктом H-06 (в алгоритме — A-12) с цитатой строки предусловия (§2.3).
2. Остальные вопросы по отсутствующему артефакту — `unknown`. Один пробел — один дефект.
3. **`no` за «не описано X»** — только если поведения нет ни здесь, ни в прочитанных связанных,
   и ни одна страница не названа местом описания.
4. Текст обрезан, раздел не виден, нет прав доступа → `unknown`. Никогда `no` на основании
   того, что не видно.
5. Внешняя система или чужой артефакт, которого у нас нет и быть не должно → `na` или
   `unknown`, но не дефект.

### 9.5. Приоритет правил при конфликте

1. §9.4 — выше всего;
2. «Что оценивается» в файле профиля — выше процедуры;
3. якорь профиля — выше процедуры (расхождение записать в `60_defects.md`);
4. процедура пункта — выше общего смысла;
5. ничего не подошло — `unknown` и запись в `60_defects.md`.

### 9.6. Прочее

- Сомнение — `unknown` и оба прочтения. Для «неоднозначности» `no` засчитывается только с двумя
  конкретными прочтениями.
- Неуклюжая, но однозначная формулировка — `yes`. Стиль не оцениваем.
- `fix` — готовая правка: что и где дописать. Не «уточнить».
- Маршрутизация дефекта между пунктами — в файле профиля.
