# Регрессионный тест-раннер движка Function

## Description

`tests/run_tests.py` — главная регрессионная серия движка Aurora. Она проверяет, что
скрипты движка (`scripts/*.py`) делают то, для чего задуманы, прогоняя их на одноразовых
синтетических проектах, собранных во временных каталогах. Живые проекты не используются
никогда.

Серия существует потому, что движок пишет разом в сотни файлов живой базы: дефект вида
«два файла переименовались в одно имя, карточка молча затёрта» находили только ручной
сверкой счётчиков. Такие вещи должен ловить прогон, а не человек.

Запуск из корня кита:

```
python3 tests/run_tests.py            # прогнать всё
python3 tests/run_tests.py -v         # печатать каждую команду и её rc
python3 tests/run_tests.py --only=repair   # только проверки, у которых в имени есть "repair"
```

`--smoke` прогоняет короткий набор инвариантных проверок (быстрый вариант для частых
запусков), `--no-invariants` — полный прогон без них. Код выхода: `0`, если все проверки
прошли, `1`, если есть падения; сводка печатает `Пройдено: X/Y` и блок по каждому падению.
В текущей версии (1.100.3) зарегистрировано 240 проверок — серия является основным
шлюзом для релиза кита.

## Key Features

- **`run(script, *args, cwd, expect_rc)`** — запускает скрипт движка из `scripts/`
  как subprocess в указанном каталоге проекта, снимает stdout/stderr и сверяет ожидаемый
  код возврата (`expect_rc`). С флагом `-v` печатает командную строку, rc и первые 12
  строк stdout.
- **`make_project(tmp, git=False)`** — разворачивает пустой проект во временном каталоге:
  стандартная структура из `structure_dirs.txt`, скрипты движка из кита скопированы в
  `.opencode/scripts/`, манифесты и папки зеркал источников из `connectors/*/connector.json`
  (манифесты кладутся как `.opencode/connectors/<id>.json`), заглушка скилла
  `aurora-vault` и минимальный `aurora.config.yaml`. С `git=True` дополнительно делает
  `git init` и коммит, чтобы тесты с git-стражами работали на живом репозитории.
- **`card(root, rel, body, **fm)`** — пишет карточку под `AuroraKnowledgeDB/` с YAML-шапкой.
  Поле `type` подставляется из раздела автоматически (карта `SECTION_TYPE` — тот же список
  раздел→тип, что в `kb_lint.py`): карточка без `type:` — это намеренная цель для линтера,
  а не «обычная карточка».
- **декоратор `@test`** — регистрирует проверку под именем функции (подчёркивания →
  пробелы), каждая проверка исполняется в собственном `TemporaryDirectory`, результат
  попадает в `RESULTS`. Провал без пояснения всё равно провал: `why(e)` возвращает
  «(без пояснения — добавьте текст в assert)», поэтому голое `assert` не может быть
  незаметно засчитано зелёным.
- **`--only=` / `--only <имя>`** — одна проверка по подстроке имени (без учёта
  регистра): правка одной вещи не стоит полного прогона на несколько минут. Инвариантные
  source-scan проверки при этом гоняются всегда — регрессия в тексте самого движка
  ловится только ими.
- **Изоляция окружения** — при импорте серия выставляет `AURORA_TESTS_ISOLATED=1` и
  вычищает все переменные `AURORA_AGENT_BACKEND_*`: личный конфиг бэкендов разработчика
  (`.env.aurora.local`) не может изменить то, что видят тесты. Проверке, которой нужно
  кольцо из нескольких бэкендов, оно объявляет само через переменные окружения.

## Test Categories

Проверки сгруппированы не по скриптам, а по тому, что они защищают:

- **Ремонт и дедупликация** (`kb_fix.py`): чинит ссылки и гомоглифы, никогда не затирает
  при коллизии имён, идемпотентен, при слиянии двойников архивирует донора, выбрасывает
  выведенные из схемы поля, сходится к устойчивому состоянию, а не повторяет одни и те же
  находки.
- **Линтер** (`kb_lint.py`): валидирует вопросные карточки, находит артефакты
  (US/AC/Jira-ключи), осевшие в базе знаний, но не трогает легитимные коды предметной
  области; проверяет реестр релизов.
- **Синхронизация и зеркала** (`sync_audit.py`, `kb_remap.py`): дрейф против хэша
  источника, NFD/NFC-нормализация путей на macOS, перенаправление `source:` после
  переезда зеркала, подсчёт orphan/missing.
- **План разбора** (`build_plan.py`): пакетирование по бюджету, возобновление по
  манифесту, нарезка источника по заголовкам, сборка карточки из именованных секций и
  отказ отметить источник разобранным, если карточек из него не появилось.
- **Обратный поток статусов** (`jira_status.py`): сообщает человеку *кандидатов* на
  закрытые issues, а не переключает `req_status` сам; читает и легаси-формат, и
  frontmatter-зеркало.
- **Контекстные паки** (`ctx_pack.py`, `spec_pack.py`): фильтрация по статусу доверия,
  учёт использования, пачка с источниками и рисками.
- **Релиз и отгрузка** (`ship_doc.py`): датированный снимок замораживается один раз,
  перезапись блокируется.
- **Детерминизм конвертеров** (`confluence_export.to_markdown`,
  `jira_export.jira_to_md`): стабильны от прогона к прогону, вычищают макросы и
  атрибуты, никогда не вшивают дату экспорта — иначе каждый прогон давал бы ложный дифф.
- **Панель и UI** (модуль `cockpit/aurora_cockpit.py`, `cockpit/ui/index.html`):
  сценарии и скины, валидация реестра и флагов, состояние токенов, корни проектов и то,
  что панель предлагает только те эндпоинты, которые есть у сервера.
- **Гигиена mermaid**: в подписях переходов `stateDiagram-v2` не бывает «голого»
  двоеточия — парсер GitHub (mermaid 10) его роняет, поэтому в диаграммах команда
  пишется как `kb#58;build`.
- **Сторож выдачи** (`test_retrieval_is_watched_not_guessed`): вес слов по редкости в
  `ctx_pack`, корпорный сторож ранжирования (`dev_qa.py --retrieval` против
  `tests/corpus/RETRIEVAL.json`) и отчёт по живым запросам — см. [Золотой корпус](./02-golden-corpus.md).

## QA-контур

Раннер — первый из трёх уровней проверки, на которых живёт разработка движка (регламент —
в скилле `aurora-dev`, механика — в `scripts/dev_qa.py`):

1. **Автотесты** — `tests/run_tests.py`: всё, что воспроизводится за секунды и должно
   падать при каждом коммите. Если поведение можно закрыть автотестом, кейс на то же
   самое не заводится.
2. **Тест-кейсы** — `Development/QA/cases/TC-NNN-….md`: то, что автотестом дорого или
   невозможно — живой Confluence и Jira, панель в браузере, база в тысячу карточек,
   читаемость вывода.
3. **Сценарии** — `Development/QA/scenarios/TS-NNN-….md`: маршрут из нескольких команд,
   где выход одной должен быть входом следующей.

Журналы прогонов лежат в `Development/QA/runs/YYYY-MM-DD_TS-NNN.md`. Поле `automated:`
в кейсе связывает уровни: как только появился автотест, кейс помечается его именем и
руками больше не выполняется; кейс вне сценария и без автотеста не гоняется никогда.
Прогон любого сценария начинается с автотестов — TS-001 обязателен после любой правки
движка. Папка `Development/` живёт в отдельной ветке `development` (git worktree на то
же место) и в публичный репозиторий не уходит: кит и кухня коммитятся раздельно.

## Implementation Notes

- Раннер импортирует модули движка напрямую (`sys.path.insert(0, str(SCRIPTS))`, затем
  `import confluence_export as ce`, `import jira_export as je`, `import ctx_pack as P`),
  чтобы тестировать чистые функции конвертации in-process; всё, что трогает каталог
  проекта, запускается как subprocess.
- `make_project` копирует реальный движок из кита, поэтому серия прогоняет ровно тот
  код, что уходит в проекты, — но каждый раз в изолированном временном проекте.
- `RESULTS` — плоский список кортежей `(имя, ошибка|None)`; `main()` печатает
  `Пройдено: X/Y` и блок по каждому падению, возвращает 1, если хоть одна запись не
  `None`.
- Состав прогона решается до его начала: регистрация (`@test`) отделена от исполнения —
  импорт-драйвер исполняет отобранные проверки после сборки списка, так что
  `--only`/`--smoke`/`--no-invariants` выбирают состав до запуска, а не фильтруют
  посреди него.
