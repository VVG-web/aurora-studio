# Built-In Agent Function

## Description

Встроенный LLM-агент Aurora Studio: аналитик выполняет рутинные LLM-шаги, не выходя из
Авроры, — агент доводит задачу до конца, а достижение цели проверяет движок. Модуль живёт
в ките и развёртывается в проект вместе с движком: `scripts/agent_core.py` и
`scripts/agent_runner.py` в проекте лежат в `.opencode/scripts/` (скрипт сам определяет,
где он — в ките или в копии движка проекта, проектом считается текущая папка с
`aurora.config.yaml`). Собрка — два слоя на жёсткой границе зависимостей: `agent_core.py`
(фаза 1 — разобрать настройку и дойти до живой модели по кольцу бэкендов, «честно сказать,
что работает») и `agent_runner.py` (фаза 2 — агентский цикл: задачи, роли, оракул, журнал).
Вызов модели изолирован в подпроцессе `scripts/agents/pydantic_ai_adapter.py`, который
работает в собственном venv `~/.aurora/venv`: ядро кита обязано работать только на stdlib,
агентский фреймворк в него протекать не имеет права.

Запуск — из корня проекта: `python3 .opencode/scripts/agent_core.py --ping` (диагностика) и
`python3 .opencode/scripts/agent_runner.py --task <task>` (задачи); то же самое — кнопки
панели (`agent:ping`, `agent:width`, `agent:aliases`, `agent:build`, `agent:ask`,
`agent:distill`, `agent:make`), настройки — «Настройка» → «Агент».

Ключевой контракт агента: **агент не выдаёт догадку за факт**. Воркер предлагает, критик и
верификатор «Момус» проверяют, оракул — команда движка, пересчитывающая факт. Самооценка
модели никогда не является путём приёмки, а в базу агент пишет только через белые списки
команд движка (dry-run, git-guard, журнал); прямая правка файлов моделью запрещена
конструкцией — LLM умеет только перегенерировать файл целиком и вместе с одной строкой
переписывает шапку, теги и тело.

## Key Features

- **Конфигурация** — только `.env`-файлы, один механизм: глобальный файл кита
  `.env.aurora.local` и переопределение любой переменной проектом в своём
  `.env.aurora.local`. Приоритет: переменные окружения > проект > кит; ключи и адреса в git
  не попадают. Панель пишет только `AURORA_AGENT_*` / `AURORA_EMBED_*` переменные.
  - Бэкенды — список `AURORA_AGENT_BACKEND_<n>_URL/KEY/MODEL`; у каждого бэкенда модели на
    роли (`MODEL_WORKER`, `MODEL_PLANNER`, `MODEL_CRITIC`, `MODEL_QA`, нет ролевой —
    общая), объявленное человеком **контекстное окно** `CONTEXT`, своя ширина `WIDTH` и
    флаги `PARALLEL`/`FALLBACK`. Первый бэкенд всегда параллельный и всегда первый в
    кольце — ему галочки не нужны.
  - Управление прогоном: `AURORA_AGENT_PARALLEL` (потолок; `авто` — сумма объявленных
    ширин), `AURORA_AGENT_MAX_STEPS` (15), `AURORA_AGENT_BUDGET_MIN` (20 мин),
    `AURORA_AGENT_REQUEST_TIMEOUT` (300 с), `AURORA_AGENT_ADAPTER` (по умолчанию
    `pydantic_ai`), `AURORA_AGENT_ADAPTER_PROCS` (потолок пула процессов адаптера, 32).
  - Рассуждения — глобальные `AURORA_AGENT_THINKING` и по ролям
    `AURORA_AGENT_THINKING_<ROLE>` (в панели — чекбоксы). Замер на живом шлюзе: пересказ
    трёх карточек в тезисы с рассуждениями — 66 секунд, без них — 5,7; тезис не хуже,
    местами точнее. Пересказ — это извлечение, а судят критик и Момус — им рассуждения
    нужны.
  - Эмбеддинги живут своей жизнью: `AURORA_EMBED_URL/KEY/MODEL` (модель по умолчанию
    `bge-m3`) — часто отдельный сервис с другим адресом и ключом; без эмбеддингов поиск
    идёт по словам, и это рабочее состояние, а не поломка.
  - CLI: `--show` (собранная конфигурация, ключи маской), `--ping`, `--probe-width`,
    `--heavy`, `--venv-status`, `--venv-install`, `--json` (машинный вывод для панели).
- **Кольцо бэкендов, не лестница** — каждый вызов обходит список с верха, поэтому
  восстановившийся основной шлюз подхватывается на следующем же запросе. К следующему
  бэкенду ведут: нет соединения за 3 с (`CONNECT_TIMEOUT`), `/slots` показывает занятый
  слот (llama.cpp молча ставит в очередь и не отдаёт ошибку), пустой или невалидный ответ.
  Полный неудачный круг — пауза 10 с (`RING_PAUSE`) — новый круг, до дедлайна.
  - Провайдер, который не ответил, помечается мёртвым на 15 минут — чтобы не долбить
    мёртвый шлюз каждым источником; кнопка панели «Вернуться на основного» (флаг-файл
    `~/.aurora/retry-primary`) снимает отметку сразу. Отказ из-за длины запроса
    (переполнение окна) мёртвым не помечает: дальше по кольцу может стоять модель с более
    широким окном, и она этот же запрос возьмёт.
  - **Контекстное окно** — объявляется человеком на каждый шлюз: одна и та же модель у
    разных провайдеров порезана по-разному, и API это не скажет. `fits()` не отправляет
    заведомо непроходящий запрос — иначе шлюз ответит 400, движок сочтёт бэкенд мёртвым и
    уйдёт к следующему с тем же запросом, и одна большая карточка «положит» всех
    провайдеров. `prompt_budget()` отдаёт движку, сколько влезает в самое широкое объявленное
    окно кольца; окон не объявлено — ноль, то есть «движок не знает», и он не выдумывает
    предел, а говорит об этом словами.
  - Параллельность: слоты прогона раздаются по объявленной ширине каждого шлюза
    (`pool()`), вызов начинается со своего бэкенда и продолжается только теми, кто
    объявлен запасным; бэкенд, взятый в пул ради пропускной способности, не обязан
    подменять упавшего.
- **Адаптер** (`scripts/agents/pydantic_ai_adapter.py`) — вызов модели через Pydantic AI
  внутри `~/.aurora/venv`, а не в питоне движка.
  - Построчный протокол: одно задание — одна строка JSON на stdin, один ответ — одна
    строка на stdout; процесс живёт весь прогон, потому что запуск venv-питона с импортом
    фреймворка стоит 6–8 секунд и платить их за каждый шаг агента нельзя. Задание:
    `{"url","key","model","messages","history","tools","mcp","guard","role","tool_calls",
    "thinking","timeout"}`, ответ: `{"ok","text","reasoning"}` либо `{"ok": false,"error"}`.
  - Pydantic AI валидирует ответ и умеет заставить модель переписать невалидный: в фазе 2
    агент возвращает не текст, а решение в JSON, по которому движок правит базу. Одиночный
    вызов без инструментов и истории идёт обычным HTTP; venv сломан — движок откатывается
    на stdlib-транспорт и работа не встаёт, причина фолбэка уходит в отчёт прогона.
  - Адаптер держит **пул процессов**, а не один: труба у процесса одна, и один процесс
    означал очередь длиной в прогон (замер: чистый HTTP при восьми потоках — 2,40 ответа в
    секунду, тот же шлюз через один процесс — 0,47). Потолок —
    `AURORA_AGENT_ADAPTER_PROCS` (32), процесс стоит ~114 МБ, с восьмого движок говорит про
    память вслух.
  - Инструменты модели — все на чтение и все внутри проекта: `read_file`, `list_dir`,
    `kb_search`, `kb_context`, `artifact_spec`. Корень проекта модель не выбирает — он
    приходит в задании; файлы с доступами (`.env*`, `id_rsa`, …) и служебные папки (`.git`,
    `.ssh`, …) ей не читаемы. Потолок на вызовы инструментов — `AURORA_AGENT_TOOL_CALLS`
    (8).
  - **Сторож на исходящее**: MCP-серверы проекта (`mcp.json`, стандартная форма
    `mcpServers`) с `outbound: true` пропускают запросы через проверку — совпало четыре
    слова подряд из задачи аналитика, пака знаний или названий карточек, или запрос
    длиннее 15 слов — наружу он не уходит, и отказ объясняется модели словами, чтобы та не
    истолковала пустоту как «в интернете ничего нет». Сторож **закрыт по умолчанию**:
    пустой guard — это «движок его не собрал», неизвестность, а не разрешение. Журнал
    последних ста запросов (ушедших и заблокированных) — `Workspaces/_outbound.md`.
- **Агентский цикл** (`scripts/agent_runner.py`) — фаза 2: агент доводит задачу до конца
  сам, а цель проверяет не он, а команда движка.
  - **Роли**: `worker` предлагает решение по одному конфликту; `critic` (флаг `--critic`)
    проверяет предложение до записи — в проде обязателен, потому что глитч в базе бьёт по
    всей последующей разработке; `planner` выбирает границы там, где их не оставил автор
    (источник без заголовков, карточка, переросшая окно) — видит **опись** абзацев
    (номер, размер, первые слова), а не текст, поэтому работает и с телом, которое в окно
    не влезает; верификатор **«Момус»** (роль `qa`) — вторая модель, читающая ответ по
    утверждениям: у каждого либо опора с цитатой из контекста, либо «нет опоры», либо
    «противоречие». Момус — мнение, а не оракул: он не переписывает ответ и не голосует за
    него, решение остаётся человеку, а утверждение «без опоры» в артефакт не переносится,
    даже если выглядит разумно.
  - **Оракул** — команда движка проверяет факт, а не мнение: для синонимов `kb_lint.py`
    пересчитывает конфликты, для сборки — счётчик плана и ошибки линтера. Успех — «движок
    посчитал, что сделано», а не «агент отчитался».
  - **Запись — только через белый список** команд движка (список живёт в `agent_core`):
    `build_plan.py --card/--done/--empty`, `kb_fix.py --stubs/--set-alias`,
    `kb_graph.py --cards` — у всех dry-run, git-guard и журнал. Запрещено навсегда, при
    любых флагах: `kb_trust.py`, `kb_reset.py`, `ship_doc.py`, `publish_doc.py`, `git` —
    доверие, снос и поставка — решения человека, это конструкция, а не настройка.
  - **Git-чекпойнт**: перед прогоном отдельным коммитом фиксируется текущая работа
    человека; работа агента ложится поверх отдельным коммитом (ровно `AuroraKnowledgeDB/`)
    — всё откатывается одной строкой. Без этого правки агента смешались бы с
    незакоммиченной работой.
  - **Журналы**: прогон — `AuroraKnowledgeDB/meta/agent-runs/<YYYY-MM-DD_HHMM>_<task>.md`,
    разговоры с базой — `AuroraKnowledgeDB/meta/ask/` (уходят в git вместе с карточками).
  - **Честные стопы**: одна и та же ошибка три раза подряд — стоп (это контур, а не
    содержание); три сбоя подряд в `distill` — остановка и указка на `agent:ping`; обрыв
    связи (VPN) ночной прогон не роняет — ждёт 5 минут и продолжает с того же места, до 24
    попыток.
  - Общие флаги задач: `--apply` (без него — предпросмотр, в базу ничего не записано),
    `--limit N`, `--partition N`, `--until-done` (весь план, партия за партией, потолок
    времени `--hours`, по умолчанию 12), `--no-checkpoint`, `--no-momus`.

## Implementation Notes

- Фаза 1 (`agent_core`) — «честно сказать, что работает», фаза 2 (`agent_runner`) —
  «довести задачу до конца»: общий транспорт, общее кольцо и общая конфигурация, разные
  обязанности.
- Контракт «не выдавать догадку за факт» держат скрипты, а не дисциплина модели: число в
  пересказе, которого нет в источнике, — «нет опоры» для Момуса; утверждение в ответе без
  `[[ссылки]]` считается выдуманным; вердикт «знания нет», вынесенный по тексту, обрезанному
  под окно, не принимается — вердикт по части не есть вердикт.
- Ссылки ответа `ask` движок сортирует механически в три корзины: «карточка в базе есть,
  в пак не попала» (промах отбора — спросите точнее), «идентификатор из таблицы внутри
  карточки» (знание не выделено — заготовить), «ни в паке, ни в базе» (перечислено по
  памяти). Три разных случая лечатся по-разному, а не общим «проверяйте внимательнее».
- Сторож исходящего нормализует слова той же нормализацией, что поиск по базе
  (`ctx_pack`): регистр, ё/е, окончания, стоп-слова. Пересказ другими словами всё равно
  пройдёт — сторож поднимает цену утечки, а не стена; единственная полная гарантия — не
  подключать `outbound`-серверы вовсе.
- Белый и чёрный списки — данные (словари в `agent_core`), а не код: их читают раннер
  фазы 2, тесты и человек.
