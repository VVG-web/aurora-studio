# Analyst Metric Computation Function
## Description
Превращает сырые выгрузки в по-годовые JSON-метрики, которые рендерит дашборд. Оркестратор
(`scripts/report_analyst.py`, панель — `ops:report`) прогоняет эти скрипты **по разу на каждый
отчётный год**, подставляя год через окружение `AURORA_REPORT_YEAR` (читает его `paths.year()`),
а каждый шаг пишет в свою годовую папку `paths.out(<name>)` — по умолчанию
`.opencode/cache/reports/analyst/by-year/<year>/`. Четыре скрипта в фиксированном порядке,
каждый опирается на выход предыдущего:

| Скрипт | Роль |
|---|---|
| `process_confluence.py` | Confluence-сырьё → `confluence_activity.json` |
| `make_analyst_metrics.py` | `full_status.json` + `issues.json` + ростер → `analyst_metrics.json` |
| `update_analyst_metrics.py` | дописывает события BA-SA Task в `analyst_metrics.json` |
| `verify_weekly_by_person.py` | пересобирает и сверяет недельные суммы по людям |

## Key Features
- **Недельная активность Confluence.** `process_confluence.py` парсит даты создания и
  последней правки каждой страницы (время из строки `2024-11-26T16:11:12…` берётся без
  таймзоны — местная дата, как она записана), дедуплицирует страницы по `page_id`,
  присваивает автору роль из ростера и собирает набор активных ISO-недель отчётного года
  — по датам создания **или** правки. Выход: `{weeks, pages, role_of}`; в терминал —
  статистика: уникальные страницы, созданные в году, топ-5 недель, авторы вне ростера,
  распределение по ролям.
- **Недельные бакеты «Аналитика - готово».** Событие «аналитик закончил» — переход **в**
  статус `Аналитика - готово`, бакет по ISO-неделе перехода: тип «История» → `stories`,
  всё, кроме «История» и «BA-SA Task» → `others`. `BA-SA Task` здесь намеренно
  пропускается: ей ведёт отдельный счёт следующий шаг, и без исключения одна задача
  попадала бы и в `others`, и в `ba_sa` — итог завышался бы, а сверка по людям
  перестала бы сходиться.
- **Длительности переходов между этапами.** `make_analyst_metrics.py` сводит сырые статусы
  в семь этапов через карты `STAGE_OF`/`STAGE_OF_R`: `Запланировано` ← «Сделать»,
  `Анализ` ← «Аналитика», `Анализ Готово` ← «Аналитика - готово», `Разработка`,
  `Разработка готово` ← «Разработка - готово»/«Разработка готова», `Тестирование`,
  `Тестирование готово` ← «Тестирование - готово»/«Тестирование готово». Только для
  «История» фиксируется **первое** вхождение в каждый этап и для каждой следующей пары —
  дни между ними (`days`, с точностью до 0.1), ISO-неделя входа во второй этап,
  исполнитель на этот момент (через общий `AssigneeResolver`) и его роль. Пары, где этапы
  пройдены не по порядку (`seen[a] > seen[b]`) или этап пропущен, отбрасываются.
  Сложение — массив `transitions_raw`.
- **События BA-SA Task.** `update_analyst_metrics.py` добавляет отдельный недельный счётчик
  `ba_sa`: событие — **первый** переход в `Закрыто` (у этого типа workflow без
  «Аналитика - готово»), отфильтрованный по ISO-году отчёта. Фильтр по году добавлен
  позже: без него закрытия за 2021-й ложились в недели 2024-го, и счёт вырастал в разы
  (на TAXKG — 185 вместо 19). Assignee берётся из `assignee_now`. Эти события **не**
  попадают в `transitions_raw`; в `types_available` «BA-SA Task» вставляется сразу после
  «История», новые исполнители добавляются в `persons_available` и `role_of`, а всем
  неделям без `ba_sa` проставляется `ba_sa: 0`.
- **Сверка по людям.** `verify_weekly_by_person.py` пересобирает `weekly_by_person`
  (`{person: {week: {stories, others, ba_sa}}}`) с нуля по тем же правилам (пустой
  исполнитель именуется «Не назначен»), суммирует его и дописывает в
  `analyst_metrics.json` только при полном совпадении сумм с авторитетными
  `weekly` — иначе печатает расхождения по каждому бакету и выходит с кодом 1,
  останавливая цепочку.
- **Роли из ростера.** Роли исполнителей — `paths.roster()` (ФИО → Роль); `role_of`
  результата заполняется из него, недостающие роли дашборд дособерёт из ростера сам.
- **Встроенные контрольные числа.** Каждый шаг печатает недельные итоги, статистику
  длительностей по переходам (N, среднее, персентиль — без `numpy`: срезы по отсортированному
  списку) и распределение BA-SA по неделям и исполнителям, чтобы прогон можно было
  проконтролировать в терминале.

## Implementation Notes
`make_analyst_metrics.py` и `verify_weekly_by_person.py` собирают по одному `AssigneeResolver`
до начала циклов (`_resolver`), подгружая свежие назначения из зеркала `sync:jira`
(`load_synced_assignees(paths.sources_jira(), "<project_key>-")`); раньше резолвер создавался
на каждый вызов и перечитывал всю папку `Sources/JIRA` на каждый переход. Неделя —
строка «WW» с нулевым дополнением (`f"{w:02d}"`), ISO-календаря; и неделя, и год берутся от момента
события. Счёт по BA-SA использует `assignee_now`, а сверка — резолвер: различие затрагивает
только атрибуцию, но не суммы. Цепочка счёта (и серверная пересборка) —
`process_confluence.py`, `make_analyst_metrics.py`, `update_analyst_metrics.py`,
`verify_weekly_by_person.py` — на каждый год; затем `make_extended.py` один раз,
собирая все годы в один HTML.
