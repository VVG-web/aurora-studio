# Aurora Studio — концепция наборов команд и дорожная карта

Документ фиксирует, из чего состоит рабочий цикл аналитика в Авроре, как команды
сгруппированы и что добавляется в каких версиях. Пишется от эксплуатации: каждый пункт
опирается на факт из живого проекта, а не на пожелание.

## 1. Что показала эксплуатация (базовая точка, июль 2026)

Два живых проекта на движке 1.2.0:

| Симптом | крупный проект | небольшой проект |
|---|---|---|
| карточек в базе | 1971 | 65 |
| `verified` | 7 (0.35 %) | 38 |
| карточек без `status` (легаси) | 1114 | 0 |
| ошибок `kb_lint` | 1046 (482 битые ссылки) | 54 |
| двойники-гомоглифы (`АИС`/`AИС`, `ВАЛЮТА`/`ВAЛЮТA`) | десятки пар | — |
| артефакты, попавшие в знания (US/Epic в `Concepts/`) | 130 | — |
| целостность зеркала Confluence | ручной отчёт: missing 216, orphan 526, collision 3 | — |
| ad-hoc python-скриптов в корне | 8 | 6 |
| `build` пришлось резать руками | на фазы P1–P5 | — |

Три вывода, которые определяют дизайн:

1. **Механику делает скрипт, суждение — LLM.** Сейчас массовый обход тысяч файлов
   (`build`, `garden`, `status`) выполняет модель — отсюда стоимость, ручная нарезка на
   фазы и накопившиеся 1046 ошибок. Правило движка: у каждой массовой операции есть
   детерминированный скрипт; агент получает его отчёт и принимает решения.
2. **Круг не замкнут.** Внутрь (`sync → build → карточки`) проработано; наружу
   (`Artifacts → Confluence/Jira`, `Deliverables → docx`) и обратная связь (комментарии
   заказчика, дрейф после публикации) — инструментов нет. Заявленная позиция «git —
   истина, Confluence — витрина» без `ship:` не выполняется.
3. **Верификация не масштабируется по папкам.** Bootstrap задумывался временным (до 20 %),
   а стал постоянным. Верифицировать 1971 карточку никто не будет — верифицировать надо
   то, что реально попадает в контекст: очередь по употреблению, а не по алфавиту.

## 2. Решение о структуре (фиксировано, не обсуждается в проектах)

**Структура папок одинакова во всех проектах Авроры.** Верхний уровень (`Sources/`,
`Raw/`, `AuroraKnowledgeDB/`, `Artifacts/`, `Deliverables/`, `Workspaces/`, `Templates/`,
`Prompts/`) и структурный второй уровень (разделы базы знаний, типы артефактов, слои
Raw) задаются kit'ом в [`structure_dirs.txt`](../structure_dirs.txt) и обновляются только
релизом движка.

- Проект **не придумывает** свои типы артефактов. `create <тип>` с неизвестным типом не
  создаёт папку — команда отказывает и предлагает подходящий стандартный тип.
- Всё, что не укладывается в таксономию (черновики, подборки, эксперименты,
  вспомогательные файлы, картинки), живёт в `Workspaces/<задача>/` — там свобода полная.
- Нужен новый тип артефакта всерьёз → это изменение kit'а: PR в `structure_dirs.txt` +
  таблицы в `SKILL.md`/`conventions.md` + запись в CHANGELOG. Так тип появляется сразу во
  всех проектах, а не только у автора.
- `structure_dirs.txt` — единственный источник правды о структуре: `install` и `update`
  читают его, `doctor` сверяет с ним факт и рапортует о самодеятельных папках.

Причина: одинаковая структура — это контракт между проектами. Она даёт переносимость
навыка аналитика, переиспользование промптов и шаблонов, работающие скрипты движка и
осмысленный `update`. Расползание таксономии убивает всё перечисленное.

## 3. Семь наборов команд

Плоский список из 25 команд уже нечитаем, а к 2.0 их будет ~45. Вводятся неймспейсы —
семь наборов, у каждого свой владелец ритуала. Старые имена остаются алиасами навсегда.

| Набор | Смысл | Кто и когда |
|---|---|---|
| `kit:` | жизненный цикл движка: развернуть, настроить, обновить, мигрировать схему, принять чужой проект, вернуть наработки в kit | лид, редко |
| `sync:` | машинные зеркала: Confluence, Jira, целостность зеркал | дежурный, после синка |
| `kb:` | извлечение и жизнь знания: ingest, build, verify, dedupe, repair, supersede, index | все, ежедневно |
| `ctx:` | использование знаний: context, ask, explain, impact, gap, eval, retro | все, ежедневно |
| `make:` | производство артефактов: create, review, spec, spec-pack, validate, template | аналитик |
| `ship:` | наружу и обратно: publish, export, jira-push, release, respond | аналитик, по вехам |
| `ops:` | управление и отчётность: status, stats, trace, owners, audit, report, onboard | лид, еженедельно |

## 4. Дорожная карта

### 1.3.0 — P0: ремонт, верификация, целостность (реализовано)

Без этого движок не выдерживает объёма реального проекта.

| Команда | Скрипт | Закрывает |
|---|---|---|
| `kb:repair` | `kb_fix.py` | 482 битые ссылки, гомоглифы, легаси-frontmatter — вместо самописных `fix_links*.py` |
| `kb:dedupe` | `kb_fix.py --dupes` | пары-двойники, разошедшиеся по регистру/гомоглифам |
| `kb:queue` | `kb_queue.py` | 7 verified из 1971: очередь по употреблению × входящим ссылкам × протуханию |
| `sync:audit` | `sync_audit.py` | missing/orphan/collision в зеркалах — вместо ручного отчёта |
| `ops:stats` | `aurora_stats.py` | дашборд и месячные метрики без обхода базы моделью |
| `kit:hooks` | `aurora_hooks.py` | pre-commit с `kb_lint` — ошибки больше не копятся молча |
| `kit:structure` | `aurora_doctor.py --structure` | самодеятельные папки, нарушения фиксированной структуры |

Плюс: неймспейсы команд, `structure_dirs.txt` едет в проект, `install` перестаёт дублировать
список папок, лог употребления карточек (`meta/usage.log`) как топливо для очереди.

### 1.4.0 — Вопросы и приёмка: два недостающих объекта цикла (реализовано)

Расширение фиксированной схемы (раздел 2) — новый раздел базы и новый тип артефакта,
приезжают во все проекты одним `update`:

- `AuroraKnowledgeDB/Questions/` — вопрос к заказчику как объект (Q-NNN): кому задан,
  что блокирует, к какому сроку, где зафиксирован ответ. Команды `kb:question`,
  `kb:answer`, `ops:questions`. Открытые вопросы механически держат DoR спеки —
  раздел «Открытые вопросы» перестал быть текстом, который никто не проверяет.
- `Artifacts/acceptance/` — результаты приёмки и испытаний (`ship:acceptance`): вердикт по
  каждому пункту ПМИ, разбор замечаний заказчика на четыре типа (дефект / новое требование /
  вопрос / разночтение). `req_status: implemented` теперь имеет доказательство.
- Механика, а не только папки: `kb_lint` проверяет карточки вопросов, `aurora_stats`
  показывает открытые/просроченные и что они блокируют, `aurora_trace` получил колонки
  «Приёмка» и «Вопросы» и два новых разрыва — требование, заблокированное вопросом, и
  `implemented` без отчёта приёмки.

Закрывает разрывы «реестр вопросов» и «приёмка» из раздела 5.

## 6. Инварианты, которые дорожная карта не имеет права нарушить

1. Артефакт ≠ знание.
2. Ничего не удаляется (`supersede`, `_archive/`).
3. Синк не перезаписывает проверенное; расхождение = DRIFT.
4. Каждая карточка входит в промпт с шапкой доверия.
5. Поставленное (`Deliverables/released/`, доказательный `Raw/`) неизменяемо.
6. Схемы — как код (mermaid в карточке).
7. **Структура папок фиксирована kit'ом** (раздел 2).
8. Массовая механика — скрипт, а не модель (раздел 1).
