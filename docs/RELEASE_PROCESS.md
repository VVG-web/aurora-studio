# Быстрый цикл выпуска

Документ фиксирует процесс, который вырос из выпуска 1.231.19: полная матрица
на каждый коммит, lint после тестов и платформенные правила «в голове» стоили
несколько лишних часов. Ниже правила, которые проверяются механически.

## 1. Дешёвые проверки первыми

В `engine-tests` есть задание `preflight`:

- `tests/check_release.py`;
- `scripts/quality_eval.py --gate`;
- `compileall`;
- `ruff`;
- `scripts/check_portability.py --changed <base>`.

Тяжёлые задания (`tests`, `floor`, `newer-python`, `windows`, `windows-314`,
`macos`, `adapter-live`, `legacy-310`) ждут `preflight`. Красный `preflight`
не тратит сорок минут на полный suite.

## 2. Один полный прогон на выпуск

`tests` на Ubuntu разбит на три доли, как `windows`; `floor`, `newer-python` и
`macos` тоже идут тремя долями. Каждая доля на своей машине, инварианты
остаются в первой доле.

Новый push в ту же ветку отменяет предыдущий прогон (`concurrency`). Старый
прогон уже не про тот коммит.

Зелёный `engine-tests` на ветке `release/*` сам делает fast-forward `master`
до проверенного коммита и ставит тег. Второй полный прогон на `master` больше
не нужен. Если `master` не предок проверенного коммита, выпуск останавливается.

## 3. Заморозка выпуска

- Фичи вливаются в `integration` до открытия `release/*`.
- В `release/*` идут только исправления, найденные гейтом.
- Новая фича после открытия ветки ждёт следующий выпуск.
- Большой релиз не заменяет короткий цикл: batch фич до заморозки, а не
  «соберём всё и один раз проверим».

## 4. Параллельные дорожки

- 4-5 независимых дорожек на релиз, у каждой свой набор файлов.
- Интегратор сводит дорожки и запускает полную матрицу один раз.
- Отдельный агент-платформенщик владеет падениями Windows и Ubuntu, чтобы
  авторы фич не ждали его очереди.
- Дорожка не считается готовой, пока её тесты не прошли на её ветке.

## 5. Платформенные правила

Правила проверяет `scripts/check_portability.py` по добавленным строкам:

- `os.path.relpath(path, start)`: `start` обязан быть `os.path.realpath(...)`,
  `os.path.abspath(...)` или `.resolve()`. Иначе на Windows относительный
  `start` и абсолютный `path` дают `../../runneradmin/...`.
- `write_text_atomic(plan..., ...)` пишется с `newline=""`: текстовый режим
  превращает LF в CRLF, а хеш плана считается по LF.
- В тестах нет `abs(..._ms...) <= N` при `N <= 1000`: wall-clock на медленном
  раннере добавляет секунду. Часы внедряются, значения проверяются точно.
- Пути в отчётах и JSON всегда через `/`, независимо от ОС.
- Сравнение путей идёт через `Path` или `os.path.normpath`, не строками с
  `os.sep`.
- Тест, который читает pandoc, обязан пройти и на дистрибутивном pandoc без
  `embed_data_files`: в песочнице он не видит свои `data/docx`.

## 6. Что делать при красном CI

1. Смотреть первое падение, а не перезапускать матрицу.
2. Повторить только упавшее задание, если причина внешняя (сеть, раннер).
3. Новый коммит делать только после локального воспроизведения.
4. Если падение платформенное, добавить правило в чекер или тест, который
   падает без исправления.
5. Не менять тест ради зелёного: менять код или вносить платформенное
   правило с объяснением.

## Чек-лист перед `release/*`

- [ ] `preflight` зелёный.
- [ ] Полная матрица зелёная на интеграционной ветке.
- [ ] `VERSION`, `CHANGELOG.md`, `UI_VERSION` и `module.json` согласованы.
- [ ] `check_portability.py --changed origin/master` чистый.
- [ ] Новые платформенные тесты падают без правки.
- [ ] В `release/*` нет новых фич, только исправления.
