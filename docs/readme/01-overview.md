# 1. Обзор фреймворка

> **Кому читать:** всем участникам проекта — аналитикам, владельцу продукта, разработчикам.
>
> **Коротко:** знания проекта живут в git как markdown-карточки. У каждой карточки есть
> статус доверия. Ассистент обязан его учитывать: проверенному — верить, импортированному —
> нет, устаревшее — только как историю. Решения фиксируются в неизменяемом журнале вместе
> с отклонёнными вариантами.

## Зачем это нужно

Мы используем ИИ, чтобы проверять и производить аналитические артефакты — истории,
критерии приёмки, спецификации. Без явной модели доверия это ломается тремя способами.

**«Сам написал — сам поверил».** Черновик истории, попавший в базу через синхронизацию,
ассистент начинает считать истиной — и не находит в нём ошибок.

**Потеря истории.** Подход поменялся, старую карточку заменили новой — и через полгода
никто не может ответить, почему отказались от альтернативы.

**Тихое устаревание.** Проверенное и протухшее лежат вперемешку, ассистент уверенно
отвечает по устаревшему, доверие к базе падает до нуля за пару таких случаев.

Фреймворк закрывает всё три двумя механизмами: **слоями доверия** (папки плюс статусы
карточек) и **журналом решений** — неизменяемыми Decision Records.

## Три принципа

**Артефакт ≠ знание.** Документ, который мы проверяем или производим, — это объект работы.
Знание — только карточки базы с подходящим статусом. Объект никогда не подаётся ассистенту
как факт, даже если его копия лежит в зеркале Confluence.

**Ничего не удаляется.** Устаревшее знание получает `deprecated`, ссылку на преемника и
уезжает в архив. Принятые решения не редактируются — только заменяются новыми.

**Проверенное меняет только человек.** Синхронизация не может перезаписать карточку,
которую проверил аналитик: она сигналит о расхождении, а владелец решает, что делать.

## Карта репозитория: слои доверия

| Папка | Что это | Уровень доверия |
|---|---|---|
| `Sources/` (`Confluence/`, `JIRA/`) | зеркала внешних систем, пишутся синком | объект работы, не знание |
| `Raw/` | первоисточники, положенные руками: `contract/` (госконтракт, ТЗ), `laws/`, `customer/`, `meetings/`, `project/` | доказательная база, цитируется |
| `AuroraKnowledgeDB/` | карточки знаний | по статусу карточки (ниже) |
| `AuroraKnowledgeDB/Requirements/` | требования заказчика (REQ) | по статусу; жизненный цикл требования — в `req_status` |
| `AuroraKnowledgeDB/Specs/` | спецификации фич (SPEC) | исполняемый контракт для разработки |
| `AuroraKnowledgeDB/Questions/` | вопросы к заказчику (Q) | незнание как объект: кому задан, что блокирует |
| `AuroraKnowledgeDB/Decisions/` | журнал решений, только добавление | accepted — истина; rejected и superseded — история |
| `AuroraKnowledgeDB/MOC/` | карты контента, оглавления | навигация |
| `AuroraKnowledgeDB/_archive/` | устаревшие карточки | только история |
| `Artifacts/` | продукты работы: истории, критерии, алгоритмы, экраны, ревью, приёмка | не знание, в контекст не подаётся |
| `Deliverables/work/` и `released/` | поставляемые документы: рабочие версии и переданные снапшоты | переданное неизменяемо и цитируется |
| `Workspaces/` | рабочие пространства задач: черновики, подборки, всё вспомогательное | не знание |
| `Templates/`, `Prompts/` | рецепты производства артефактов | инструкции, не факты |

Список папок фиксирован движком (`.opencode/structure_dirs.txt`) и одинаков во всех
проектах. Всё, что не укладывается в эту таксономию, живёт в `Workspaces/<задача>/`.

## Жизненный цикл карточки

В шапке каждой карточки есть `status`, `owner` (кто отвечает за актуальность), `verified`
(когда проверена) и `review_by` (срок годности).

| Статус | Что означает | Как трактует ассистент |
|---|---|---|
| `imported` | положено синком или извлечением, человек не смотрел | материал для оценки, НЕ факт |
| `draft` | набросок аналитика, гипотеза | идея, требует проверки |
| `in-review` | на ревью у команды | не использовать как факт |
| `verified` | проверено владельцем | факт с датой годности |
| `deprecated` | устарело, заменено | история, не применять |

Переходы: `imported`/`draft` → `in-review` → `verified`; в `deprecated` — только с
указанием преемника. Обратный переход `verified → draft` допустим, когда обнаружен дрейф.

`verified` — верхний статус базы. Ступень «утверждено вторым человеком» была в схеме до
версии 1.10 и не использовалась ни в одном проекте, поэтому её убрали: кто проверил и
когда — видно из `owner` и `verified`.

У карточки есть и версия схемы (`schema_version`) — по ней движок понимает, нужна ли
миграция, когда схема меняется. Проставляет её команда `kb:schema`.

## Журнал решений

Любое значимое решение — выбор подхода к интеграции, бизнес-правило, соглашение по
данным — оформляется как Decision Record. DR содержит контекст, **все рассмотренные
варианты, включая отклонённые с причинами**, само решение и следствия.

После принятия DR неизменяем: смена подхода — это новый DR со ссылкой `supersedes` на
старый. Вопрос «а почему мы не сделали через X?» всегда имеет адрес.

Тематические карточки описывают **текущее** положение дел и ссылаются на DR как на
обоснование. Карточка — «что истинно сейчас», DR — «как мы к этому пришли».

## Круговорот знаний

```
Confluence / Jira ──синк──▶ Sources/ ──извлечение──▶ карточки (imported)
                                                          │ ревью человеком
Raw/ (ТЗ, законы, встречи) ──разбор──▶ карточки (imported) │
                                                          ▼
                                            AuroraKnowledgeDB (verified)
                                                          │
        шаблоны + промпты + карточки ──производство──▶ Artifacts/ (US, AC, алгоритмы)
                                                          │ ревью человеком
                                                          ▼
                       публикация в Confluence/Jira ──синк──▶ Sources/ …
```

Произведённый артефакт не попадает в базу знаний напрямую — он возвращается через
публикацию, синхронизацию и обычный ревью-гейт. Это защита от самоопыления: база не
должна наполняться тем, что сама же и сгенерировала.
