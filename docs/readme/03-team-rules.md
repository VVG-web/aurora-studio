# 3. Регламент команды

> **Кому читать:** аналитикам, работающим с базой. Это правила, по которым база остаётся
> предсказуемой, когда с ней работает больше одного человека.

## Роли и владение

**Владелец карточки** (`owner`) — аналитик, который перевёл её в `verified` и отвечает за
актуальность до даты `review_by`. Владелец получает работу при дрейфе источника и при
истечении срока годности.

**Куратор раздела** — по одному на раздел, следит за качеством и отсутствием дублей:

| Раздел | Кто ведёт |
|---|---|
| `Glossary`, бизнес-процессы | бизнес-аналитик |
| `Processes` (алгоритмы), `Systems`, `Statuses` | системный аналитик |
| `Requirements`, `Specs`, трассировка | системный аналитик |
| `Decisions` продуктовые, `Questions` к заказчику | владелец продукта |

**Дежурный по базе** — по очереди, на неделю. Запускает `sync:diff` после синхронизации и
`kb:garden` в пятницу, раздаёт находки владельцам.

Если в проекте один аналитик, все три роли — это он. Регламент от этого не отменяется:
он превращается в разговор с собой через полгода.

## Ритуалы

### После каждой синхронизации → `sync:diff`

Синк не перезаписывает проверенные карточки. Вместо этого отчёт дрейфа показывает: какая
страница изменилась, какая `verified`-карточка на неё опирается, кто владелец. Владелец в
течение двух рабочих дней либо перепроверяет карточку и обновляет `verified`, либо
запускает замену через `kb:supersede`, либо помечает изменение как несущественное.

### Приём знаний в базу → ревью-гейт

Карточка попадает в `verified` только через проверку человеком:

1. Автор сверяет содержимое с источником, ищет дубли (по названию и алиасам), проверяет ссылки.
2. Проставляет `owner`, `verified`, `review_by` — по умолчанию три месяца, для стабильных
   справочников можно шесть.
3. Оформляет коммит или пул-реквест.

Механику записи делает `kb:verify` — он же откажет, если у карточки нет источника или есть
битые ссылки. Решение «этой карточке верю» остаётся за человеком.

### Еженедельно → `kb:garden`

Полчаса дежурного. Отчёт собирает: просроченные `review_by` по владельцам, карточки без
владельца, битые ссылки, сироты, дубли, `imported` старше тридцати дней. Механика чинится
сразу (`kb:repair`), содержательное уходит задачами владельцам.

### Перед передачей в разработку → `make:spec-pack`

Бандл спеки собирается скриптом и проверяет готовность механически: требования в
`agreed`, открытые вопросы не блокируют, основания не ниже `verified`. Нарушения не
блокируют сборку, но печатаются и попадают в раздел «Риски передачи» — подрядчик должен
видеть, на чём построен контракт.

## Правила Decision Records

**Когда DR обязателен:** выбирали из двух и более вариантов, и выбор влияет на систему,
процесс или данные; меняете ранее принятый подход; фиксируете договорённость со
смежниками, о которой будут спрашивать «почему так».

**Когда не нужен:** факт из первоисточника — это карточка знания; оперативное решение без
альтернатив; косметика.

**Незыблемое:**

1. Принятый или отклонённый DR не редактируется. Единственная разрешённая правка —
   `status: superseded` и ссылка на новый.
2. Отклонённые варианты описываются с причинами отказа — так, чтобы через год ответ на
   «почему не X» читался без археологии.
3. DR не удаляются никогда.
4. Принимая DR, автор обновляет затронутые карточки (через `kb:supersede`, если меняется
   текущая истина) и ставит в них ссылку на решение.

## Правила «никогда»

1. **Не редактировать `Sources/`** — папка принадлежит синку, правки затрутся. Контент
   правится в Confluence или Jira.
2. **Не удалять знания.** Устаревшее — `deprecated`, архив, ссылка на преемника.
3. **Не класть артефакты в `AuroraKnowledgeDB/`.** Истории, критерии приёмки и отчёты
   живут в `Artifacts/`; в базу знание попадает только через извлечение и ревью-гейт.
4. **Не публиковать произведённый ассистентом артефакт без проверки человеком.**
5. **Не заводить свои папки верхнего уровня.** Структура фиксирована движком; всё
   нестандартное — в `Workspaces/<задача>/`.

## Работа в git

База — часть репозитория, поэтому командная работа это обычный git-процесс: ветка →
изменения карточек → пул-реквест → ревью. История каждой карточки видна через `git log`
бесплатно. Но первичны статусы во frontmatter: именно их читает ассистент, а не историю
коммитов.

Полезно поставить храповик — `kit:hooks` ставит pre-commit, который не даёт числу ошибок
линтера расти. Он не требует чинить всё сразу; он лишь запрещает делать хуже.

## Чеклист качества карточки

Перед переводом в `verified`:

- [ ] одна карточка — одна мысль; заголовок совпадает с содержанием;
- [ ] шапка полная: `status`, `owner`, `verified`, `review_by`, `source`, `type`;
- [ ] `source` указывает на реальный первоисточник в `Sources/` или `Raw/`;
- [ ] алиасы включают все варианты названия: оригинал из источника, короткий код, аббревиатуру;
- [ ] все вики-ссылки ведут на существующие карточки;
- [ ] дубля нет — искали по названию и по алиасам;
- [ ] утверждения, зависящие от выбора, ссылаются на Decision Record.

Первые шесть пунктов проверяет `kb:lint` и частично чинит `kb:repair`. Седьмой — только
человек.
