# 2. Лёгкий старт: база знаний за один день

> **Кому читать:** тому, кто открыл проект впервые.
>
> Полный фреймворк — это система со статусами, решениями и трассировкой. Она никуда не
> денется и будет расти. Но чтобы **начать**, достаточно малого: пять правил, три команды,
> одна привычка.

## Зачем это лично вам

Ассистент отвечает настолько хорошо, насколько хорош его контекст.

**Без базы** каждый запрос начинается с нуля: он не знает ваших сокращений, путает
статусы, выдумывает алгоритмы. Вы тратите время на объяснения — каждый раз заново.

**С базой** вы за секунды получаете подборку проверенных карточек по теме. Ассистент
говорит на языке проекта и опирается на факты, а не на догадки.

**Ваш вклад.** База живёт, только если каждый возвращает в неё то, что узнал.
Минимальный вклад — десять минут в неделю.

## Пять правил

**1. Работайте в `Workspaces/` и `Artifacts/`.** `Workspaces/<задача>/` — ваша папка под
задачу: черновики, подборки, что угодно. `Artifacts/` — результаты: истории, критерии
приёмки, алгоритмы, отчёты.

**2. Не трогайте руками `Sources/` и `Raw/`.** `Sources/` пишет синхронизация — ваши
правки затрутся при следующем прогоне; правьте в Confluence или Jira. `Raw/` — это
доказательства: ТЗ, законы, протоколы встреч. Они неизменны по определению.

**3. Различайте три состояния вместо пяти статусов.** На старте достаточно светофора:

| Состояние | Статусы | Что можно |
|---|---|---|
| **Непроверено** | `imported`, `draft` | читать можно, ссылаться в работе — нельзя |
| **Проверено** | `verified` | это факт, на него опирается ассистент |
| **Устарело** | `deprecated` | только история, лежит в архиве со ссылкой на замену |

`in-review` включится, когда в команде появится ревью. Пока вы одни — всё, что прошло
вашу проверку, это `verified`.

**4. Ничего не удаляйте.** Устаревшее не стирается, а заменяется: `kb:supersede` пометит
старую карточку и перепишет ссылки на преемника.

**5. У проверенной карточки есть владелец и срок.** Ставя `verified`, вы пишете `owner`
(себя) и `review_by` — обычно три месяца. Через три месяца карточка сама попросится на
перепроверку.

## Три команды на каждый день

**Перед любым серьёзным вопросом — соберите контекст:**

```bash
python3 .opencode/scripts/ctx_pack.py "тема"
```

Получите подборку карточек с шапками доверия. Её и вставляйте в запрос — вместо того,
чтобы пересказывать проект своими словами.

**После правки базы — проверьте механику:**

```bash
python3 .opencode/scripts/kb_lint.py --summary
```

Битые ссылки, потерянные шапки, случайные секреты в коммите. Занимает секунду.

**Раз в неделю — посмотрите на здоровье:**

```bash
python3 .opencode/scripts/aurora_stats.py
```

Сколько карточек, сколько проверенных, что протухло, где сироты.

Все команды — и эти три, и остальные сорок шесть — есть в панели управления, если
терминал не ваш инструмент:

```bash
python3 aurora.py cockpit
```

## Одна привычка

**Узнали что-то, чего нет в базе, — заведите карточку.** Не откладывайте «на когда будет
время»: через неделю знание забудется, а через месяц вы будете выяснять его заново у того
же человека.

Карточка на старте — это три строки в шапке (`title`, `status: draft`, `source`) и один
абзац текста. Довести её до `verified` можно потом, когда знание подтвердится.

## Что отложить

| Что | Когда понадобится |
|---|---|
| Decision Records | когда впервые поменяете ранее принятый подход |
| Требования и трассировка (REQ → SPEC → задача → приёмка) | когда пойдёт разработка по вашим документам |
| Ритуалы: дежурный, еженедельная прополка | когда в проекте станет двое аналитиков |
| Публикация в Confluence из git | когда база обгонит витрину по актуальности |
| Спецификации и spec-pack | когда появится внешний подрядчик |

Ничего из этого не нужно в первый день. Всё это уже есть в ките и включится тогда, когда
станет нужным.
