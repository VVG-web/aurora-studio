# ADR-059. Профили развёртывания и baseline Python

## Контекст и проблема

Целевые пункты технического задания — перенос в облако, масштаб, роли и единый вход — упирались в
одну неопределённость: Аврора существует в одном режиме, и никто не записал, какой именно. Панель
отвечает только на `127.0.0.1` (`cockpit/aurora_cockpit.py`), состояние лежит в нескольких корнях и
в памяти процесса, движок копируется в каждый проект (`engine_manifest.txt`), а один прогон
использует три рантайма: код кита в процессе панели, копию движка в подпроцессах и адаптер в общем
venv. Корневой синтез ревью (кластер BL-ARC-01) называет «ADR профилей развёртывания» первым
пунктом порядка разблокировки.

Владелец ответил на вопрос о профиле эксплуатации (Q-01, 09.10.2026): **один человек на машине;
команда — это несколько клонов одного git-репозитория**. Облако, роли с правами и единый вход не
планируются (Q-11); роли — только пресеты разделов панели без прав доступа (Q-10).

Отдельно открыт вопрос минимальной версии Python. CI гоняет ядро на 3.9 и 3.12
(`.github/workflows/test.yml`), системный Python macOS — 3.9, но актуальные версии нужных
библиотек требуют 3.10 и выше. Версия 3.9 снята с поддержки 31.10.2025, 3.10 — в октябре 2026.

## Факторы решения

* Горизонт — 180 дней, исполнитель один: решение не должно создавать матрицу профилей, которую
  некому поддерживать.
* Ничего не ломать у действующих проектов: движок копируется в `.aurora/` и обновляется вместе с
  китом.
* Закрытые проекты не отправляют данные наружу; код кита открыт (Q-03).
* Аналитик на macOS часто работает без прав администратора и на системном Python.

## Рассмотренные варианты

1. **Один локальный режим «как есть», облако потом.** Дёшево сейчас, но контекст исполнения
   (cwd процесса как единственный «проект») и headless-запуск будут обойдены локальными заплатами.
2. **Три профиля: solo, team-server, cloud** (вариант отчёта ревью). Честно описывает цель из
   технического задания, но тратит силы на то, что владелец не планирует.
3. **Два режима: solo и «команда клонов через git».** Облако, роли, единый вход вне горизонта.
   Выбранный вариант.
4. **Отдельный серверный продукт.** Удвоение поддержки при одном исполнителе.

## Решение

Выбран вариант 3.

1. **Профиль по умолчанию и единственный в горизонте — solo.** Один пользователь, панель на
   loopback, проект — каталог на его машине. Команда работает так: каждый участник держит свой клон
   одного git-репозитория и свой экземпляр кита; общее состояние — только то, что лежит в git.
2. **Не планируются:** облачный профиль, серверная панель за прокси, роли с правами доступа,
   единый вход. Записи про них (ADR-019, ADR-022, ADR-057 предложений ревью) не принимаются сейчас;
   пересмотр — только по новому запросу владельца с новым ADR.
3. **Инварианты** (держатся в любых будущих режимах): Markdown и git — система записи знания;
   доверие вычисляется, а не назначается; модель не пишет файлы вне белого списка; каждый
   исполняемый шаг видит контекст исполнения (проект, каталоги состояния) явным объектом, а не
   текущей папкой процесса.
4. **Шов на будущее:** остаётся один дешёвый интерфейс `AuthProvider` как задел, если он стоит
   меньше дня; без него и без реализаций.
5. **Baseline Python — трёхуровневая политика.** Python **3.11 и новее** поддерживаем и тестируем в
   CI. **3.10** работает, но его поддержка апстримом заканчивается в октябре 2026 (PEP 619,
   день не подтверждён): `kit:doctor` и панель предупреждают, CI-задание неблокирующее, срок — до апреля 2027. **Ниже 3.10** — понятная остановка с текстом
   «нужен Python 3.10+, рекомендуем 3.11 и новее» и способом установки. Пересмотр baseline на 3.12 —
   октябрь 2027.
6. **Установка нужной версии** — лаунчер перебирает `python3.14 … python3.10`, проверяет кандидата
   запуском и предлагает путь установки без прав администратора; без явного согласия ничего не
   ставится. Реализуется отдельным кластером бэклога.

## Последствия

* Плюс: в ближайшие 180 дней не нужно проектировать и тестировать серверные профили; около 108
  чел.-дн. кластеров про облако, роли и единый вход переходят в «позже».
* Плюс: у любого нового ADR появляется критерий «нужно ли это в solo или в команде клонов».
* Плюс: массовая модернизация кода не нужна — аннотации уже написаны по-современному, на 3.9 они
  держались на `from __future__ import annotations`.
* Минус: аналитик на системном Python 3.9 перестаёт запускать кит, пока не поставит 3.11; это
  главный риск и он закрывается лаунчером и текстом в README.
* Минус: README и документация обещают «Python 3.9+»; их нужно изменить вместе с принятием, а
  CI-задание `oldest-python` заменено на `floor` (3.11, блокирующее) и `legacy-310` (3.10, неблокирующее).
* Попутно исправляется `min_python (3, 9)` у надстройки Pydantic AI: пакет требует 3.10+.

## Проверка

* Тест на строки README, `docs/INSTALL.md` и `scripts/aurora_extras.py`: заявленный минимум
  совпадает с этой записью.
* CI: блокирующие `tests` (3.14), `floor` (3.11) и `windows` (3.12, три доли: выпуск не должен уходить при красном
  Windows); неблокирующие `newer-python` (3.12 и 3.13), `legacy-310` (3.10, до апреля 2027), `windows-314` (3.14)
  и `macos` (3.14); блокирующими станут после зелёных прогонов. Неблокирующее `adapter-live` (3.12, Linux и Windows)
  ставит venv Pydantic AI как панель и гоняет `--selfcheck` и живые проверки адаптера; отдельный еженедельный
  `canary.yml` проверяет свежие версии зависимостей без ограничений и при красном открывает issue (выпуск от него не зависит).
* `kit:doctor` на Python 3.10 выдаёт предупреждение, на 3.9 — остановку.
* Тест «нет ветвлений по профилю»: в предметном коде нет проверок вида «если облако».
