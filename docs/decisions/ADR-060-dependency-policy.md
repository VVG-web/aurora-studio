# ADR-060. Политика зависимостей

## Контекст и проблема

Принцип «ядро без обязательных рантайм-зависимостей» держался на двух пакетах без версий
(`requirements.txt`: `beautifulsoup4`, `markdownify`), а надстройки ставятся без пинов и хешей
(`scripts/aurora_extras.py`, `pip: ["pydantic-ai"]`) — на фоне серии компрометаций PyPI в 2026
году. Самописное закрепилось там, где зависимость не разрешалась: много HTTP-клиентов, читателей
конфигурации, рендереров Markdown, самодельные замки и проверка живости процесса. Часть дефектов
Windows оттуда же.

Владелец решил (Q-04, 09.10.2026): **зависимости допустимы**, принцип «ядро только на стандартной
библиотеке» снят. Минимальная версия Python определена в [ADR-059](ADR-059-deployment-profiles.md):
3.11 и новее тестируем, 3.10 с предупреждением, ниже — остановка.

## Факторы решения

* Воспроизводимость и защита цепочки поставок важнее «чистоты» stdlib.
* Лицензии: код кита открыт, но поставляется в закрытые проекты.
* Один исполнитель: правила приёма должны быть короткими и проверяться машиной.
* Модель «копия движка в `.aurora/`» не должна ломаться.

## Рассмотренные варианты

1. **Ядро только на stdlib** (рекомендация отчёта ревью). Сохраняет автономность, но закрепляет
   самописное и мешает заменить хрупкие места проверенными пакетами. Отклонён владельцем.
2. **Любые зависимости без правил.** Быстро, но риск цепочки поставок и лицензий.
3. **Зависимости допустимы по политике приёма** — чек-лист, закреплённые версии, хеши, карантин.
   Выбранный вариант.

## Решение

Выбран вариант 3.

1. **Зависимости допустимы и в ядре.** Приоритетные кандидаты на замену самописного: проверка
   живости процесса и работа с процессами, файловые замки, разбор конфигурации с сохранением
   комментариев, тесты. Каждая замена — отдельным кластером бэклога со своим тестом; эта запись
   разрешает, но не требует.
2. **Чек-лист приёма.** Новая зависимость принимается, если выполнено всё: лицензия из списка
   разрешённых (MIT, BSD, Apache-2.0, PSF, ISC; MPL-2.0 без изменений); AGPL, GPL, BSL, SSPL и
   Elastic запрещены для поставляемого или линкуемого кода, как отдельный внешний процесс — только
   по отдельной записи ADR; `Requires-Python` не выше baseline из ADR-059; нет открытых
   уязвимостей по базе OSV за последние 12 месяцев; есть живое сопровождение (релиз за последний
   год); поддерживается Windows; вес и число транзитивных зависимостей оправданы.
3. **Единый источник и закрепление.** Зависимости объявляются в одном месте (`pyproject.toml` и lock
   с хешами); версии закреплены; новые релизы принимаются с карантином (по умолчанию 7 суток).
   Надстройки (venv Pydantic AI и другие) подчиняются тем же правилам: пины и хеши вместо голого
   имени пакета.
4. **Проверки в CI:** `pip-audit` и Dependabot; перечень зависимостей в SBOM (CycloneDX) —
   вместе с [ADR-066](ADR-066-version-and-release-policy.md).
5. **Учёт решений.** Список зависимостей и причина каждой ведётся в `docs/dependencies.md`;
   решения «не брать» фиксируются строкой с причиной и сроком пересмотра, чтобы вопрос не
   возвращался.
6. **Вендоринг** допустим только для чистого Python с разрешающей лицензией, закреплённой версией
   и тестом.
7. **Порты не обязательны.** Сторонний пакет можно использовать напрямую; запасной путь на stdlib
   нужен только там, где пакет не ставится без сети в закрытом контуре (разбор страниц Confluence и
   сайтов остаётся с запасным путём).

## Последствия

* Плюс: единые критерии вместо споров по каждому пакету; воспроизводимая установка; сокращаются
  самописные замки и проверки живости процесса.
* Плюс: убирается противоречие, при котором документация обещает «никаких зависимостей», а
  установка уже тянет два пакета и надстройки.
* Минус: нужны `pyproject.toml` и lock; установка в закрытом контуре без доступа к PyPI требует
  локального зеркала или вендоринга.
* Минус: нагрузка на единственного исполнителя — проверки приёма и обновления зависимостей.
* Риск: README и CI-задание про «Python 3.9+ без зависимостей» нужно изменить вместе с принятием.

## Проверка

* Тест на `pyproject.toml` и lock: все зависимости закреплены, у каждой есть хеш.
* Тест на `docs/dependencies.md`: каждая зависимость из lock в нём описана, лицензия из списка
  разрешённых.
* CI: `pip-audit` без находок уровня high; Dependabot включён.
* `kit:doctor` проверяет, что надстройки поставлены из закреплённых версий.
