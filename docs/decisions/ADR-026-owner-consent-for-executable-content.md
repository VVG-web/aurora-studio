# ADR-026. Согласие владельца машины на исполняемое содержимое проекта

## Контекст и проблема

Проект — это git-репозиторий, и команда работает через несколько клонов. Часть его содержимого
исполняется на машине каждого участника: боты (`bots/*.md`), запускаемые по расписанию и по
кнопке, скрипты движка, лежащие в проекте (`.aurora/scripts/`), и (до решения 10.10.2026, см. ниже)
определения серверов MCP в проектном `mcp.json`.
Изменение такого файла у одного участника при обычном `git pull` у другого становится запуском
чужой команды без его ведома. Проектный `mcp.json`, кроме того, может подменить по имени сервер,
заданный на машине.

Владелец решил (Q-08, 09.10.2026): новое или изменённое исполняемое содержимое **не запускается без
согласия владельца машины**, согласие привязано к хешу.

## Факторы решения

* Репозиторий не должен давать исполнение на чужих машинах без подтверждения.
* Команда небольшая: подпись коммитов и инфраструктура ключей — слишком тяжело.
* Согласие не должно ломать работу с привычными ботами: подтверждается один раз на содержимое.
* Решение должно работать офлайн и в закрытом проекте.

## Рассмотренные варианты

1. **Ничего не менять:** определения из git исполняются сразу. Просто, но небезопасно.
2. **Подпись коммитов и проверка подписи.** Сильная гарантия, но тяжело для небольшой команды.
3. **CODEOWNERS на `bots/`.** Защищает только на платформе git, не на машине участника.
4. **Реестр согласий по хешу на машине.** Выбранный вариант.

## Решение

Выбран вариант 4.

1. **Реестр согласий** хранится в состоянии пользователя на его машине, не в репозитории: проект,
   путь определения, SHA-256 содержимого, кто и когда согласился.
2. **Что подпадает:** боты проекта (`bots/*.md`: промпт, расписание `cron`, `enabled`) и скрипты
   движка из папки проекта (`.aurora/scripts/`, у старых проектов `.opencode/scripts/`). Серверы MCP
   из проектного `mcp.json` в перечень **не входят** (уточнение 10.10.2026, ниже).
3. **Неодобренное или изменённое** определение (хеш не совпал с записью) **не запускается** ни по
   расписанию, ни по кнопке, ни из консольной команды; в разделах Cron и «Боты» оно помечено, а
   причина названа текстом.
4. **Согласие даёт владелец машины** явным действием (кнопка в панели или команда). Автоматика,
   ассистент и ночная цепочка согласие не дают.
5. **Скрипт проекта.** Скрипты движка из папки проекта (`.aurora/scripts/` с `agents/`) исполняются,
   только если **вся папка** чиста: каждый её файл — копия кита (тот же хеш) или согласован, лишних
   `.pyc`, расширений и ссылок на папки нет. Проверка по одному файлу не годится: Python кладёт папку
   скрипта первой в `sys.path`, и соседний чужой модуль подхватывается `import`ом. Иначе запускаются
   скрипты кита (у них `sys.path[0]` — папка кита), а в «Ботах» появляется карточка «Скрипты
   проекта ждут согласия». Раннер, лежащий в самом проекте, сверяется с китом по `kit_path.txt`;
   кит не найден — «копией кита» файл не считается, решает только согласие. Папку проекта `Scripts/` движок не запускает вовсе.
6. **Запись в журнал** (событие согласия и отказа запуска) — вместе с общим журналом действий.

### Уточнение владельца 10.10.2026: MCP не исполняемое содержимое проекта

Целевое состояние: MCP-серверы настраиваются **один раз на уровне кита** (как модели), проектный
`mcp.json` серверы не определяет, а проект выбирает серверы кита по имени; тогда согласие на
определения MCP не нужно. **Реализовано (BL-SEC-12):** определения серверов (команда, аргументы,
окружение, токены) читаются только из `<кит>/local/mcp.json`; проектный `mcp.json` не читается и не
перекрывает серверы кита (`agent_core.mcp_config`), `doctor` и панель предупреждают «файл не
используется», перенос в кит — по показу различий и явному подтверждению. Проект выбирает серверы кита
по имени (`mcp: servers:` в `aurora.config.yaml`); неизвестное имя — ошибка до запуска. Право записи в
Jira (`jira_write`) выдаёт только кит (`permissions` в `local/mcp.json`), а `jira_write: true` проекта
из git его не включает: проект может лишь сузить. Согласие нужно ботам и скриптам проекта.

### Реализация (BL-SEC-04)

* Реестр — `~/.aurora/consent.json` (`AURORA_CONSENT_HOME` переопределяет папку), ключ — вид, проект,
  файл; значение — SHA-256 текста (концы строк приводятся к `\n`), время, кто, текст одобренной
  версии (для показа изменений). События согласия и отказа — `consent-log.jsonl` рядом.
* Единое место отказа для бота — `bots.run()`: расписание, кнопка и командная строка проходят через
  него; планировщик Cron дополнительно не ставит бота без согласия в очередь и не раскрывает его в
  шаге «все боты».
* Согласие даёт кнопка «Одобрить» (панель показывает изменения или весь текст, согласие привязано к
  показанному хешу) или `bots.py --approve`. Ассистент (`write_allowed`), маршруты и Cron этой команды
  не имеют: в `commands.txt` её нет.
* Быстрый путь автора: бот, созданный или сохранённый в панели, остаётся согласованным, если
  согласован был его прежний текст; копия несогласованного и бот из `git pull` согласия не получают.
* Старые проекты при первом запуске получают запрос на все существующие боты: пакетная кнопка в
  «Ботах» (одобряет только показанный список; запрос без списка отклоняется) и `--approve --all`.
  `--all` одобряет только ботов; скрипты проекта — отдельное решение (`--scripts`, `--script <имя>`):
  для устаревшего движка проще обновить его, чем одобрять около сотни файлов.
* Все пути запуска скрипта проекта идут через `trusted_engine_script` / `script_path`, включая
  `kb_lint.py`, `kb_corrections.py` и `kb_graph.py` панели; `doctor` не импортирует модули из
  `<проект>/.aurora/scripts`; команды терминала `aurora.py <команда> <проект>` и `aurora.py setup`
  идут через ту же функцию (`aurora.engine_script`). Бот без согласия в шаге «все боты» Cron идёт пропущенным с пометкой
  «не одобрен», а `doctor` предупреждает о ждущих ботах и файлах движка.
* Байт-код: Python грузит `.pyc` из `__pycache__` проекта без сверки с исходником (с хешем «не
  проверять» — всегда, с отметкой времени — когда её подогнали под файл, например архивом).
  Поэтому `aurora_common` закрепляет за процессом и его потомками префикс байт-кода машины
  (`PYTHONPYCACHEPREFIX`, `~/.aurora/pycache`; MCP-серверу — аргумент `-X pycache_prefix`), а `.pyc` с
  хешем в папке проекта запирает её как лишний файл.
* Шаги отчёта (`.aurora/reports/analyst`) и библиотека графа (`.aurora/vendor`) лежат вне
  `.aurora/scripts` и согласием не сверяются: берутся китовые; проектные — только если кита не найти.
  Зонд отчётов панели идёт с `-I`, чтобы корень проекта не попал в `sys.path`.
* Реестр один на родителя и потомков: `child_env` не берёт `AURORA_CONSENT_HOME` из файлов настроек
  (проект приезжает через git) и выставляет его равным `consent_home()` родителя.
* Хеш скрипта считается по байтам (CRLF и LF — один); запись реестра идёт под замком, с уникальным
  именем временного файла; агенту закрыты и сокращения флага (`--appr`).

## Последствия

* Плюс: клон чужого репозитория или `git pull` от коллеги не запускают незнакомый код.
* Плюс: ночные цепочки не выполняют изменённого без ведома владельца.
* Минус: лишнее подтверждение после каждого изменения бота — особенно у автора, который правит
  бота каждый день; нужен быстрый путь «одобрить свои изменения».
* Минус: защита от владельца машины, который согласился не глядя, отсутствует; это согласие, а не
  изоляция.
* Риск: старые проекты при первом запуске получат запрос на все существующие определения;
  нужна пакетная кнопка «одобрить текущее состояние» с показом списка.

## Проверка

* Тест: бот с неодобренным хешем не запускается ни одним из трёх путей (расписание, кнопка,
  командная строка), а после согласия запускается.
* Тест: изменение одного байта определения снимает согласие.
* Тест: проектный скрипт, отличающийся от кита, не исполняется без согласия; после согласия
  исполняется, после правки снова ждёт.
* Тест: ночная цепочка и ассистент не имеют пути к выдаче согласия.

## Дополнительно

* Источник: предложения ревью 08.10.2026 (ADR-026), решение Q-08 от 09.10.2026.
* Закрывает кластер бэклога BL-SEC-04 частично (боты и скрипты проекта); BL-SEC-12 (MCP: определения
  только в ките, выбор проектом по имени, право записи в Jira у кита) и часть BL-TEAM-32 — отдельными шагами. Остаточный риск, вынесен из этого кластера: согласие на бота
  считает хеш только его текста, а `SKILL.md` выбранных навыков (папка навыков проекта едет
  через git) в хеш не входят — правка навыка после согласия меняет поведение одобренного бота;
  значение `mcp.jira_write` проекта на запись больше не влияет без права кита (BL-SEC-12);
  «знания только своего проекта» не реализовано (BL-SEC-33).
  Раннер, запущенный из проекта без указателя на кит, исполняет то, что человек запустил сам.
  Остаточные риски вне согласия: вложения и контекст бота (текст из git вне хеша бота), git-хуки
  (`aurora_hooks.py` запускает `.aurora/scripts/kb_lint.py` без проверки), настройка внешнего
  ассистента `aurora_mcp.config_block` (печатается `--selftest`, указывает на скрипт проекта);
  запись реестра защищена замком процесса, а два одновременных процесса (`--approve` в терминале и
  панель) могут потерять запись друг друга.
* Связано: [ADR-059](ADR-059-deployment-profiles.md) (команда как несколько клонов одного
  репозитория); права по ролям не вводятся.
* Решено при реализации: исполняемыми скриптами считаются файлы `.aurora/scripts/*.py`, которыми
  движок подменяет скрипты кита; `Scripts/` проекта движок не запускает.
