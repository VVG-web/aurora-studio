# Git без конфликтов: личное, части участников и общий manifest

Проект Aurora открывают несколько человек и несколько машин. Один обновляет базу, другой
только смотрит, третий разбирает свои источники. Если всё это лежит в одном файле, Git
даёт конфликт на каждой параллельной правке. Поэтому файлы делятся на три класса.

## LOCAL — состояние машины, вне Git

Это история открытых файлов панели, раскладка Obsidian, локальная точка сравнения выдачи,
производный граф, штамп версии и пусковые файлы. Они не нужны команде и не должны
синхронизироваться.

- Канонический блок `.gitignore` добавляет их при установке и `kit:update`.
- Уже отслеживаемые файлы снимаются с index через `git rm --cached`, но **остаются на
  диске**. Повторный запуск ничего не меняет.
- Список ведёт `scripts/aurora_update.py` (`LOCAL_STATE_RELS`), а не человек.

## SHARD — общие данные, но по частям участника

Это история замеров поиска, дата обновления базы, журналы агента и холостые прогоны.
Дописывать в один общий файл нельзя: два участника гарантированно конфликтуют.

- `AuroraKnowledgeDB/meta/kb_updated.d/<actor>.json`
- `AuroraKnowledgeDB/meta/search-quality.d/<actor>.json`
- `AuroraKnowledgeDB/meta/agent-runs/<stamp>_<actor>_<task>.md`
- `AuroraKnowledgeDB/meta/agent-runs/_пустые/<actor>.md`

Идентичность участника даёт `scripts/aurora_actor.py`: `AURORA_USER`, затем git
`user.name`/`user.email`, затем пользователь ОС. Имя части — безопасный slug и короткий
SHA-256; email в имя не попадает. Запись идёт только в свою часть, чтение объединяет
legacy-файл и все валидные части, дедуплицирует и сортирует детерминированно. Битая часть
соседа не мешает читать остальные.

## SHARED — смысловые знания

Карточки, решения, требования и сам `manifest.json` остаются общими. Их нельзя просто
игнорировать: это потеря работы. Для `manifest.json` добавлен доменный merge.

## manifest.json: merge по ключам источников

`AuroraKnowledgeDB/meta/manifest.json` — учёт разобранных источников. Два участника почти
всегда меняют разные ключи `sources`, поэтому построчный merge даёт ложный конфликт.

- `.gitattributes`: `AuroraKnowledgeDB/meta/manifest.json merge=aurora-manifest`.
- `scripts/merge_manifest.py` — трёхсторонний merge:
  - `sources` по ключам; если сторона не меняла запись, побеждает изменение другой;
    если обе меняли — более поздний `processed`; удаление при неизменной второй стороне
    сохраняется;
  - `cards` — объединение по каноническому JSON;
  - `updated` и `version` — максимум.
- `install_aurora.py` и `aurora_update.py` настраивают git driver
  `merge.aurora-manifest.driver` в проекте. Без git шаг тихо пропускается.

Драйвер не удаляет данные: при битом JSON он возвращает код 1, и Git оставляет конфликт
человеку.

## Откат и смешанные версии

- Откат кода оставляет части на диске и в Git. Старый движок читает legacy, но не видит
  новые части; для полного возврата нужна отдельная явная консолидация.
- `manifest.json` merge работает и на старых проектах: правило и драйвер добавляются при
  `kit:update`, повтор идемпотентен.
