# Проверка доступности и стабильности соединения

Часть работы кита зависит от связи: источники живут за VPN, веб — в интернете, модели — у провайдеров, а есть работа, которой
сеть не нужна вовсе. Раньше кит о связи не знал: оборвавшееся соединение выглядело как «таймаут источника» или «провайдер не
ответил», движок гонял запросы по кольцу шлюзов и ждал вслепую. Теперь связь описана явно и проверяется до работы, а не по её
следам. English version: [en/connectivity.md](en/connectivity.md).

Проверка **выключена, пока владелец её не включит**: без настройки кит работает ровно как раньше, ничего не проверяет и
ничего не блокирует. Всё настраивается в панели — файлы руками править не нужно.

## С чего начать

Панель → **Проверка соединения** (группа «Машина»). Пока профилей нет, раздел объясняет, что такое probe, и предлагает мастера
из трёх шагов:

1. **Назовите профиль**, например `VPN-1`. Имя — для узнавания: на него потом ссылаются источники и провайдеры моделей, а
   адресов в проекте нет.
2. **Впишите адрес, который отвечает только при включённом VPN** (внутренний сервис, а не публичный сайт), выберите тип
   проверки и, для TCP, порт.
3. **Нажмите «Проверить»** — панель покажет ответ, время и что считать нормой. Если VPN сейчас выключен, ответа не будет, и это
   нормально: профиль можно добавить и проверить позже.

Затем включите «Проверка включена» и сохраните. Рядом с каждым полем — пояснение и пример (`example.com`); «Проверить сейчас»
работает и до сохранения (кнопка «Проверить» у самого probe), и после.

## Профили и probe

- **Профиль** — имя канала связи (`VPN-1`). Сам он ничего не проверяет.
- **Probe** — адрес, который отвечает только когда связь есть: например, внутренний сервис за VPN или любой сайт, которому вы
  доверяете, для проверки интернета. У профиля может быть несколько probe. **Всего на кит — не больше десяти.**

| Тип | Подходит для | Замечания |
|---|---|---|
| **TCP** | «порт открыт» | хост и порт, например `example.com`, 443 |
| **HTTP/HTTPS** | «сервис отвечает» | статус (по умолчанию 2xx и 3xx; можно `200`, `2xx`, `401`) и необязательный текст, который должен встретиться в начале ответа (в первых 64 КБ); перенаправления не выполняются; логин и пароль в адрес не вписываются |
| **ICMP (ping)** | «хост отвечает» | через системный `ping`; на многих серверах и в сетях ICMP закрыт — тогда берите TCP или HTTP |

Срок ответа и частота проверки задаются для каждого probe или один раз для всех (раздел «Общие настройки»). Адреса хранятся
на этой машине (файл закрыт правами 600), в git проекта они не попадают. Токены и пароли в адрес не вписывают: путь адреса
лежит в файле открытым текстом.

## Правило профиля и антидребезг

Из ответов probe профиль получает состояние по правилу:

- **`any_healthy`** — доступен, пока отвечает хотя бы один адрес (рекомендуется: один упавший сервис не гасит весь VPN);
- **`quorum(K)`** — доступен, если отвечает не меньше K адресов;
- **`all_healthy`** — доступен, только если отвечают все.

Профиль меняет состояние не сразу: **недоступным** он становится после N проверок подряд с неудачей, **доступным** снова — после
M проверок подряд с успехом (по умолчанию 3 и 2; их можно задать для всех или для профиля). Между проверками состояние
держится, мигание не показывается. Проверка, пришедшая раньше половины интервала после прежней (30 секунд при интервале по умолчанию; так бывает при
нескольких нажатиях «Проверить сейчас»), заменяет прежнюю оценку, а не добавляется к ней. Первая проверка после долгого перерыва (данные старше трёх интервалов) решает состояние сразу — сравнивать не с чем.

## Состояния

Профиль: `online` — доступен; `degraded` — правило выполнено, но не все probe отвечают; `offline` — правило не выполнено;
`unknown` — проверки ещё не было или она старше трёх интервалов.

Кит в целом считается **только по тому, что нужно делу**: по включённым источникам выбранного проекта и по провайдерам из
раздела «Модели», а не по всем описанным профилям.

| Состояние | Что значит |
|---|---|
| `online` | всё нужное доступно |
| `degraded` | всё нужное доступно, но часть probe не отвечает |
| `partial` | часть нужного недоступна: работают функции, которым оно не нужно |
| `no_vpn` | интернет есть, а все нужные профили недоступны |
| `offline` | нет интернета: доступны только функции без подключения |
| `unknown` | состояние не определено |

**Интернет** — встроенный профиль `internet`. Адреса для него задаёт только владелец: **кит сам не ходит на чужие адреса**. Пока
ни одного адреса нет, интернет «не известен» — это не «нет интернета», и ничего не блокируется. Впишите любой адрес, которому
доверяете (например, `example.com`).

## Где видно

- **Значок в шапке панели** — состояние кита (появляется, когда проверка включена); нажатие открывает раздел.
- **Раздел «Проверка соединения»** — режим работы кита, профили, probe с последним ответом и временем, интернет, журнал смен
  состояния. Фоновая проверка идёт в панели, пока она работает.
- **`kit:doctor`** — строка «связь: …» из сохранённого состояния.
- Сообщения: при отсутствии интернета — «Режим работы — offline, доступны только функции без подключения»; при недоступном
  профиле — «VPN-1 недоступен; доступны функции без VPN-1 и web-функции».

## Источники: режим доступа

Панель → **Настройки проекта → Режим доступа источников**. У каждого подключённого источника задаётся, как он достаётся:

| Режим | Что значит |
|---|---|
| без VPN, требует интернет | веб-страницы и подобное: профиль не нужен, но без интернета источник недоступен |
| требует VPN-профиль | источник за VPN; выбирается профиль из раздела «Проверка соединения» |
| локальный или из кэша | читается с этого компьютера, сеть не нужна |
| смешанный: VPN и локальный кэш | свежие данные — через профиль, прочитанное остаётся доступным из кэша |

Два признака независимы от режима: **«Требует интернет»** (нужен независимо от VPN: «без VPN» не значит «без интернета») и
**«Доступен из кэша без связи»**. В проекте хранится только **имя** профиля (блок `source_access:` в `aurora.config.yaml`,
остальной конфиг запись не трогает); адресов проверки в проекте нет.

Умолчания: у веб-модуля — «без VPN, требует интернет» (так сказано в его манифесте, `access.mode`); остальные источники и
провайдеры без привязки к профилю **считаются доступными, как раньше**: пока владелец ничего не настроил, поведение не меняется.

## Провайдеры моделей

Панель → **Модели** → у провайдера: **«Работает через профиль»** (профиль из «Проверки соединения» или «без VPN») и
**«Проверка ручки провайдера»**: «не проверять» (по умолчанию), «отвечает ли» или «отвечает с ключом». Доступность VPN — не
доступность провайдера: VPN жив, а провайдер лежит — провайдер всё равно считается недоступным. Ключ при проверке «с ключом»
уходит только на адрес самого провайдера и только по защищённому каналу (https либо этот компьютер). Старые файлы настройки
моделей читаются без изменений, привязки у провайдера нет. Провайдер на этом же компьютере (`127.0.0.1`) не зависит ни от VPN,
ни от интернета; облачный провайдер без VPN зависит от интернета.

## Зависимости команд

У каждой команды есть метаданные зависимостей (`command_deps.json`): какие источники нужны, нужна ли модель кита, нужен ли
интернет, может ли она работать без связи. Умолчания выведены из реестра команд: `sync:*` зависит от источника своего модуля,
команда с моделью — от LLM, команда без источников и модели работает и без связи; единичные команды правятся в файле. Профили,
без которых команда в проекте недоступна, **вычисляются** из режимов доступа источников и привязок провайдеров.

Закладка **«Команды»** показывает у каждой команды: ярлык типа (1 — зависит от источников или сети, 2 — от модели, 3 — ни от
того, ни от другого; ярлыки только для показа), VPN-профили, нужна ли модель, работает ли без связи и какие источники использует.

## Что происходит, когда связи не хватает

Проверка включена, а нужному делу связи не хватает — функция **не запускается** (а не падает таймаутом через минуты), и причина
названа: «VPN-1 недоступен (нужен источнику «Wiki»)», «интернет недоступен», «все провайдеры моделей недоступны — VPN-1 не
отвечает». Блокирует только **известное** «недоступно»: `unknown` (проверок ещё не было, у интернета нет адресов) не останавливает
ничего. Команды, которым связь не нужна (`kb:lint`, `kb:repair`, `net:status`…), идут всегда.

| Откуда запуск | Что происходит |
|---|---|
| Кнопка команды в панели | диалог с причиной и выбором: **встать в очередь** (задание ждёт восстановления без предела и стартует само; «Прервать» снимает ожидание) или **отменить** |
| Маршрут, кнопка «Пройти» | диалог со списком шагов, которым не хватает связи: **только доступное**, **встать в очередь** или **отменить** |
| Cron, боты по расписанию | политика (ниже): общая из раздела «Проверка соединения», у задания — своя |
| Синк источника из командной строки | скрипт не стартует: причина, код 2 и машинная строка `AURORA-NET {…}`, по которой маршрут и расписание узнают отказ по связи |
| Вызов модели | недоступного провайдера не трогают и в карантин не садят; недоступны все — отказ с причиной (разовый вызов) или ожидание (шаг маршрута) |

### Политики автоматических прогонов

| Политика | Шаг, которому не хватает связи |
|---|---|
| `fail_fast` | прогон не начинается (или шаг отказывает): причина в итоге, код «нет связи» |
| `partial` | шаг пропускается с пометкой, остальное идёт; итог — «частично», пропущенное названо |
| `queue` | прогон ждёт восстановления без предела и идёт целиком |
| `partial_queue` (по умолчанию) | доступное идёт сразу, недоступное откладывается и повторяется в конце — после восстановления (там ждёт) |

Блок «цикл:» не крутится вхолостую: шаг без связи останавливает оборот, блок повторится целиком после восстановления
(`partial_queue`) или пойдёт без этого шага (`partial`). Ожидание нигде не имеет предела по времени — маршрут доводит дело до конца,
пока его не остановит человек; «Проверить сейчас» будит ожидание. Политику узнаёт и процесс шага (`AURORA_NET_POLICY`): вызов
модели внутри него либо ждёт возвращения провайдеров (`queue`, `partial_queue`), либо отказывает сразу (`fail_fast`, `partial`):
шаг при этом печатает строку `AURORA-NET {…}`, по которой маршрут и расписание узнают отказ по связи, а не поломку.

Подробности, которые стоит знать:

- **«Частично».** Маршрут, в котором шаги пропущены по `partial` (или переданы расписанию), заканчивается как «пройден частично»:
  кнопка «Продолжить маршрут» остаётся и выполнит пропущенное, база не помечается обновлённой, отправка (push) не идёт. В Cron такой пункт
  — «частично» (пропущено) или «отложен» (передано цепочке, в конце она вернётся к нему и дождётся связи); остальные проекты цепочки
  связь не ждут.
- **Ожидание не отпускается без положительного ответа.** Если проверка не может завершиться (например, зависло разрешение имени),
  обычная сводка через три интервала считает профиль «неизвестным» и ничего не блокирует; ожидание же держит последнее известное
  «недоступно», пока не придёт хотя бы один положительный раунд. Проверка, которую нельзя выполнить (нет программы `ping`, сбой самой
  проверки), раунд не засчитывает совсем.
- **Продолжение и диалог.** Шаги, пройденные в прошлый раз, связи не требуют и в диалоге не перечисляются. Отказ до первого шага
  ничего не коммитит. «Остановить» слышно и во время ожидания, и в тот миг, когда связь вернулась.
- **Отложенный шаг и шаги после него.** Если шаг отложен до восстановления связи, а следующие за ним шли на прежних данных (разбор на
  старом зеркале), маршрут после отложенного шага «пройден частично»: шаги после отложенного назначены к повтору, «Продолжить маршрут»
  (а в Cron — повтор в конце цепочки) пройдёт их заново.
- **Метка при выходе.** Процесс агента, у которого последние вызовы модели не начались из-за недоступных провайдеров, выходит с
  ненулевым кодом и последней строкой `AURORA-NET {…}`: маршрут и расписание применяют политику прогона. Метка берётся из хвоста вывода.
- **Проверка ручки, которая не проходит одна.** Если профили и интернет в порядке, а не проходит только проверка ручки провайдера
  (путь или ключ проверки могли быть заданы неверно), вызовы всё равно пробуются, а ожидание прогона её не держит; команда, которой
  нужна модель, при этом остановлена с названной причиной «проверка ручки не прошла» — поправьте путь проверки в «Моделях».
- **Блок режимов в нестандартной записи.** Если `source_access:` записан многострочно в скобках, с якорем или в файле с несколькими
  документами YAML, страница блок не перепишет (отказ `unsupported`): поправьте файл руками.
- **Диагностика не блокируется.** `agent:ping`, `agent:probe`, `agent:width` спрашивают провайдеров живьём: они и нужны, чтобы увидеть,
  что с ними.
- **Один классификатор обрыва.** Вид обрыва (DNS, отказ соединения, таймаут соединения, маршрут, TLS, прокси, сброс…) называет
  классификатор движка (`agent_core.link_kind`, таблица причин `CAUSES`), тот же, что даёт тревогу связи `link:<n>` и строки
  «обрыв связи» в итоге прогона. Проверка соединений своего разбора не держит: обрывы с отметкой `conn` в таблице заставляют
  кольцо спросить проверку, не лежит ли профиль или интернет, а коды ответов probe (`timeout`, `refused`, `dns`…) получаются из
  тех же видов. Отказ вызова по связи несёт метку «обрыв связи» — прогон агента узнаёт по ней, что партия встала из-за связи.
- **Карантин.** Обрыв, который объясняет недоступный профиль или интернет, карантина не вызывает; если проверка узнала о падении позже
  первого обрыва, карантин, посаженный за него, снимается, когда связь вернулась.

### Что стало с прежним ожиданием

Проверка выключена — всё прежнее. Включена — каждое «ждём вслепую» заменено ожиданием по известной причине, а если причина
проверке не известна, остаётся прежнее:

| Было | Стало (проверка включена) |
|---|---|
| Прогон агента после обрыва: пауза 5 минут, до 24 раз (`OFFLINE_WAIT`, `OFFLINE_TRIES`) | все модели недоступны по проверке — ждём их возвращения, перепроверяя каждые 15 секунд; причина неизвестна — прежняя пауза |
| Шаг маршрута упал по сети: 15 минут (30 секунд, если шаг сделал работу), «Проверить сейчас» будит | причина известна — ждём восстановления по проверке и повторяем сразу; неизвестна — прежний ритм |
| Карантин провайдера в кольце: 15 минут после обрыва, «Вернуться на основного» | обрыв объясняет недоступный профиль или интернет — карантина нет, провайдер вернётся вместе со связью; настоящий отказ провайдера — карантин как раньше |
| Запрос к провайдеру, чей профиль лёг, уходил и падал по сроку | запроса нет: провайдер пропущен до возвращения профиля |
| Сторож шагов спрашивал модель и серверы источников прямыми запросами | берёт сводку проверки соединений по нужному делу; серверы, режим доступа которых не задан, опрашивает прямо, как раньше |
| Упавшая связь → прямой HTTP-запрос в обход адаптера | не делается: резерв прямого запроса — только при неисправном адаптере, не при потере связи |
| Cron: упавший шаг откладывался и повторялся в конце | шаг без связи откладывается тем же механизмом (`partial_queue`), повтор в конце ждёт восстановления |

## Команды

Только чтение и проверка — настройки пишет панель:

- `net:status` — состояние профилей, probe, интернета и провайдеров, режим работы и причины. Адреса probe не печатаются
  (`--targets` — печатать); `--json` — машиночитаемо.
- `net:probe` — проверить сейчас: все probe или `--only` (профиль или probe). Код 1, когда нужные профили недоступны. У
  выключенной проверки ничего не делает.

## Что где хранится

- Профили и probe — в ките, `local/connectivity.json` (на машине, в git не попадает, секретов нет). Это формат хранения, а не
  способ настройки: правится в панели, запись защищена от потерянного обновления (страница, открытая до чужой правки,
  получает отказ, а не затирает её), лишние поля файла при записи сохраняются.
- Рядом с настройками в `local/` живут служебные файлы: `.stamp-salt` (соль слепка страницы, с машины не уходит) и
  `models.json.broken-<время>` / `connectivity.json.broken-<время>` — копии файла, который не удалось разобрать, перед заменой
  по вашему согласию (права 600, хранятся три свежие). В копиях моделей могут остаться ключи: после смены ключа удалите их.
- Состояние проверок и журнал смен (права 600) — `~/.aurora/connectivity-state.json`: его пишут и фоновая проверка панели, и любой процесс,
  проверивший связь перед запуском.
- Данные в состоянии свежи один интервал; устаревшее перед запуском перепроверяется сразу (все probe разом, не дольше трёх
  секунд). Данные старше трёх интервалов считаются неизвестными.

Пример `local/connectivity.json` (адреса и имена — условные):

```json
{
  "version": 1,
  "enabled": true,
  "settings": {"interval": 60, "timeout": 3, "fail_after": 3, "ok_after": 2},
  "policy": {"auto": "partial_queue"},
  "profiles": [{"name": "VPN-1", "aggregate": "quorum", "quorum": 2}],
  "internet": {"aggregate": "any_healthy"},
  "probes": [
    {"id": "p1", "profile": "VPN-1", "type": "tcp", "host": "service-a.example.com", "port": 443},
    {"id": "p2", "profile": "VPN-1", "type": "http", "url": "https://service-b.example.com/health", "expect_status": ["2xx"]},
    {"id": "p3", "profile": "internet", "type": "tcp", "host": "example.com", "port": 443}
  ]
}
```
