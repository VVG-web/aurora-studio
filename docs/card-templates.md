# Шаблоны карточек базы знаний

Карточка базы знаний описывается **шаблоном** — файлом `TemplatesCommon/akdb_<тип>_v<версия>.md`
(например, `akdb_concept_v1.0.md`). В шаблоне записано всё, что нужно знать о типе: как он называется,
в каком разделе базы лежит, какие у него допустимые виды и статусы, из каких разделов состоит тело,
как выглядит шапка, пример готовой карточки и чек-лист самопроверки. Шаблон читает человек, ассистент
в IDE и **сам движок**: реестр типов берёт из него паспорт, а проверка карточки — правила.

Раньше «какие бывают типы» было записано пятью копиями таблицы «раздел → тип» в разных скриптах, а «как
выглядит правильная карточка» — словами в справке. Теперь место одно: модуль `card_types.py`.

Страница описывает то, что работает в ките сейчас. Чего пока нет, названо одним списком в конце
([что будет в следующих выпусках](#10-что-будет-в-следующих-выпусках)) и ниже как готовое не описывается.

## 1. Что работает сейчас

- Тринадцать шаблонов лежат в `scaffold/TemplatesCommon/` кита. Новый проект получает их при создании,
  существующий — при `aurora.py update <проект> --apply` (правило **seed**: новые файлы появляются под своими
  именами; изменённая проектом копия остаётся на месте, а версия кита ложится рядом как `<файл>.new`).
- Реестр типов (`card_types.registry()`) читает паспорта шаблонов. Таблица «раздел → тип» теперь одна:
  разбор, ремонт, линтер и схема берут её из реестра. Нет шаблонов — таблица прежняя, поведение не меняется.
- Команда **`kb:cards`** показывает реестр и проверяет карточки по шаблонам их типов (раздел 7).
- `kb:lint` печатает после итоговой строки раздел «шаблоны карточек» (раздел 8), `kit:doctor` — три строки
  о доставленных шаблонах.
- Проверка **только советует.** Разбор источников, ремонт и маршруты ведут себя как раньше; карточка без
  `template:` в шапке — «до-шаблонная», а не ошибочная. Ошибки шаблона `kb:cards` показывает
  предупреждениями (строгий режим — флагом `--strict`).

## 2. Устройство шаблона

Файл собран из зон сверху вниз:

| Зона | Что в ней | Читает |
|---|---|---|
| Паспорт | плоский frontmatter: название, описание, класс, раздел, виды, статусы, разделы тела, минимум связей | человек, ассистент, код |
| Комментарий-шапка | «ШАБЛОН: … КАК ПОЛЬЗОВАТЬСЯ: …» | человек, ассистент |
| Правила для ИИ | жанр, что живёт и чего нет в каждой части, границы с соседними типами, стиль | ассистент |
| Общий блок `AKDB:COMMON` | двенадцать общих правил — один и тот же текст во всех тринадцати шаблонах | ассистент, проверка на равенство |
| `## Шапка карточки` | скелет шапки с подсказкой у каждого поля (`# …` в карточку не переносится) | код, ассистент |
| `## Тело карточки` | скелет тела с комментариями `<!-- ИНСТРУКЦИЯ: … -->` | код, ассистент |
| `## Пример` | законченная карточка на нейтральных данных; проходит проверку без нарушений | ассистент, тест |
| `## Чек-лист самопроверки` | список `[ ]` | ассистент |
| Выжимка `AKDB:PROMPT` | короткий текст типа (до `prompt_chars` знаков) для запросов модели | код |

Паспорт — плоский frontmatter (вложенного YAML нет). К шести обязательным полям общих шаблонов (`artifact`,
`template`, `version`, `file`, `author`, `created`) добавлены поля типа:

| Поле | Значение |
|---|---|
| `card_type` | идентификатор типа: `concept`, `status-model`, `cited-document` … |
| `card_class` | `entity`, `source`, `record` или `map` (раздел 3) |
| `name`, `name_en`, `description`, `description_en` | название и описание типа на двух языках |
| `section` | раздел базы (`Concepts`, `Processes` …); у исправления пусто |
| `home`, `id_prefix` | у записей — папка мастер-файла в `Raw/` и префикс номера (`DR-`, `Q-`) |
| `kinds`, `statuses` | допустимые виды (первый — по умолчанию) и статусы |
| `sections` | разделы тела, которые пишет модель, в порядке |
| `fields_extra` | поля шапки сверх общего словаря |
| `min_links` | минимум исходящих ссылок (раздел 6) |
| `prompt_chars` | предел длины выжимки для модели |
| `migration` | `none`, `auto` или `llm`: как приводить карточки прежней версии |

Класс карточки в самой карточке **не хранится**: он читается из паспорта шаблона по `type`.

Шаблоны ищутся в таком порядке: `Templates/` проекта (свои типы и свои редакции), `TemplatesCommon/` проекта
(шаблоны кита, доставленные обновлением), а если типа нет ни там, ни там, — `scaffold/TemplatesCommon/` самого
кита. Файл проекта сильнее файла кита при любой версии. Неполный паспорт не роняет проверку: файл пропускается,
а `kb:cards --list` и `kit:doctor` называют проблему.

## 3. Тринадцать типов

| Тип (`type`) | Название | Шаблон | Класс | Раздел базы | Виды (`kind`; первый — по умолчанию) |
|---|---|---|---|---|---|
| `concept` | Понятие | `akdb_concept_v1.0.md` | entity | `Concepts` | knowledge, dictionary, document |
| `glossary` | Термин | `akdb_glossary_v1.0.md` | entity | `Glossary` | dictionary, knowledge, document |
| `process` | Процесс | `akdb_process_v1.0.md` | entity | `Processes` | knowledge, document |
| `system` | Система | `akdb_system_v1.0.md` | entity | `Systems` | knowledge, dictionary, document |
| `role` | Роль | `akdb_role_v1.0.md` | entity | `Roles` | knowledge, dictionary |
| `status-model` | Статусная модель | `akdb_status-model_v1.0.md` | entity | `Statuses` | dictionary, knowledge |
| `requirement` | Требование | `akdb_requirement_v1.0.md` | entity | `Requirements` | knowledge, document |
| `reference` | Справочник | `akdb_reference_v1.0.md` | source | `Reference` | dictionary, document |
| `cited-document` | Цитируемый документ | `akdb_cited-document_v1.0.md` | source | `Documents` | document |
| `decision` | Решение | `akdb_decision_v1.0.md` | record | `Decisions` | document |
| `question` | Вопрос | `akdb_question_v1.0.md` | record | `Questions` | document |
| `correction` | Исправление | `akdb_correction_v1.0.md` | record | — | — |
| `moc` | Карта | `akdb_moc_v1.0.md` | map | `MOC` | document, dictionary |

Классы:

| Класс | Что это | Типы |
|---|---|---|
| `entity` — сущность | знание о предмете; накапливается из многих источников | `concept`, `glossary`, `process`, `system`, `role`, `status-model`, `requirement` |
| `source` — дословный носитель | документ или таблица, ценность которых — точный текст | `reference`, `cited-document` |
| `record` — запись | написана человеком, из источников не выводится | `decision`, `question`, `correction` |
| `map` — карта | навигация: ссылки и аннотации без собственных утверждений | `moc` |

Что стоит знать о таблице:

- Сомневаетесь в типе — берите `concept`. Определение в одну–две фразы без свойств и правил — `glossary`;
  «система должна…», история, критерии приёмки — `requirement`; шаги ради результата — `process`;
  состояния и переходы одного объекта — `status-model`; то, что запускается и обменивается данными, — `system`.
  Границы разобраны в блоке «Правила для ИИ» каждого шаблона.
- Раздел `Documents` для цитируемых документов в схеме папок проекта ещё не заведён, а карточек этого типа
  движок не создаёт: шаблон описывает форму заранее (раздел 10).
- Решение, вопрос и исправление — **записи**: их пишет человек. Шаблоны описывают и мастер-файл записи в
  `Raw/`, но пока записи живут там, где жили: решения в `Decisions/`, вопросы в `Questions/`, исправления в
  `Raw/corrections/`. Исправление в базе карточкой не бывает: `kb:correct` вписывает его в целевую карточку.
- `spec` (раздел `Specs`) остаётся допустимым значением `type` **без шаблона**: такие карточки пишутся
  вручную по `Templates/spec_template.md`, проверка их не судит.
- Не вошли в набор: правило отдельной карточкой, интерфейс, сущность данных (это раздел «Правила» сущности,
  раздел «Интерфейсы» системы, понятие с разделом «Свойства»), а также спецификации, поставки и приёмка.
  Человек, организация, место и проект не вводятся: ни одной такой карточки в базах нет, а персональные
  данные — риск.

## 4. Тип, вид и статус — три разные оси

| Ось | Поле | Отвечает на вопрос | Значения |
|---|---|---|---|
| Тип | `type` | **о чём** карточка и **по какому шаблону** она составлена | идентификаторы реестра (раздел 3) |
| Вид | `kind` | **кому позволено править тело** | `knowledge` — тезис пишет модель; `dictionary` — переносится целиком; `document` — дословно, не меняется |
| Статус | `status` | **какой уровень доверия** (у решения — цикл `proposed → accepted \| rejected → superseded`) | `knowledge`, `draft`, `placeholder`, `deprecated`; `index` у карт |

Шаблон задаёт, какие сочетания допустимы: поля паспорта `kinds` и `statuses`. Тип записан папкой раздела:
карточка из `Processes/` — `type: process`.

## 5. Контракт карточки

**Шапка.** Обязательные поля зависят от класса. Для `entity` и `source`: `title`, `type`, `template`, `status`,
`created`, `updated`; `kind` — если у типа есть виды; для машинной карточки (`built: machine`) не-пустышки
ещё `sources` и `source_synced`. Для `map`: `title`, `type`, `template`, `status`, `updated`. Остальные поля — из
общего словаря (`aliases`, `tags`, `sources`, `built`, `related`, `trust`, `distilled`, `summary` и другие) или
из `fields_extra` типа. Поле `template` называет файл шаблона (`template: akdb_concept_v1.0.md`); у прежних
карточек его нет — это не ошибка, а «до-шаблонная» карточка. Даты — `ГГГГ-ММ-ДД`. В шаблонах нет поля `schema_version`:
версию формы карточки задаёт `template`; у прежних карточек поле допустимо и не трогается. Шапку читает единый
разбор движка, вложенный YAML недопустим.

**Тело** делится на собственную часть и служебный хвост. Проверяется только собственная часть:

```
[шапка]
[ведущий абзац-определение]                  ← первая строка, одна–две фразы
[## разделы типа — из закрытого списка, по порядку, без повторов]
[## Расхождения]                             ← пишет движок
[> 🎙 Из встречи …]                          ← пометка, если среди источников есть Raw/meetings
[## Под вопросом]
[## Источник (перенесено дословно)]          ← с этого места текст дословный, не проверяется
[## Исправления человеком]
[## История изменений]
[## Слияние]
```

Правила:

- Ведущий абзац — определение, не заголовок, не список, не таблица, не длиннее 600 знаков. Для `kind: dictionary`
  и `document` собственная часть может быть целиком переносом, для пустышки (`status: placeholder`) — заготовкой.
- Заголовок `##` в собственной части допустим, только если он назван в списке типа; порядок — как в списке;
  пустых разделов нет.
- Остатки шаблона (`{{…}}`, `<!-- ИНСТРУКЦИЯ`, `[ПРИМЕР]`, строка `TODO:`) в собственной части недопустимы.
- Заголовок `# Имя` допустим; если он есть в написанной моделью части (не в дословном переносе), он равен `title`.
- Хвост служебный: порядок `Под вопросом` → `Источник (перенесено дословно)` → `Исправления человеком` →
  `История изменений` → `Слияние`. Разделы `Не путать`, `Что относится к теме`, `Упоминается в`, `Названо в
  карточках` движок дописывает ниже собственной части сам.
- Если среди `sources` есть `Raw/meetings/…`, в собственной части обязательна пометка `> 🎙 Из встречи …`.

Разделы собственной части, которые пишет модель (необязательные, в этом порядке):

| Тип | Разделы |
|---|---|
| `concept` | `Свойства`, `Правила` |
| `glossary` | `Синонимы` |
| `process` | `Участники`, `Шаги`, `Исключения`, `Результат` |
| `system` | `Интерфейсы`, `Данные` |
| `role` | `Ответственность`, `Права и ограничения` |
| `status-model` | `Состояния`, `Переходы` |
| `requirement` | `Условия` |
| `reference`, `cited-document`, `decision`, `question`, `moc` | собственных разделов нет: тело — перенос или генерируется |

## 6. Связи

Карточка без связей — ошибка линтера, а в шаблонах это записано числом: поле `min_links` — сколько разных карточек
она обязана назвать (ссылки `[[…]]` собственной части плюс типизированные поля шапки; ссылка на себя и повторы
не считаются). Для пустышек, `kind: dictionary` и `document` минимум не проверяется: тело писала не модель.

| Тип | `min_links` | Что ожидается |
|---|---|---|
| `concept`, `system`, `role`, `status-model`, `requirement` | 1 | хотя бы одна смежная сущность: часть чего, что использует, объект, чьи статусы описаны, источник требования |
| `process` | 2 | участник (роль или система) и данные, результат или модель статусов |
| `decision`, `question`, `correction` | 1 | затронутая карточка (у вопроса — что он блокирует, у исправления — что исправляет) |
| `glossary`, `reference`, `cited-document`, `moc` | 0 | у термина связей может не быть; вход из карты обязателен |

Связь называется глаголом («входит в», «использует», «формирует»), а не «см. также». Поле `related:` ведёт
движок (`kb:links --cards`), руками его не заполняют.

Типизированные поля шапки — закрытый список; значение — ссылка `[[Имя]]` (одна или список), кроме `corrected_by`
(имена файлов исправлений, как их пишет `kb:correct`) и `answer_source` (путь в `Raw/`); у `corrects` допустимо и имя без скобок:

| Поле | Где допустимо |
|---|---|
| `supersedes`, `superseded_by` | сущности и решения |
| `same_subject` | сущности (зарезервировано: движок его пока не ставит) |
| `blocks`, `answer_source` | вопрос |
| `corrects` | исправление |
| `corrected_by` | сущности и дословные носители (ставит `kb:correct`) |
| `decisions` | требование |
| `prev`, `next` | цитируемый документ |
| `part_of` | части разрезанной карточки |

Граф базы строит рёбра по этим полям: `part_of` — «часть документа», `prev` и `next` — «следующая».

## 7. Коды нарушений (V-NN) и команда `kb:cards`

Серьёзность: `error` блокирует запись в строгом режиме, `warn` попадает в отчёт, `info` — только в статистику.
В обычном режиме (`--check` без `--strict`) ошибки показываются предупреждениями.

| Код | Серьёзность | Правило | Выпуск |
|---|---|---|---|
| V-01 | error | шапка не найдена или не разбирается | работает |
| V-02 | error | нет обязательного поля шапки (нет только `template:` — это сведение `info`: карточка до-шаблонная) | работает |
| V-03 | error | `type` не из реестра, тип выключен или не совпадает с типом шаблона | работает |
| V-04 | error | `template:` не называет существующий файл шаблона своего типа | работает |
| V-05 | error | `kind` вне допустимых для типа | работает |
| V-06 | error | `status` вне допустимых для типа | работает |
| V-07 | warn | поле шапки вне общего словаря и `fields_extra` | работает |
| V-08 | error | дата не в формате `ГГГГ-ММ-ДД` | работает |
| V-09 | error | заголовок `##` собственной части не из списка типа и не служебный | работает |
| V-10 | error | разделы не в порядке или повторяются; служебные заголовки не в порядке | работает |
| V-11 | — | зарезервирован, не используется | — |
| V-12 | error | первая строка собственной части — не определение, либо собственная часть пуста | работает |
| V-13 | error | в собственной части остались `{{…}}`, `<!-- ИНСТРУКЦИЯ`, `[ПРИМЕР]`, `TODO:` | работает |
| V-14 | error | строка `## Расхождения` не по грамматике | позже: с разделом расхождений |
| V-15 | warn | исходящих ссылок меньше `min_links` | работает |
| V-16 | error | типизированное поле не на месте или значение — не ссылка | работает |
| V-17 | error | запись: нет полей цикла, мастер-файл не в `Raw/`, зеркало не указывает на мастер | позже: с записями в `Raw/` |
| V-18 | info | `template:` старее наибольшей версии типа | работает |
| V-19 | error | среди `sources` есть стенограмма встречи, а пометки встречи нет | работает |
| V-20 | warn | нет `built: machine` и нет `sources`: происхождение неизвестно | работает |
| V-21 | error | цитируемый документ: нет `doc`, `unit` или `cite`, вид не `document` | позже: с цитируемыми документами |
| V-22 | error | у карты нет метки `<!-- ФАЙЛ ГЕНЕРИРУЕТСЯ` | работает |
| V-23 | error | `# Заголовок` собственной части не равен `title` | работает |
| V-24 | warn | служебный раздел (`Не путать`, `Что относится к теме`) стоит в собственной части | работает |
| V-25 | error | `status: index` у карточки, которая не карта и не «разрезана» | работает |

Проверка — чистая функция: без сети, без модели, результат детерминирован; на 3000 карточек — секунды.

### Команда `kb:cards`

Запуск в корне проекта (в панели — команда `kb:cards`; в терминале —
`python3 .aurora/scripts/card_types.py`):

| Вызов | Что делает |
|---|---|
| `kb:cards` или `--list` | таблица эффективного реестра: тип, название, класс, раздел, файл шаблона, откуда взят |
| `--show ТИП` | паспорт одного типа, версии шаблона и выжимка для модели |
| `--check [ПУТЬ…]` | проверить карточки базы (или только названные файлы и папки) по шаблонам их типов |
| `--check --strict` | то же, но ошибки остаются ошибками и дают код возврата 1 |
| `--stats` | карточек всего, по версиям шаблонов, без шаблона, с нарушениями по кодам |
| `--all` | с `--check` и `--stats`: включить архив базы (`_archive/`) |
| `--summary` | с `--check`: только итоговая строка |
| `--json` | машинный вывод |
| `--root ПУТЬ` | корень проекта, если запускаете не из него |

Код возврата: **0** — ошибок нет (в обычном режиме всегда, если проверка состоялась), **1** — есть ошибки в
строгом режиме, **2** — сбой: нет папки базы, нет шаблонов (реестр пуст — обновите проект командой `kit:update`),
нет такого файла или типа. Команда **ничего не пишет**: ни карточек, ни каталогов.

Как читать вывод `--check`:

```
kb:cards: проверено 13 · с шаблоном 12 · до-шаблонных 1 · ошибок 0 · предупреждений 4 · сведений 1 (советы: …)

V-06 · warn · карточек 1: статус вне допустимых для типа
   - AuroraKnowledgeDB/Concepts/Накладная.md:4: статус «imported» не из допустимых для типа «concept»: …
   как исправить: kb:trust пересчитывает статус по классу источника
```

Первая строка — итог: сколько проверено, у скольких стоит `template:`, сколько «до-шаблонных» (без него).
Дальше — группы по кодам: код · серьёзность · сколько карточек, затем до восьми примеров «путь:строка:
сообщение» и подсказка, как исправить. Если у реестра есть проблемы (неполный паспорт, два типа в одном разделе),
они печатаются строками «проблема реестра».

## 8. Связь с `kb:lint` и `kit:doctor`

`kb:lint` после итоговой строки «карточек N, ошибок M» печатает раздел **«### шаблоны карточек (предупреждения,
не ошибки)»**: сколько карточек проверено по шаблону, у скольких есть `template:`, сколько без него, сколько с
нарушениями и перечень кодов с числом карточек. Раздел только в полном прогоне (не с `--summary` и не с `--only`);
он ничего не меняет в итоговой строке, числе ошибок и коде возврата — хук pre-commit, панель и «Здоровье»
читают итог так же, как раньше. Подробности — `kb:cards --check`.

`kit:doctor` добавляет три строки-сведения: сколько шаблонов кита из тринадцати доставлено в проект (не хватает —
выполните `kit:update`), есть ли проблемы реестра и сколько карточек без `template:`. На итог доктора они не
влияют.

## 9. Версии шаблонов

Версия — часть имени файла (`_v1.0`). Старые версии не удаляются: карточка, составленная по `v1.0`,
проверяется по `v1.0`, пока её не переведут на новую. Версии сравниваются числами (`1.10` новее `1.9`), а
`kb:cards --stats` считает, сколько карточек отстало от наибольшей версии типа (код V-18).

**Выпущенный файл `akdb_*_v1.0.md` не правят.** Правило seed доставляет правку в старые проекты только как
`.new`, поэтому исправление или расширение — это новая версия (`v1.1`, `v2.0`) с полем паспорта
`migration: none|auto|llm` (`none` — старые карточки валидны навсегда).

### Свой тип или своя редакция типа

Положите в `Templates/` проекта файл `akdb_<тип>_v<версия>.md` с паспортом, как у шаблонов кита.

- **Своя редакция типа кита:** тот же `card_type`, `section` и `card_class`, версия любая. Файл проекта сильнее
  файла кита. Менять `section`, `card_class` или `card_type` нельзя: реестр отвергнет такой шаблон (проблема
  `V-REG-2`).
- **Новый тип:** новый идентификатор (2–31 знак: `a-z`, `0-9`, `-`), новый раздел — папка в `PascalCase`
  внутри `AuroraKnowledgeDB/`, объявленная в `paths.extra_structure_dirs` конфига; класс `entity`, `source` или
  `record` (карты создаёт только кит). Один раздел — один тип: два шаблона с одним разделом отключают оба типа
  до исправления (проблема `V-REG-1`).

Сейчас такой тип попадает в реестр и в проверку; создавать карточки по шаблонам проекта движок начнёт в
следующих выпусках.

## 10. Что будет в следующих выпусках

Здесь нет и как готовое не описывается: настройки типов в панели и блок `cards:` в конфиге; инструкция выбора
типа `Prompts/KB_classify.md` и каталог типов `AuroraKnowledgeDB/meta/card_types.md`; обязательность шаблона при
создании и изменении карточек (запись `template:` в шапку, отказ создавать карточку типа вне реестра); записи в
`Raw/decisions`, `Raw/questions`, `Raw/reference` и команда `kb:record`; цитируемые документы (раздел
`Documents`, команда `kb:cite`); миграция базы на шаблоны (`kb:conform`); раздел `## Расхождения` и лестница
«доверие → вопрос → исправление». До этих выпусков проверка остаётся советом, а правило «карточка только по
шаблону» — целью, а не действующим запретом.
