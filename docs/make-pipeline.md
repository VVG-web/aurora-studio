# «Продуктивность»: план, ремонт, отчёт и несколько артефактов

Раздел «Продуктивность» производит документ по базе знаний проекта. Внутри одного
запуска роли идут строго последовательно: сначала писатель, затем Момус, критик и
исправления. Параллельность есть только между независимыми артефактами.

## Что происходит с артефактом

1. Движок собирает пак знаний обычным гибридным поиском.
2. До первого вызова писателя сохраняется `plan.md` и `plan.json`: разделы шаблона
   становятся пунктами плана. Планировщик заменяет его версией 2, добавлением
   `steps`; если планировщик не ответил, остаётся план из шаблона.
3. Писатель создаёт первый черновик. Один писатель на весь документ: разделы не
   пишутся параллельно, иначе расходятся голос и стыки.
4. Момус проверяет утверждения без опоры. Его замечания получает критик.
5. Критик проверяет форму, полноту и замечания Момуса. Пока критик недоволен,
   писатель исправляет документ, но не больше двух раз.
6. После того как критик доволен, финальный Момус проверяет последнюю версию.
   Если критик недоволен после второго исправления, финальный Момус не запускается:
   сохраняется лучший черновик и отчёт с замечаниями.
7. Каждая версия черновика и каждый вердикт лежат в `Workspaces/<сессия>/run/`.
   Лучшая версия выбирается детерминированно по вердикту критика, числу замечаний,
   заполненности покрытия, числу утверждений без опоры и непустым разделам.

`ready` ставится только когда финальный Момус чист, замечаний критика нет и нет
опоры на непроверенные карточки. Во всех остальных случаях документ остаётся
`draft`, даже если он сохранён и открывается.

## Ограничения

Лимиты ограничивают зацикливание, а не полезную работу. У этапа нет бюджета времени.

| Параметр | По умолчанию | Что делает |
|---|---:|---|
| `hard_timeout_seconds` | 3600 | общий аварийный предел запуска, 60 минут |
| `max_attempts_per_stage` | 3 | транспортные повторы одного этапа |
| `max_same_error` | 2 | две одинаковые ошибки останавливают повтор |
| `max_no_progress` | 2 | две попытки без нового результата |
| `max_question_rounds` | 3 | потом план с допущениями |
| `max_repairs` | 2 | исправления после замечаний критика |
| `max_parallel_runs` | 3 | одновременных артефактов в панели |
| `warn_seconds` | 600, 1200 | предупреждения «долго», без остановки |
| `report_dir` | `Artifacts/reports/make` | папка отчётов руководителю |

Прогрессом считается новый этап, новый ответ модели, изменение черновика, новый
вердикт, новый статус пункта плана или ответ человека. Одинаковая ошибка, тот же
черновик и те же вопросы прогрессом не считаются.

## Остановка и продолжение

Остановка происходит по отмене, исчерпанию попыток, повторяющемуся состоянию,
фатальной ошибке или общему пределу 60 минут. При остановке сохраняются план,
манифест, лучший черновик, причина и отчёт. Кнопка «Продолжить работу» сбрасывает
счётчики попыток и продолжает с того же места, не пересобирая пак и уже пройденные
этапы.

Если обогащение не дало ни одной карточки, содержательный документ не пишется:
создаётся заготовка с задачей и разделом «Чего не хватает». Путь и отчёт остаются,
статус `draft`.

## Отчёт руководителю

Технический `report.json` лежит в `Workspaces/<сессия>/run/`. Отчёт для руководителя
пишется в `Artifacts/reports/make/<дата>_<вид>_<имя>_<сессия>.md` и открывается
кнопкой «Посмотреть отчёт» в панели.

В отчёте: что просили и что получилось, путь к артефакту и статус, план и проверки,
замечания критика и Момуса, что осталось невыясненным, время, вызовы, токены, модели
и запасные модели. Промпты, ключи, внутренние адреса провайдеров и пак знаний в отчёт
не попадают. Токены показываются как факт только при наличии usage, иначе с пометкой
«оценка» или «нет данных».

## Несколько артефактов

Панель запускает несколько производств одновременно и показывает их списком, как
консоль. У каждого запуска свои план, журнал, метрики, отчёт и кнопки. Переключение
не прерывает остальные. После перезагрузки список восстанавливается из
`/api/make/runs`; подробности запуска читаются из `/api/make/state`.

Внутри одного запуска критик и Момус не параллелятся. Одновременных запусков по
умолчанию три, это защита ресурсов, а не ограничение времени работы.

## Инструменты и Pydantic AI

Планировщик может сам искать по базе и читать файлы проекта. Эти инструменты
работают через Pydantic AI: прямой HTTP движка не умеет вести цикл «модель позвала
инструмент → получила результат → ответила» и не подключает MCP.

Если Pydantic AI не установлен или его venv не запускается, движок не отправляет
запрос с инструментами напрямую. Он пишет в журнал причину, отключает инструменты
и повторяет планирование без них. Документ можно получить, но план будет собран
без самостоятельного поиска.

Проверить окружение:

```bash
python3 .aurora/scripts/agent_core.py --venv-status
```

Установить или обновить Pydantic AI: «Установка» → Pydantic AI в панели или

```bash
python3 .aurora/scripts/agent_core.py --venv-install
```

После установки повторный запуск снова включает инструменты. В журнале запуска
появляется строка с причиной отключения, поэтому молчаливого перехода на ответ без
инструментов больше нет.

### Если «Установка» зелёная, а агент просит поставить Pydantic AI

Панель и агент могут смотреть в разные `AURORA_HOME`. Установка проверяет home
панели, а дочерний прогон читает окружение проекта: `.env.aurora.local` в проекте
может задать другой `AURORA_HOME`. Тогда venv и Pydantic AI установлены в одном
home, а прогон ищет их в другом.

Проверить с тем же окружением, с которым идёт проект:

```bash
python3 .aurora/scripts/agent_core.py --venv-status
```

Вывод называет `AURORA_HOME`, фактический Python адаптера и причину, если venv не
найден. Если в выводе есть подсказка «в ~/.aurora/venv/bin/python Pydantic AI есть —
проверьте AURORA_HOME», значит установка и прогон разошлись по home.

Другие частые причины:

- venv собран на Python, которого больше нет, или `bin/python` — битая ссылка;
- пакет поставлен в глобальный Python или в `site-packages` другого пользователя,
  а не в эффективный Python из `~/.aurora/config.json`;
- панель запущена до смены runtime и держит старый процесс Python;
- проект исполняет старую копию `.aurora/scripts/agent_core.py`, несовместимую с
  установленной версией пакета.

Панель «Установка» показывает `AURORA_HOME` и предупреждает, если `.env.aurora.local`
проекта уводит агента в другой home. Ошибка fallback в журнале тоже называет home,
фактический Python и причину.

В предупреждении есть кнопка «Убрать AURORA_HOME из проекта»: она удаляет только
строку `AURORA_HOME` из `.env.aurora.local`, остальные строки сохраняет и кладёт
рядом резервную копию файла. После этого агент снова использует home панели.

## Восстановление и приватность

`--session` продолжает сессию. Манифест сверяет SHA-256 черновиков, плана и
артефакта. Повреждённый черновик не удаляет работу: он помечается и заменяется
следующей версией. Готовые артефакты автоматически не удаляются.

Рабочее состояние и промпты лежат в `Workspaces/<сессия>/run/` и не уходят в git.
Отчёт руководителю и сам артефакт лежат в объявленных папках проекта.
